# 원래 benchmark 단일 DB 연결 복구 계획

**Goal:** 원래 benchmark가 사용하던 DATABASE_URL과 그 계정의 기존 전체 읽기·쓰기 권한을 그대로 재사용하고 프리뷰도 같은 연결 설정을 사용한다.

**Architecture:** 접속 자격 증명의 기준은 원래 app.core.config의 DATABASE_URL 하나다. 프리뷰 경기·이름·통계·인증·저장 caller가 같은 기준에서 연결을 얻는다. 새 계정, 전용 일반 읽기 계정, 제한 역할의 권한 합성, 신규 GRANT는 만들지 않는다. 기존 저장 위치·데이터·인증 API 권한은 유지한다.

**Tech Stack:** 기존 FastAPI/SQLAlchemy/PostgreSQL, 현재 shell 런처, Orca DeepSeek 구현/검토.

**Spec:** 2026-11-12 사용자 최종 지시: "원래 권한이 전체 조회 및 전체 쓰기 … 그대로 쓰면 된다". 이 지시가 직전 별도 읽기 역할·제한 계정 통합 제안을 대체한다. 앞선 계획은 실제 구현·권한 적용 전이었으며 전부 폐기한다.

**완료 보고 후 범위 정정:** 원래 계정은 public 전체 권한이 있으나 다른 계정이 만든 preview_dev 기존 표의 저장 권한이 없다는 실측이 나왔다. 위·아래의 신규 GRANT 전면 금지는 root가 추가한 제한으로, [마지막 실행 준비](../../implementation/match-preview/home-db-final-runtime-brief.md)에 명시한 기존 원래 계정·기존 preview_dev 표의 필요한 권한 보완만 허용하도록 정정한다. 새 역할·소유권 이전·public 권한/구조/행 변경·자동 migration은 여전히 제외한다. 이 정정 자체가 권한 적용 완료를 뜻하지 않는다.

## 범위와 소유

- HOME-DB-01: 별도 DeepSeek의 현재 서버 실제 연결·writer 권한 읽기 조사. 보고서 외 수정 없음. 새로운 권한 설계는 하지 않는다.
- HOME-DB-02: DeepSeek 구현자 단독. scripts/run_benchmark_dev.sh, app/db.py, app/preview/config.py, app/preview/db.py, 필요한 경우 기존 app/auth/identity.py와 preview source 연결 선택 경계. 검사 파일은 기존 직접 runtime/auth 검사 중 영향 사례 및 최소 단일 연결 사례만. frontend/생성 프롬프트/품질 정책/Plans는 편집하지 않는다.
- HOME-DB-R: 별도 DeepSeek 읽기 전용 검토 1회. 변경된 URL 선택·caller 연결·기존 데이터 보존·비밀값·대표 증거만 확인한다.
- ROOT: Plans·수용·기존 소유 백엔드 재시작·무인증 GET 확인. 구현 코드는 작성하지 않는다.

## Task HOME-DB-02 — 기존 DATABASE_URL 그대로 사용

사용자가 이미 복구를 지시했다. 별도 승인 요청 없이 구현하되 사용자 데이터 변경이나 새 역할 설계로 확대하지 않는다.

- [ ] 원래 repo .env/명시 DATABASE_URL과 app.core.config의 기존 로딩 규칙을 확인한다. 값은 출력하지 않고 현재 새 전용 DSN과 목적지가 같은지 확인한다. 다른 DB라면 임의 선택/복사하지 않고 차이를 보고한다.
- [ ] 런처가 원래 DATABASE_URL을 fixture 전용 계정으로 덮어쓰는 코드를 제거한다. 별도 BENCHMARK_READ_DATABASE_URL을 신설/요구하지 않는다. 원래 설정이 없으면 연결 오류를 명확히 알리고 프리뷰 전용/로컬 임시 DB로 대체하지 않는다.
- [ ] 프리뷰 경기·이름·통계·계정 조회·생성 결과 저장이 모두 원래 DATABASE_URL을 사용하도록 기존 설정/caller를 연결한다. 사용자가 별도 PREVIEW_* DSN 다섯 개를 관리할 필요가 없게 한다. 기존 내부 필드 호환이 필요하면 동일한 기준값을 제공하며 옛 환경값이 다른 계정으로 분기시키지 않게 한다.
- [ ] 원래 일반 backend 연결에 임의로 추가한 강제 읽기 전용 옵션을 제거한다. 기존 계정 권한을 축소·확장하지 않는다. 조회 전용 함수가 SELECT만 하는 것은 유지 가능하며, 전체 backend의 쓰기 연결을 막지 않는다.
- [ ] 기존 public 데이터와 preview_dev 저장 테이블·실행 증거는 이동·초기화·변경하지 않는다. SQLAlchemy Base/명시 스키마를 하나로 합쳐 새 테이블을 생성하는 작업도 하지 않는다. 같은 URL을 쓰는 것과 다른 저장 스키마를 유지하는 것은 모순이 아니다.
- [ ] ADMIN 생성 권한, 비로그인 공개 조회, 기존 JWT/사용자 역할은 유지한다. 이번 수정 검증을 위해 사용자 로그인·계정 변경·원격 세션 쓰기를 하지 않는다. 현재 로컬 로그인 세션의 저장 위치와 기존 행 무변경 동작은 별도 사용자 요청이 없으므로 유지한다.
- [ ] 최소 대표 검사로 일반/인증/preview reader/writer가 같은 원래 접속 자격 증명을 소비하고 fixture 전용 URL이 덮어쓰지 못함을 확인한다. 기존 가드가 있는 루프백 *_test 또는 DB 없는 합성 설정으로 검사하며 운영 DB에서 pytest/DDL/쓰기 탐침은 실행하지 않는다. 영향받은 auth/runtime 검사만 1회, 전체 suite 없음. 정확한 선택 nodeid/명령을 결과에 남긴다.
- [ ] 실제 DB의 SELECT 권한 및 필요한 preview_dev 저장 테이블 INSERT/UPDATE 권한은 메타데이터로 확인한다. 사용자 데이터를 쓰거나 모델을 호출해 확인하지 않는다. DSN/호스트 식별자/비밀번호/계정행/토큰을 로그나 보고서에 넣지 않는다.
- [ ] 정확한 변경 파일·caller 매핑·원래 설정과 현재 설정의 동일성·검사 명령/결과를 보고하고 EDITING STOPPED. 서버 재시작은 루트가 인계·한정 검토 후 수행한다.

## 완료 조건과 별도 문제

하나의 기존 DATABASE_URL로 통합 backend와 preview의 모든 DB caller가 연결되고 기존 권한이 축소되지 않아야 한다. 새 계정/GRANT/프로비저닝 스크립트/비밀값 복제는 0이다. 루트가 백엔드만 재시작해 원래 일반 조회와 홈 추천 GET을 확인한다. 새 프리뷰 생성·사용자 로그인·수집 자동실행은 하지 않는다.

현재 DB에 없는 기존 홈 발행 표가 확인되면 권한 문제와 별도로 보고한다. 이 계획만으로 public 마이그레이션이나 기존 저장 결과의 자동 공개를 승인한 것으로 해석하지 않는다. 연결 복구 결과와 남은 홈 저장 계약 문제를 정확히 구분한다.

## 검토 초점

원래 DATABASE_URL 우선순위와 동일 대상, 모든 caller의 단일 자격 증명, 일반 연결 강제 읽기 전용 제거, 기존 데이터/비밀값 보존, 테스트의 루프백 가드만 확인한다. 새 권한 아키텍처·전체 보안 리뷰·전체 회귀·커밋·배포는 제외한다.
