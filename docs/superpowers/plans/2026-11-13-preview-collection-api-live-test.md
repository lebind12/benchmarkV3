- **경기 수집/처리 기간:** 2026-11-21 21:30 ≤ 킥오프 ≤ 2026-11-22 00:00 KST. UTC로 2026-11-21 12:30~15:00, 양 끝 포함이다.

## 시험 프로세스에만 지정할 기간과 대상

기존 POST 계약에 존재하지 않는 기간/경기 ID를 넣지 않는다. DeepSeek이 작성하는 독립 시험 도구에서 입력 경계 두 곳만 제어한다.

1. **경기 수집 기간:** 실제 API-Football 응답을 받은 뒤 기존 경기 선택 단계에서 위 킥오프 구간만 처리한다. 저장·상세 후속 수집도 이 목록을 사용해야 하며 최종 출력만 가리는 시험은 허용하지 않는다. 가짜 응답/행을 만들지 않는다. 현재 원격 요청은 리그/시즌 단위이므로 API 요청량까지 두 경기로 줄었다고 주장하지 않는다. 팀/선수/순위 보조 수집은 현재 target 설정의 리그 범위임을 기록한다.
2. **프리뷰 후보:** 기존 후보 알고리즘에 판정 기준 시각18:00과 두 ID를 적용한다. 우선순위·NS·팀 연결·6시간 경계는 실제 함수를 통과한다. 후보를 수작업 합성해 판정을 생략하지 않는다. 생성 엔진·승인 판정·DB 세션·실패 격리·모델 전송은 대역으로 바꾸지 않는다.

이 시험은 **기간/판정 시각을 지정한 실제 수집 연동 시험**이다. 6시간 경계 알고리즘은 실제로 통과하지만 실제 날짜에 정기 스케줄러가 실행됐다는 근거와 구분한다. 정상 시계에 따른 운영 자동 실행 자체는 이후 확인에 남긴다.

후보의 실행 표시는 시험 ID와 경기 ID로 구별하고, 정기 수집의 같은 경기/회차 중복 키를 선점하지 않는다. 수집 실행 결과 안에 실제 두 프리뷰 실행 ID를 남겨 연결 근거를 유지한다. 기존 관리자 실행 ID와 새 실행 ID가 달라야 한다. 승인 게이트·경기별 실패 격리·재시도·생성 내용은 시험 대상으로 그대로 통과한다.

시험 설정은 실행 중인 8000/5173 서비스와 공유하지 않는다. 기존 앱을 별도 프로세스의 내부 API 클라이언트로 호출하며 웹 서버 재시작·새 상시 서버·별도 DB를 요구하지 않는다. 기간/후보 지정은 해당 시험 실행이 끝날 때까지 유지한 뒤 프로세스 종료로 해제한다. 실제 인증을 검증하고 기존 인증 설정을 재사용한다. 비밀값을 명령 인자·출력·산출물에 기록하지 않는다.

## 선행 수정 — 이미 배정된 PC-CONNECT 범위

독립 검토 `docs/implementation/match-preview/preview-collection-connect-review.md`의 현재 요구 위반4건만 수정하고 한정 확인한다.

1. preview 세션 팩토리가 실제 Session을 제공하도록 계약을 맞춘다. 대역 팩토리만 통과하는 검사를 실제 호출 단계까지 보완한다.
2. 수집의 정상 반환뿐 아니라 상위 예외 종료에도 기존 DB로 프리뷰를 한 번 시도한다. 명시 취소와 원래 수집 실패 상태를 보존한다.
3. 자동 생성 전에 기존 승인 판정을 적용한다. 승인 없음/버전 불일치/조회 실패를 정상 자동 생성으로 진행하지 않는다.
4. 예외 없이 반환된 FAILED 결과도 실패로 기록한다. 실패를 generated 목록에 넣지 않는다.

이번 지정 경기 시험을 위해 승인 정책을 우회하거나 자동 승인 POST를 보내지 않는다. 승인 조건이 맞지 않으면 실호출 전 그 상태를 보고한다.

## 실행 순서와 판정

1. **읽기 사전 확인.** 대상13·두 경기 식별자·기존 실행 ID·현재 승인 상태·live 모델 설정·새 preview_dev 저장 경계를 확인한다. 기존 실제 설정을 재사용하며 오래된 개별 실행 스크립트의 DB 환경 매핑을 복사하지 않는다. 프리뷰 연결 활성 조건이 필요하면 해당 시험 프로세스에서만 명시하고 보고한다. 자동 스케줄러는 켜지 않는다.
2. **내부 수집 API 1회.** 실제 ADMIN 인증으로 기존 POST `/api/v1/admin/management/runs`를 호출한다. 요청 계약은 target_ids=[13], mode=refresh, parent_run_id=null이다. 기간·판정 시각·두 ID는 시험 프로세스 입력에 기록하며 제품 요청 본문에 존재하지 않는 필드를 추가하지 않는다. 응답의 수집 실행 ID를 즉시 기록한다.
3. **수집 종료 추적.** 같은 run_id의 GET으로 관측한다. 실제 경기 처리 목록이 지정 기간 안이고 두 대상이 포함돼야 한다. 범위 밖 상세/경기 저장이 발생하면 기간 지정 실패다. 보조 팀/선수/순위의 원래 리그 범위는 별도 기록한다. `status`만 종료값이 됐다고 완료로 보지 않고 `finished_at`과 프리뷰 결과까지 확인한다. 응답/대기 오류가 나면 새 POST를 반복하지 않는다.
4. **실제 생성 확인.** 후보가 정확히1557470·1557476이며 각각 collection 시스템 호출·live 모드·새 run_id·최종 상태·저장 섹션이 있어야 한다. API-Football과 모델 호출 근거를 실제 기록에서 확인한다. 기존 관리자 bundle-runs를 별도로 POST해 성공을 보충하지 않는다.
5. **본문 및 최신 조회.** 첼시–리즈와 토트넘–입스위치의 새 저장본을 읽는다. 배당·기사 자료가 실제 부족하면 사유와 사용자 수용 수준의 핵심 본문으로 판단한다. 필수 본문 실패·파싱 실패·실제 자료 누락을 정상 부재로 분류하지 않는다. 공개 문서가 새 승인 가능 결과를 선택하는지도 확인한다.
6. **증거 보존과 종료.** 수집 ID·지정 기간·판정 시각·실제 실행 시각·경기 처리 목록·원래 수집 상태·API 최신화 결과·두 프리뷰 ID·최종 상태·자료 부족·최신 문서 선택을 저장한다. 수집 실패 후 DB 기반 생성 성공은 별도로 기록하며 수집 성공으로 표시하지 않는다. 시험 입력과 실제 호출 영역을 명시한다. 추가 전체 재생성·과거 경기·부하 시험은 하지 않는다.

수집 실행 목록 GET은 기존 코드에 과거 이력 정리를 포함하므로 이 시험 도구는 목록을 반복 조회하지 않고 반환된 특정 run_id만 추적한다. 계정·기존 경기 행을 시험 조건으로 조작하거나 기존 실행 기록을 삭제하지 않는다. 정상 수집이 수행하는 갱신 외에 별도 초기화/undo를 실행하지 않는다.

## 구현 파일·검증 경계

새 통합 시험 도구 후보: `scripts/preview_collection_live_once.py`(DeepSeek만 작성). 기존 앱을 내부 API로 호출하고 지정 기간·판정 시각·두 경기·실제 인증/수집/생성·결과 저장을 담당한다. 생성 엔진을 복제하거나 제품 라우트/화면을 추가하지 않는다. 기본 실행은 사전 확인이며 명시적 live 인자가 있어야 유료 호출과 수집을 수행한다. 실제 기본 DB 계약은 현재 앱 설정을 사용한다.

직접 검사: `tests/unit/test_home_preview_collection.py`에서 선행4결함 및 기간 밖 제외·끝 시각 두 경기 포함·승인/실패 격리를 우회하지 않는 연결만 확인한다. 시험 도구의 POST1회·기간 필터의 저장/상세 전달·기존 후보 알고리즘·실제 인증/전송·두 후보·정기 중복 키 미소비를 한정 검토한다. 테스트 수 목표나 환경 행렬은 없다. 실호출 명령/인자와 산출물은 구현 인계 때 실제 도구와 대조해 확정한다. 아직 없는 도구를 실행했다고 기록하지 않는다.

기록 파일: `docs/implementation/match-preview/preview-collection-live-evidence.md`. 민감값 없는 결과 자료는 필요 시 같은 디렉터리의 evidence 아래에 둔다. Plans.md만 현재 상태를 관리한다. 신규 시험 도구는 아직 배정하지 않았으며, 현재 사용자 요청에 따라 계획까지 정리한다.
