# 관리자 경기별 프리뷰 시험 → 수집·홈 연결 구현 계획

> **2026-11-12 대체됨 — 실행 금지:** 현재 계획은 [Benchmark Preview Integration](2026-11-12-benchmark-preview-integration.md)이다. 아래는 대상 오지정과 중단된 작업의 이력으로 보존하며, “현재 실행” 등의 표시는 더 이상 유효하지 않다.

> **대상 정정:** 사용자가 말한 관리 페이지는 원래 benchmark 프로젝트의 관리 페이지다. 아래 T2의 5173 `/admin/sections` 연결 지정은 조정자의 오류이며 해당 지정으로 진행하지 않는다. 이미 작성한 생성/저장 로직·UI는 보존하고 원래 프로젝트 화면에 재사용한다. 현재 백엔드 워커 작업은 사용자 지시로 중단했으며 중간 변경은 검증되지 않았다. 원래 실행 중인 프로젝트의 관리 라우트/소스/인증과 생성 API 경계를 확인한 뒤 T2 파일 소유권을 다시 확정한다. 별도 검사 화면을 실제 관리 화면으로 대체하지 않는다.

> 실행 방식: 프로젝트 AGENTS.md와 최신 사용자 지시를 적용한다. 백엔드 구현·독립 검토는 실제 DeepSeek, 프론트 구현은 사용자가 지정한 현재 GPT 세션이 맡는다. 계획에 구현 코드나 패치를 대신 작성하지 않는다. 1단계는 사용자 요청으로 실행하며 2·3단계는 직접 시험 결과를 확인한 뒤 진행한다.

**Goal:** 관리자가 경기 번호로 최신 프리뷰를 생성하고 DB 저장 결과를 확인하게 만든 뒤, 같은 생성 경로를 수집 과정과 경기별 홈 조회에 연결한다.

**Architecture:** 기존 bundle_pipeline의 LangGraph와 섹션 모듈을 재사용한다. 기존 preview_dev 실행·섹션·아티팩트 저장을 유지하고 관리자/수집은 같은 생성 진입점을 사용한다. 홈 GET은 저장 자료만 읽으며 생성·검색을 시작하지 않는다.

**Tech Stack:** FastAPI, SQLAlchemy/PostgreSQL preview_dev, LangGraph, 기존 Vertex 모델, Vue/TypeScript.

**Spec:** 현재 대화의 사용자 확정 사항 및 `../specs/2026-11-11-preview-sections-design.md`. 충돌 시 이 문서의 최신 확정이 우선한다.

## Global Constraints

- 경기 하나 선택 → 프리뷰 하나 생성. 자동 다경기 시험·일괄 생성 없음. 사용자가 직접 선택·실행·성공 판단한다.
- 한 생성 실행의 각 AI 논리 모듈에 최초 포함 최대3회. 다른 경기·이전 개발 시험 집합 사용량은 차감하지 않는다. 독립 전체8회 제한 제거. SDK/그래프 중복 재시도 금지.
- 429·503 등 일시 오류와 잘린/파싱 불가 응답은 모듈의 동일한3회 안에서 대응한다. 글의 질·출처 수·내용 부족을 재시도용 새 판정 엔진으로 만들지 않는다. 인증/설정 오류는 반복하지 않는다.
- 전망과 스코어는 현재 한 모듈의 한 응답이다. 이번 연결에서 별도 모듈로 분리하지 않는다.
- 생성된 부분 본문은 보존·표시한다. 기술적 전송/파싱/저장 오류와 사용자의 내용 평가를 분리한다. 일부 자료·섹션 누락만으로 전체 결과를 숨기거나 자동 재생성하지 않는다.
- 모델 출력40000, 실제 검색 요약 대체 근거, 이름 강조 prompt4 유지. 배당 없는 사실을 꾸미거나 목업 배당을 실제 저장하지 않는다.
- 기존 운영 경기·선수·계정은 읽기 전용, 새 저장은 preview_dev만. 기존 인증/ADMIN 사용. 새 DB·전역 스키마 초기화 없음.
- 프론트 목업5174와 현재 관리자5173/백엔드8000의 역할을 혼동하지 않는다. 삭제된 원본 제품 파일을 일괄 복원하지 않는다.
- 이번 구현 확인은 recorded 전송·대표 경로·기존 검사만. 새 유료 생성은 사용자가 관리자 버튼으로 실행한다. 자동 시험이나 실호출 smoke 금지.

## Review Focus

1. 서로 다른 경기 실행이 이전 모듈 사용량 때문에 막히지 않는가(T1).
2. 두 모듈이 각각3회 필요해도 전체8회 제한이 개입하지 않는가(T1).
3. 번호가 없는 경기·내부/외부ID 혼동 시 모델을 보내기 전에 멈추는가(T1/T2).
4. 부분 결과가 DB에 보존되고 기술 오류와 콘텐츠 판단이 혼동되지 않는가(T1/T2).
5. 관리자 재조회와 향후 홈 조회가 모델을 재호출하지 않는가(T2/T3).

## 단계와 의존 관계

T1 백엔드 경기별 생성·재시도·저장 → T2 관리자 버튼/저장 결과 확인 → 사용자 직접 시험 → T3 수집 트리거·경기별 홈 조회.

### T1. 경기별 생성 API와 모듈별 재시도 바로잡기 (현재 실행)

**담당:** DeepSeek 구현. 프론트 편집 금지.

**Files:** `app/preview/retry.py`, `provider.py`, `bundle_pipeline.py`, `modules/bundle_sections.py`, `app/api/v1/preview_admin.py`; 필요시 `sources/fixtures.py`, 기존 해당 테스트. 다른 호출자의 구동 변경은 직접 영향 범위만.

**Interfaces:** 기존 POST `/api/v1/admin/preview/bundle-runs`에 외부 fixture_id만 보내도 서버가 저장 경기의 리그·시즌·팀·킥오프를 해석하도록 확장한다. 기존 완전 입력은 보존하되 경기와 충돌하는 값을 받아 다른 경기를 생성하지 않는다. 조회용 GET `/api/v1/admin/preview/fixtures/{fixture_id}`를 같은 읽기전용 조회기로 제공한다. 응답은 기존 FixtureCandidate 계약을 사용한다. 실행 응답의 run_id로 기존 section-results/preview/information-bundle을 조회한다.

- [ ] 경기 번호 단건 조회·확인과 저장 경기 동일성 검사를 연결한다. 없는 번호/읽기 권한 없음은 실제 이유와 함께 전송 전에 거부한다.
- [ ] 현재 trial-set 누적3·전체8이 새 전체/재생성 경로를 막지 않도록 제거하고 실행별 논리 모듈3회 한도를 적용한다. 수치가 필요한 구 기록 계약은 모듈 한도 합계로 파생하되 독립적인 추가 제한으로 사용하지 않는다.
- [ ] 기술적 출력 실패의 재호출도 같은 논리 모듈 카운터 안에서 실행한다. 새 품질 평가/글 분량/근거 충족 기준은 추가하지 않는다.
- [ ] 현재 부분 본문·원문·실패 기록 저장은 보존한다. 필수 섹션 누락을 사용자의 콘텐츠 실패 판단처럼 전체 표시하지 않도록 실행 완료와 내용 진단을 분리한다. 저장/실행 자체의 실패는 숨기지 않는다.
- [ ] 기존 recorded 테스트에 위5항목과 재시도3회 거부 대표 사례를 필요한 만큼만 보완한다. 기존 관련 `test_retry_budget`, `test_provider`, `test_bundle_pipeline`, `test_bundle_sections`, `test_bundle_integration` 중 변경 영향 검사만 실행하고 실제 명령·결과를 보고한다. 전 테스트/유료 호출 금지.
- [ ] 응답 계약·변경 파일·버전·검증 결과를 인계하고 편집 종료한다. 기능 버전 변경에 따른 기존 승인 기록은 덮어쓰지 않는다.

### T2. 관리자에서 한 경기 생성·저장 결과 열람 (현재 실행, T1 계약 의존)

**담당:** 현재 GPT 세션 직접 프론트 구현. DeepSeek 독립 검토1회는 T1/T2 통합 후 직접 변경 경로만.

**Files:** `frontend/src/features/match-preview/api.ts`, `types.ts`, `SectionRunView.vue`, `FixtureSelector.vue` 중 필요한 화면, `MatchPreview.vue`, `SectionStructuredView.vue`. 현재 `/admin/sections` 경기 선택 경로를 재사용하며 새 앱을 만들지 않는다.

- [ ] 경기 번호 입력·조회 후 대진/시각 확인, 기존 목록에서 선택도 유지한다.
- [ ] `전체 프리뷰 생성` 버튼을 기존 bundle-runs에 연결한다. 클릭한 경기1개만 전송하고 진행 중 중복 클릭은 막는다. 자동 선택/자동 실행 없음.
- [ ] 응답의 run_id로 DB에 저장된 프리뷰/섹션을 GET하여 본문 우선 표시한다. 진단은 접어서 열게 하고 전체/섹션 재실행과 단순 재조회를 구분한다.
- [ ] 이름 **강조**를 안전한 strong 렌더로 표시한다. 사용자 성공 평가를 프로그램이 대신하는 배지·점수·새 승인 기능은 만들지 않는다.
- [ ] 기존 type-check와 영향 UI 검사, 실제 브라우저의 무호출 번호조회/저장 결과열람을 확인한다. 새 실제 생성 클릭은 사용자에게 남긴다.

### 사용자 직접 시험

사용자가 경기를 고르고 결과를 평가한다. 자동 시험 표본/성공률 계산/성공 임계값은 정하지 않는다. 요청한 섹션 수정은 해당 모듈만 조정·재실행하며 기존 성공 결과를 일괄 덮어쓰지 않는다.

### T3. 수집 파이프라인·경기별 홈 연결 (사용자 시험 후)

**현재는 구현 후보:** 이 작업트리의 앱은 preview 전용이며 원본 collection/home 서비스가 Git 이력에는 있으나 활성 코드에 없다. 원본 제품 실행 경로를 확인해 명확한 연결 대상과 파일을 정한 뒤 실행 계획을 구체화한다. 지금 별도 수집 엔진을 새로 만들거나 삭제된 소스를 전부 복구하지 않는다.

- [ ] 원본 수집에서 경기 자료 저장 완료 후 같은 bundle 생성 함수를 호출하도록 연결한다. 생성 시점·대상은 기존 수집 정책과 사용자 시험 결과로 확정한다.
- [ ] 경기 fixture_id와 저장 실행/섹션 구성본을 연결하여 홈이 읽을 저장본을 명시한다. 사용자 콘텐츠 승인과 기술 완료를 혼동해 자동 게시하지 않는다. 공개 조회에 원문 요청·계정·내부 진단은 내보내지 않는다.
- [ ] 홈 추천경기 선택 → 해당 fixture_id의 저장된 프리뷰 GET → 확정 디자인 렌더로 연결한다. 읽기 요청에서 생성 금지, 맨시티 고정 목업과 합성 배당 제거.
- [ ] 대표 경기1건에서 수집→생성→DB 재조회→홈 표시를 확인한다. 새로고침/서버 재시작 후에도 같은 저장 결과를 읽고 조회만으로 호출이 증가하지 않아야 한다.

## 종료 기준

1단계는 관리자에서 경기 번호를 확인하고 최신 생성 경로를 한 번 실행할 수 있으며 저장 결과를 다시 열 수 있을 때 끝난다. 생성 글의 성공 여부는 사용자가 판단한다. 최종 목표는 수집이 미리 저장한 해당 경기의 프리뷰를 홈에서 조회하는 것이며 관리자 시험 완료와 수집/홈 연동 완료를 별도로 보고한다.
