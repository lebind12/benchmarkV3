# 검색 응답 대체 근거·모듈 결과 조합 구현 계획

> 실행: 사용자가 설계 기준에 동의하고 구현·실제 생성 결과 확인을 명시 요청했다. 조정은 GPT, 구현과 별도 독립 검토는 실제 DeepSeek 세션으로 진행한다. 추가 계획 승인 대기를 두지 않는다.

**Goal:** 본문 수집 실패에도 실제 검색 응답과 DB 자료로 프리뷰를 작성하고, 모듈별 선택 결과를 조합해 최종 AI 결론 및 독자 화면까지 저장한다.

**Architecture:** 기존 LangGraph·provider·information bundle을 확장한다. 실제 확보한 기사 본문 → 실제 검색 자료 → DB 순으로 작성 자료를 선택하고, 선택 결과 ID 집합을 명시한 구성본에서 마지막 AI를 호출한다. 검증은 데이터 연결·응답 형식·실제 저장을 확인하며, 근거 강도를 이유로 본문 전체를 반려하는 별도 사실 심사 엔진은 두지 않는다.

**Tech Stack:** 기존 Python/FastAPI/SQLAlchemy/LangGraph/Google Gen AI 및 Vue. 새 검색 서비스·브라우저 배포·새 실행 엔진 없음.

**Spec:** [확정 설계 최신 절](../specs/2026-11-11-preview-sections-design.md).

## Global Constraints

- 문체 유지. 팀당 선수2명 목표·부상 최대2명·매체 최대3곳·배당 정규시간1X2. 없는 점수·배당·부상 사건을 만들지 않는다.
- 원문 수집 실패와 작성 실패를 분리한다. 본문 미확보를 이유로 검색 자료를 버리지 않는다. Google grounding 메타데이터는 필수 승인 조건이 아니다.
- 실제 검색 도구 반환 자료와 모델이 별도로 쓴 설명을 구분한다. 도구가 제목·요약문을 직접 노출하지 않는 경우 모델 산문을 검색 스니펫이라고 명명하지 않는다. 실제 제공 필드·원문 응답을 확인하고 가능한 경로와 한계를 조정자에게 조기에 보고한다.
- 새 자료·출력 계약 변경 워크플로우의 모듈별 실제 전송 상한3회. 이번 변경 시험의 run 집합을 명시하며 이전 시험의3회 도달 기록은 과거 별도 버전으로 보존한다. 자동 재시도·무한 복구·새run으로 동일시험계수 초기화 없음. max_output_tokens40,000, 정상 전체 실행6논리호출, 동시2, HTTP24.
- 원문·전송 장부는 후처리 실패에도 보존한다. public읽기전용·preview_dev실행소유쓰기만, 기존 인증·권한·비밀값·기존800개 이상삭제보존. 비밀값은 출력하지 않는다.
- 수집 상태·대체 자료 유형·진단은 관리자와 로그에만 표시한다. 독자용본문·홈UI에 내부 설명을 섞지 않는다.
- 워커는 Plans.md를 수정하지 않고 사용자 승인을 자동 생성하지 않는다. git add/commit/push 및 배포는 이번 범위에서 하지 않는다.
- 기존 테스트 강제 종료 요청을 존중해 전체/반복pytest·vitest·추가 벤치마크·유료smoke를 실행하지 않는다. 변경 계약의 정적 확인·기존 저장 응답 재처리·실제 생성과 저장값 확인을 사용한다. UI 변경 시 필요한 type-check만1회 한다.

## Review Focus

- 403/404/301/JS shell을 전부 추출기 실패로 뭉개지 않고 실제 자료 확보 단계와 대체 사용 여부가 구분되는가.
- 실제 검색에서 반환하지 않은 요약·URL을 수집한 원문처럼 표시하지 않는가.
- 서로 다른 실행의 같은 경기 결과 버전을 선택해 마지막 AI에 실제 전달하며 선택되지 않은 최신 결과를 몰래 섞지 않는가.
- 마지막 AI는 새 검색·추가 사실 반려 없이 선택 결과로 결론을 쓰며 내부 ID·실패 진단이 독자 본문에 들어가지 않는가.
- 빈 본문·불완전 JSON을 성공으로 위장하지 않고 부분 결과·원문·장부·실패 단계가 보존되는가.

## 작업·소유권

### SF-01 실제 검색 자료 보존·대체 입력·선택 구성본 통합

단일 DeepSeek 구현자가 기존 discovery.py/information_bundle.py/retrieval.py/modules/bundle_sections.py/bundle_pipeline.py/section_preview.py/presentation.py/store.py/contracts.py/version_manifest.py/registry.py/sections.py/preview_admin.py와 필요한 기존 프롬프트·실제 실행 스크립트 및 match-preview UI를 소유한다. 거대 리팩터링·범용화는 하지 않는다.

- [ ] 저장 검색 응답의 실제 필드 및 호출 설정을 읽고 도구 원문과 모델 산문 경계를 정한다. 구체적인 검색 자료 계약·원문 artifact 연결을 section-interface-manifest.md에 먼저 공지한다.
- [ ] 검색 결과의 실제 제목·요약·URL·시각·자료유형을 보존하고 작성 입력으로 넘긴다. 본문 확보 시 본문 우선, 실패 시 검색 자료 사용, 검색 자료도 부족할 때 DB를 사용한다. URL만 있으면 기사 내용을 추정하지 않는다. 리다이렉트의 예외 경로를 최소 수정하고 홉 전송계수는 유지한다.
- [ ] 모듈별 독립 재생성의 선택 결과 ID 집합을 API→저장 구성본→최종 AI 입력까지 연결한다. 서로 다른 실행의 동일 경기 결과를 선택할 수 있으며 기존 결과는 불변이다. 마지막 AI만 재실행할 수 있어야 한다.
- [ ] 새 구성본과 마지막 결론을 독자 프리뷰로 투영하고 기존 관리자 UI에서 본문·근거·검색/본문/DB 자료 구분과 선택 결과를 확인하도록 연결한다. 직접 본문 편집·출처 선택기를 추가하지 않는다.
- [ ] 정적 계약/형식 및 저장 응답 재사용으로 직접 연결을 확인하고 정확한 필드·변경 파일·버전·실패 사유와 EDITING STOPPED를 보고한다. 유료 실행 전 조정자의 연결 수용을 받는다.

### SF-02 한정 독립 검토

- [ ] 별도 DeepSeek 읽기전용 세션에 위 Review Focus와 변경 파일·기존 증거를 전달한다. 보고서는 search-fallback-review.md 한개다. 코드·테스트·외부호출·DB쓰기 없음, 전면 구경로 재검토 없음.
- [ ] 현재 요구 위반과 참고 개선을 구분한다. 수정이 필요하면 구현자에게 해당 항목만 반환한다. 이미 통과한 항목을 반복 심사하지 않는다.

### SF-03 실제 생성·모듈별 보완·결과 인계

- [ ] 새 워크플로우 버전·시험 run 집합에 모듈별3회 상한을 전송 전에 적용하고 전체 생성1회 실행한다. 실패하면 기록을 먼저 확인하고 해당 모듈만 보완한다. 다른 성공 모듈을 자동 재호출하지 않는다.
- [ ] 생성된 각 섹션·전체 프리뷰·실제 선택입력·출처·원문/응답·finishReason·추론/후보 토큰·전송/HTTP계수를 저장 후 다시 읽는다. 선택 섹션 부족은 원인을 명시하고 없는 사실로 채우지 않는다.
- [ ] 기존 backend8000은 최종 코드 반영 시 조정자가 한 번 재시작한다. frontend는HMR우선. 기존 로그인·공개 자료를 변경하지 않는다.
- [ ] 조정자가 생성 본문과 남은 실패의 정확한 단계·원인·확인 URL을 사용자에게 전달하고 Plans.md를 갱신한다. 구현 워커·검토 워커는 인계 종료 후 정리한다.

## 자체 대조

기사 미확보 시 실제 검색 내용 활용, DB대체, 사용자 선택 모듈별 조합, 마지막 AI의 추가 출처 검증 없음, 독자/관리자 구분, 모듈별 호출3·출력40,000·과거 증거 보존을 각 작업에 반영했다. 제품 구현·실제 연동·사용자 승인 완료 여부는 별도로 보고한다.
