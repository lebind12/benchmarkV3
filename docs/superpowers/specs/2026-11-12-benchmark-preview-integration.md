# benchmark 프리뷰 통합 — 사용자 요구와 연결 기준

기준일: 2026-11-12 KST. 상태: 사용자 계획 확인 후 BI-01~03 구현 진행. 실제 생성은 사용자 직접, 수집 자동화·배포는 후속이다.

## 1. 목표

별도로 개발한 프리뷰 생성 기능을 **원래 benchmark 백엔드의 기능으로 통합**한다. 원래 benchmark 관리 화면에서 경기 번호를 입력해 생성하고, 같은 DB에 저장한 결과를 다시 읽는다. 사용자가 결과물을 직접 시험한 뒤, 같은 생성 함수를 기존 수집 종료 경로와 홈의 경기별 조회에 연결한다.

프론트가 별도 프리뷰 서버나 배포 API를 우회 호출하는 구조를 최종 구조로 삼지 않는다. 원래 benchmark 앱 안의 `app/preview/`는 유지할 수 있다. 모듈 디렉터리가 분리돼 있는 것과 서버·제품이 분리돼 있는 것은 다르다.

## 3. 목표 구조와 소유권

| 경계 | 통합 후 책임 |

| `app/preview/config.py`, `app/preview/db.py` | 현재 preview 설정/개발 저장 연결을 전용 이름공간으로 이동. 기존 테이블명·스키마는 그대로 |
| `app/services/match_preview.py` | 경기 번호를 해석하고 기존 LangGraph를 실행하는 단일 서비스 진입점 |

| `frontend/` | 원래 benchmark 앱을 정식 소스로 사용. `out/` 복사본을 영구 실행 소스로 삼지 않음 |
| `app/services/home_preview.py` | 추천 정책 유지, 후속 단계에서 새 저장 프리뷰를 경기 번호로 조회 |

DB 연결은 목적별로 분리하되 FastAPI 앱과 생성 엔진은 하나다. preview의 `Base`를 원래 public 모델의 `Base`와 합치지 않는다. 인증된 actor의 ID를 넘기기 위해 가짜 계정이나 고정 ADMIN을 만들지 않는다.

## 4. 현재 단계: 관리자 시험까지

- 5173은 원래 benchmark 프론트, 8000은 통합된 로컬 benchmark FastAPI로 연결한다. 배포된 Koyeb에 의존해 로컬 신규 기능을 시험하지 않는다.
- 기존 로그인 화면·계정·비밀번호 검증·ADMIN 권한을 재사용한다. 프리뷰 실행은 ADMIN만 허용한다. 기존 관리 화면의 STREAMER 권한은 별도 정책대로 보존한다.
- 원본 로그인은 `last_login_at`을 갱신하고 원격 refresh 저장소를 사용한다. 로컬 시험에서는 이 갱신을 하지 않고 세션을 `preview_dev`에 저장한다. JWT 응답·refresh 쿠키·`/me`라는 원본 프론트 인증 계약은 유지한다. 운영 세션·계정은 변경하지 않는다.
- 관리 화면의 기존 네 탭은 유지한다. 확인한 원본에 전용 폼이 없으므로 **`/admin?tab=preview`의 프리뷰 탭**을 연결 위치로 계획한다. 구현 시작 시 더 최신 원본에 해당 폼이 확인되면 중복 탭 대신 그 폼을 사용하고 경로를 계획에 정정한다.
- API-Football 외부 경기 번호 하나 → 저장 경기의 대진/리그/시각 확인 → 명시적 생성 클릭 → DB에 저장 → 같은 run ID로 다시 읽기.
- 실제 생성을 누르는 사람은 사용자다. 자동 표본 선정·첫 시험·다경기 일괄 생성·유료 smoke를 수행하지 않는다.
- 본문을 먼저 표시하고 원문 요청/응답·검색 요약·수집 실패·전송 횟수는 펼치는 진단으로 유지한다.
- 부분 본문도 저장·표시한다. 글 길이·출처 수·선택 섹션 부족으로 전체 결과를 숨기거나 자동 재생성하지 않는다. 기술 오류 기록과 사용자의 콘텐츠 성공 판단을 구분한다.
- 기존 섹션 재생성·구성본 선택·마지막 AI 결론 흐름은 보존한다. 같은 경기의 선택 버전만 조합하고 최종 AI에서 새 검색·출처 재검증을 하지 않는다.

## 5. 재시도 의미

한 번의 경기 생성 실행에서 **각 논리 AI 모듈의 최초 전송 포함 최대 3회**다. 정상 경로는 조사 두 모듈·선수·부상·매체·최종 전망의 여섯 모듈이며 배당은 모델 0회다. 전망과 예상 스코어는 현재 같은 모듈의 한 응답으로 유지한다.

예: A 경기에서 선수 작성이 429→잘린 JSON→정상 응답으로 3회를 써도, A 경기의 최종 전망은 자신의 3회, B 경기는 각 모듈의 새 3회를 가진다. 성공한 모듈은 다시 보내지 않는다. 실패한 모듈이 네 번째를 보내는 것은 거부한다.

- 전체 독립 8회 제한과 trial-set을 통한 다른 실행/경기 누적 차감을 제거한다. 여섯 모듈×3=18은 가능한 전송 수의 산술적 설명이며 새 공용 예산을 배분하는 정책이 아니다.
- 429·503·요청 타임아웃·MAX_TOKENS 절단·JSON 파싱 실패는 해당 모듈의 남은 횟수로 처리한다. 인증/설정 오류, 문장의 품질·길이·내용 부족은 자동 반복하지 않는다.
- 같은 실행을 복구할 때는 전송 전 장부를 읽어 이미 사용한 횟수를 보존한다. 새 run ID를 내부적으로 만들어 실패 재시도를 초기화하지 않는다.
- SDK/그래프/호출자가 각각 중복 재시도하지 않는다. HTTP 수집 홉 횟수는 AI 모듈 재시도 횟수와 분리한다.
- 모델 동시 2, 요청당 타임아웃 300초, 출력 상한 40,000은 유지한다. 기존 전체 1,800초 기한이 모듈별 재시도보다 먼저 잘라내는지 함께 확인해 새 생성 경로의 별도 전체 중단 기준으로 사용하지 않는다. 요청별 타임아웃·명시적 취소·기술 실패는 계속 기록한다.
- 문맥 수집은 기사 본문 → 검색 기반 AI 요약과 인용 주소 → DB를 활용한다. grounding 메타데이터 부재만으로 요약을 버리지 않는다.

## 6. 관리자 시험 이후의 목표

사용자가 결과물을 직접 보고 다음 단계 진행을 정한다. 자동 성공률·완성도 문턱을 만들지 않는다. 시험/조정의 결과로 섹션 워크플로우 버전 승인을 기록하며, 매 경기마다 승인을 요구하지 않는다.

다음 단계는 별도 실행 단위로 진행한다.

1. 확정한 디자인에 필요한 독자 JSON 계약을 만들고, 저장된 결과를 그 계약으로 투영한다. 새 원문 생성이나 요약 호출 없이 전망/점수 → 주목 선수 → 부상 → 외부 매체/배당 순서로 표시한다.
2. 경기별 표시본의 연결은 `preview_dev` 안에 둔다. 기존 원문·섹션 버전을 보존하며 원래 public 프리뷰 테이블을 개발 작업으로 변경하지 않는다. 승인되지 않은 워크플로우 시험 결과가 기본 공개 결과로 자동 채택되지 않게 한다.
3. 기존 `/home/fixtures/{external_id}/prematch`가 해당 경기의 저장본을 읽고, 원래 추천경기 선택 UI가 그 응답을 렌더한다. GET은 모델·검색·스크래핑을 시작하지 않는다. 합성 배당과 맨시티 고정 JSON은 제품 응답에 포함하지 않는다.
4. 원래 수집 완료 hook에서 같은 생성 서비스를 호출한다. 새 스케줄러·별도 생성 엔진을 만들지 않는다. 원래 후보/시간 정책(현재 NS·6시간 이내)은 후속 계획에서 사용자 시험 결과와 함께 확인하며, 관리자 번호 시험에는 적용하지 않는다.

## 7. 실행·검증 범위

계획 승인 전 코드·서버·DB를 변경하지 않는다. 최신 사용자 제공 AGENTS.md를 적용해 프론트를 포함한 구현·테스트·설정은 실제 DeepSeek, 독립 검토는 별도 DeepSeek 세션이다. GPT는 계획·연결 확인·수용을 맡는다. 독립 검토는 단위별 1회, 수정 확인은 지적 항목만 한다.

공통 작업트리의 변경·삭제·미완성 코드를 먼저 보존하고 파일별로 병합한다. 전체 checkout/reset·자동 커밋·광범위 테스트·새 평가 프레임워크는 범위 밖이다. 검증은 바뀐 연결, 모듈 재시도, 기존 영역 무변경, 저장 후 재조회에 한정한다. 현재 지원에 필요한 읽기 권한이 없다면 부족한 테이블/권한을 명시하고 해당 연결만 중단한다. 운영 관리자 DSN을 대체 연결로 사용하지 않는다.
