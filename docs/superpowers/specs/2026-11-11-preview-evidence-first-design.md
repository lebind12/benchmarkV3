# 경기 프리뷰 자료 우선 생성 설계

작성: 2026-11-11, GPT 조정자. 상태: 접근법 ③ 사용자 선택 완료. 세부 설계는 승인 전 초안이며 제품 구현·설치·유료 호출은 하지 않았다. 독립 DeepSeek builder 검토 1회 후 다섯 질문의 설계자 판단을 반영했다(§17).

## 최신 대화에 따른 설계 재검토: 기존 Vertex 검색 + URL 본문 수집

### 섹션 구성 토의 — 사용자 확정 및 미결정

추가 사용자 확정: 외부 전망은 서로 다른 매체 최대3곳을 매체별로 표시한다. 각 매체가 제시한 예상 스코어와 이유를 유지하며, 점수가 없는 기사는 전망 요약만 포함하고 점수를 생성하지 않는다. 매체들의 차이를 보존하고 우리 AI의 최종 예상 스코어와 판단은 별도 섹션으로 작성한다.

사용자는 경기 전망, AI 예상 스코어, 주목 선수 각 팀2명, 주목할 부상 선수 각 팀2명, 외부 매체의 예상 스코어와 이유, 외부 사이트 배당을 섹션으로 구성하고 동일한 수집→정보 원문→작성 흐름을 적용해 한 프리뷰로 조합하기를 원한다. 사용자 답변으로 다음을 확정했다. 선수 근거는 웹과 DB를 함께 찾되 모든 선수에게 둘 다 확보되어야 하는 조건은 두지 않는다. 부상 선수는 팀당 최대2명으로 하고 확인된 인원이 적으면 확보된 인원만 표시하며 불확실한 선수를 확정 부상자로 만들지 않는다. 배당은 우선 정규시간 홈승/무승부/원정승 소수점 배당으로 비교하고 수집시각을 보존한다. 확보하지 못한 값은 생성하지 않는다.

공통 수집과 자료 저장을 공유하되 섹션별 출력 계약은 구분하고, AI 전망/점수는 함께 작성해 일관성을 유지하며 마지막 조합은 새 사실을 추가하지 않는 방식이 현재 제안이다. 외부 매체 전망의 건수/표현 및 모듈 배치·전체 호출 예산은 아직 미결정이며 이 절은 구현 승인이 아니다.

### 최신 확정 방향 및 1차 시험 범위

사용자는 브라우저 없는 수집 자료와 DB 자료로 먼저 정보 원문 묶음을 구성하고, 그 묶음에서 프리뷰 원문을 작성하도록 설계 변경 및 현재 모듈 테스트를 지시했다. 일반 HTML은 Scrapling HTTP 수집과 Trafilatura 본문 추출을 사용한다. JavaScript 페이지는 내장 JSON 또는 공개 본문 API를 직접 읽을 수 있는지 확인하며, 브라우저 자동 실행을 배포의 필수 의존성으로 두지 않는다. 직접 읽지 못하는 기사는 다른 기사 또는 API·DB 자료로 보완한다.

정보 원문은 기사 본문·URL·수집 시각과 API·DB의 경기 자료·조회 시점·식별자를 출처별로 유지하는 작성 입력이다. 기사와 DB 중 하나로 덮어쓰거나 교차 검증으로 탈락시키지 않는다. 생성 모델은 이 입력을 읽고 한국어 프리뷰를 작성하며, 선수 선정/선정 이유 및 DB 한글명 정책을 유지한다. chunks/supports 유무를 기사 채택의 필수 조건으로 삼지 않는다.

1차 시험은 주목선수 R4 한 섹션의 격리된 실험이다. 저장된 검색 URL 후보를 재사용해 불필요한 검색 호출을 하지 않고, 브라우저 없는 실제 자료 수집과 DB 읽기 후 정보 원문 및 실제 생성물을 함께 남긴다. 작성 모델 전송은 최대 1회, 재전송·모델 교체·전체 그래프·자동 승인·배포는 제외한다. 실험용 코드와 결과는 제품 기본 경로와 분리하며, 이 시험 성공은 전체 기능 연결 또는 섹션 사용자 승인을 뜻하지 않는다. 전체 확장 시 검색 공유 및 호출 예산은 후속 결정한다.

### 사용자 확정 채택 정책 — 2026-11-11, 아래 이전 검증 제안보다 우선

해당 경기의 외부 프리뷰·전망 기사에서 주목 선수와 선정 이유를 먼저 가져온다. 기사 본문을 확보한 경우 해당 기사를 근거로 활용하며, API·DB와 교차 검증하거나 충돌을 이유로 기사 내용을 제외하는 절차는 두지 않는다. 본문 수집은 인용할 실제 내용을 확보하기 위한 과정이며 별도 사실 심사 엔진을 만들기 위한 과정이 아니다. 기사를 확보하지 못하면 API·DB의 과거 경기 자료를 바탕으로 AI가 선정·전망한다. AI 자체 전망의 사실 입력은 해당 API·DB 자료에 연결한다. 기사에 없는 내용을 기사에서 나온 것처럼 추가하지 않는다.

프리뷰 화면에는 내용 중심으로 표시하며 근거 등급·검증 기준·충돌 판정 문구를 노출하지 않는다. 기사 URL과 수집 본문, 생성 입력 및 기사 기반/AI 자체 판단 구분은 관리자 검사 기록에 보존한다. 아래의 문장별 함의 검증·숫자 재대조·API 충돌에 따른 기사 탈락 같은 기존 제안은 이 정책과 충돌하는 범위에서 채택하지 않는다. 라이브러리와 실행 예산은 조사 및 추가 설계 대상으로 남으며 이 문단은 구현 승인이 아니다.

사용자는 검색 자체는 이미 실행되고 있음을 지적하고, 모델 evidence URL과 공급자 메타데이터의 URL을 스크래퍼로 열어 실제 본문을 확인한 뒤 조합하는 방식을 제안했다. 조정자는 이를 현재 구조에 맞는 추천 방향으로 받아들였다. 아래 기존 독립 검색 제공자/Tavily/SearXNG 제안은 채택되지 않았다. 본 문서의 기존 §4/§5/§9는 그 전 제안의 기록이며, 그대로 구현 승인된 것으로 사용하지 않는다.

현재 제안 흐름은 기존 Vertex 검색·조사 → URL 후보 보존 → 스크래퍼 본문 확보·출처 ID/구간 저장 → 그 근거만 사용해 해석/작성 → 기존 섹션 결과와 진단 분리다. URL 발견 자체는 확인 완료가 아니다. Google chunks/supports는 있으면 후보·문장 연결에 활용하되 없으면 모델 evidence URL을 미확인 후보로 사용해 직접 수집을 시도한다. URL을 모델이 지어낼 수 있으므로 404/접속실패/다른경기·선수/시즌불일치를 구분하고, 실제 읽지 못한 내용을 확인된 사실로 표시하지 않는다.

스크래퍼는 추가 AI 호출 없는 Trafilatura를 일반 HTML 기사 기본 후보로, 브라우저 렌더링이 실제 필요한 경우에만 Crawl4AI를 보완 후보로 제안한다. 새 검색 서비스/유료 스크래핑 클라우드/벡터DB는 필요하지 않다. 저장 본문을 기준으로 source_id/passage_id를 서비스가 부여하고, 작성 단계는 실제 전달된 구간만 인용한다. 한 링크 실패 시 다른 자료와 API를 유지한다. 독자 화면에는 수집 실패 메시지를 넣지 않고 관리자에게 남긴다.

이 방식은 기존 모듈 결과를 그대로 '확인된 조사 결과'라고 재사용하는 것이 아니라, URL 발견과 근거 확보와 작성의 실행 증거를 나누는 설계다. 우선 R4 섹션 하나를 완결 단위로 확인하는 범위를 제안한다. R4에서 검색·조사1회와 근거기반작성1회면 정상 모델2회이며, 이것을 R1~R4 전체에 단순 적용하면 4×2+S1=9회가 되어 기존 전체 모델상한8을 넘는다. 스크래핑은 모델 호출이 아니지만 네트워크/실행 예산에는 포함한다. 전체 확장 시 조사 합치기 또는 모델/자료 예산 조정 여부를 명시적으로 결정해야 하며, 앞선 정상5회유지 주장을 이 흐름에 그대로 붙이지 않는다.

아직 본 수정 접근의 세부설계/실험/호출상한 승인을 받지 않았고 제품 코드·설치·유료 호출은 하지 않았다. 이전 builder 검토는 독립 검색 제공자 초안을 대상으로 했으므로 본 흐름의 검토 완료를 뜻하지 않는다.

## 1. 의도와 이미 확정된 요구

Google 인용 메타데이터가 생략되어도 확보한 API·웹 자료를 활용해 경기 프리뷰를 만들고, 사용자가 섹션별 생성물과 채택 근거를 직접 확인할 수 있게 한다. 두 메타데이터의 강제 반환을 해결 목표로 삼지 않는다.

기존 LangGraph, Vertex AI 제품 모델, R1 경기력/R2 부상/R3 외부전망/R4 주목선수/S1 종합, ADMIN 접근, 섹션 워크플로우 버전 승인, DB 한글명 우선·미보유 시 같은 생성 응답의 AI 번역을 유지한다. 구현·독립 검토 모델은 별도 DeepSeek 세션만 허용한다.

사실 전제는 근거와 연결하지만 선수 선정·관전 포인트·예상 스코어 같은 AI 판단 자체가 외부 매체와 일치해야 하는 것은 아니다. 프리뷰 수준의 확인을 목표로 하며 부상 발생 경위 등의 완전한 규명을 완료 조건으로 확대하지 않는다. 독자 화면에 자료 누락·오류 진단을 넣지 않는다.

## 3. Approaches: 대안과 선택

| 대안 | 장점 | 한계 | 결론 |
|---|---|---|---|
| 요청 설정·프롬프트·제한 재시도 중심 | 적은 변경 | 공급자 생략 가능성이 남고 무의미한 유료 반복이 생김 | 주 해결책에서 제외 |
| 현 조사 유지 + 실패 시 evidence URL 본문 조회 | 빠른 보완 | 모델이 URL을 만든 뒤 확인하는 순서, 잘못 만든 URL과 뒤늦은 보정 문제 | 이행 시 참고, 최종 구조 아님 |

## 4. 검색 제공자 제안과 비용 경계

**최신 검토 상태:** 사용자는 비용을 이유로 Tavily 대신 오픈소스 대안을 요청했다. 아래 Tavily 제안은 미승인 보류이며 도입 결정이 아니다. 새 후보는 자가호스팅 SearXNG 검색 + Trafilatura 본문 추출, 필요한 경우 Crawl4AI 자가호스팅 보완이다. 후보 선택 후 본 절과 HTTP/본문 수집 예산을 함께 갱신한다. 설치·실사용·사이트별 품질은 아직 검증하지 않았다.

조정자 제안은 Tavily Search + Extract이다. Search에서 실제 결과 URL/제목/설명, Extract에서 선택 URL의 본문과 개별 실패를 받는다. Search의 자동 생성 answer는 사용하지 않고, 웹 원문/결과를 자료로 저장한다. Tavily Research/자율 다단계 조사 엔진은 사용하지 않는다.

선택 근거는 기존 모델 호출에 검색 의사결정을 숨기지 않고 URL과 본문 확보를 한 제공자로 연결할 수 있다는 점이다. 실제 축구 coverage·한국어 품질·접속 가능성은 이 설계에서 입증되지 않았다. 초기 검증에서 경기 한 건으로 확인한다. Brave Search는 날짜 필터/추가 스니펫을 주는 대안이지만 본문 추출 경로를 별도로 연결해야 한다. 둘을 동시에 구현하지 않는다.

Tavily는 새 외부 서비스이며 키와 별도 사용량이 필요하다. 이 문서 승인 시에도 계정 생성·구독·유료 호출을 자동 실행하지 않는다. 구현 계획은 기존 키의 존재를 값 노출 없이 확인하고, 없으면 연결 방법을 안내한다. 결제/구독은 명시적 사용자 지시가 있어야 한다. 새 검색 제공자를 승인하지 않으면 이 항목을 다시 정하고 구현 계획을 수정한다.

고정 사이트 목록에 가두지 않는다. 팀/선수/리그/시즌/기준일/조사 주제로 검색하며 공식 구단·리그·기사 등은 우선순위 신호이고 특정 도메인만 허용하는 완료 조건이 아니다.

## 5. 실행 순서와 모듈 경계

전체 그래프는 D0 → E0 자료 확보 → R1/R2/R3/R4 병렬 생성 → V0 → S1 → V1로 바꾼다. E0는 이번 run에서 활성화한 섹션들의 질의·검색·본문 수집·중복 제거·자료 묶음 저장을 소유하는 단일 단계다. 수집 HTTP는 E0 안에서 최대 2개씩 병렬 실행할 수 있지만, 자료 저장/분배 소유자는 하나이며 R 분기들이 공유 DB session이나 수집 캐시를 동시에 수정하지 않는다. E0가 준비한 섹션별 자료 묶음을 고정한 뒤 모델 생성 갈래를 연다. 느린 한 URL을 기다리며 먼저 준비된 섹션이 잠시 대기할 수 있는 대신, 수집 소유권과 예산·재개의 경계가 명확해진다. 개별 HTTP 기한과 실행 기한이 대기를 제한한다.

| 섹션 내부 단계 | 하는 일 | 제품 모델 호출 |
|---|---|---|
| 자료 준비 | D0 자료·DB 경기/이름/허용된 선수 자료와 E0의 섹션별 검색 질의를 준비 | 0 |
| 검색·선별·본문 확보 | 검색 결과를 받고 관련 URL만 본문 추출. 중복 URL은 실행 안에서 공유 | 0 |
| 근거 묶음 확정 | 출처 ID/원문/시각/관계/조회 상태를 저장하고 이번 생성 입력을 고정 | 0 |
| 섹션 생성 | 고정된 API·웹 자료에서 사실을 인용하고 판단·서술/번역 결과를 한 번에 생성 | R별 1 |
| 근거 연결·표현 | 참조와 인용을 대조, 미확인 사실·진단 분리, 본문 저장 | 0 |

쿼리는 코드/설정의 주제별 규칙과 현재 경기 자료로 만든다. 별도 LLM 쿼리 작성/출처 평가/문장 수리 호출은 기본 경로에 추가하지 않는다. 추가 모델 호출이 필요하면 본 설계의 변경 사항이며 기존 상한을 우회하지 않는다.

새 자료를 받은 뒤 R1~R4 생성에서는 google_search 도구를 기본으로 켜지 않는다. 독립 수집이 새로 정한 근거 경계다. 이미 보존된 공급자 grounding_metadata는 진단/비교 자료로 남기고, Google 외부 메타데이터 모양을 서비스가 가짜로 재구축하지 않는다.

단독 섹션 실행도 같은 E0 수집기를 사용하되 활성 섹션 목록을 하나로 제한한다. 전체 실행과 별도의 수집/검증 구현을 만들지 않는다. E0의 수집 규칙 버전은 해당 섹션 워크플로우 manifest에 포함되지만 E0 자체를 사용자가 따로 승인하는 단위로 만들지 않는다.

사용자 시험 단위는 여전히 경기 선택 → 섹션 전체 실행 → 본문과 근거 확인 → 조정·버전 승인이다. 검색 노드마다 별도 승인을 요구하지 않는다.

## 6. 자료 계약과 저장

검색/본문/API를 공통 근거 참조로 묶되 자료의 종류와 확인 수준을 보존한다. 기존 SourceSnapshot·artifact·EvidenceClaim을 재사용하고 필요한 필드만 버전 확장한다. 웹 검색엔진·벡터DB·임베딩·범용 문서 플랫폼을 새로 만들지 않는다.

| 자료 | 보존 내용 |
|---|---|
| 검색 요청/응답 | run/section/logical_call/attempt ID, provider, 질의, 시간, 실제 결과 URL·제목·설명, 검색 순위, 사용량 제공 여부, 원문 artifact |
| 웹 문서 | source_id, 요청 URL·최종 URL(제공될 때), 본문 수집 상태, 추출 원문 artifact·hash, collected_at, published_at(알 수 없으면 null), 조회에 사용한 언어/기준일, 문서 제공자 |
| 근거 구간 | source_id, passage_id, 원문 인용문, 문서 내 구간 식별(오프셋이 정확히 재현될 때만), 관련 팀/선수/시즌·대회와 그 확인 방식 |
| API 사실 | 기존 snapshot/항목 ID, 실제 필드 값, 제공자 갱신 시각·수집 시각, 경기/팀/선수 ID 공간 |
| 생성 입력 | 이번 생성에 실제 전달한 source/passage/snapshot ID 목록과 가림된 입력 원문/hash |

검색 스니펫과 추출 본문은 다르다. 스니펫만 보유한 자료는 discovery_only로 기록하고 다음 URL 선별/검색 질의의 단서로만 사용한다. 이 설계의 독자용 사실 또는 core_evidence_satisfied에는 계산하지 않고 web_attributed로 승격하지 않는다. 본문 추출이 실패해도 같은 실행의 다른 웹 근거와 API 사실은 유지한다. 검색 제공자의 요약 답변을 기사 원문으로 취급하지 않는다. 링크가 발견됐다는 이유로 전체 페이지를 읽었다고 표시하지 않는다.

웹 문서의 내용은 신뢰할 명령이 아니라 자료다. 자격증명/내부 URL은 검색 질의에 넣지 않으며 HTTP 경계의 허용 대상·리다이렉트 제한을 두고 로컬/내부 주소를 수집하지 않는다. 전체 웹 보안 감사나 범용 크롤러 구현으로 확대하지 않는다.

신규 테이블/인덱스가 필요하면 preview_dev에만 두고 명시적 마이그레이션을 사용한다. 기존 public 경기·계정·번역 자료는 읽기 전용이다. 기존 원문/본문/승인을 backfill 또는 덮어쓰기하지 않는다. 저장 기간은 기존 artifact/구조화 기록 정책을 따르며 비밀값은 근거에 복사하지 않는다.

### 6.1 실제 생성 입력의 양과 발췌 기준

섹션 하나에 웹 출처 최대 4개·passage 최대 16개·각 passage 최대 1,500 Unicode 문자·웹 인용문 총합 최대 16,000 Unicode 문자를 제안한다. 시스템 지시/경기/API 사실/표시명/웹 근거를 포함한 전체 입력은 32,000 Unicode 문자로 제한한다. 이는 문자 상한이며 토큰·가격 상한과 같다고 설명하지 않는다. 실제 토큰/사용량은 제공자가 반환한 값으로 별도 기록한다.

발췌는 질의의 팀/선수 원문·DB 별칭·주제 단어가 있는 문단과 바로 연결되는 문맥을 우선하고, 같은 구간은 합쳐 중복을 제거한다. 웹 본문에 명시된 수치/단위/시즌이 주변 문단에서 분리되지 않게 문단 경계를 유지한다. 남은 길이에 맞춘다고 문장을 중간에서 잘라 인용 가능 구간으로 등록하지 않는다. 이 과정에 추가 LLM 요약/재랭킹 호출은 없다.

고정 근거 묶음은 모델에 실제 전달된 passage/API 사실만 가리킨다. 저장한 문서 전체가 자동으로 모델 입력이 되는 것은 아니다. 입력에서 제외된 구간은 관리자에게 not_in_input_bundle/truncated_by_input_limit로 남기며, 모델이 그 구간을 인용해도 채택하지 않는다. 재개는 같은 입력 묶음 ID/hash를 재사용한다. 전체 문서는 원문 artifact에 별도로 보존하되 문서가 크다는 이유로 모델에 전부 전달하지 않는다.

## 7. 생성 출력과 검증의 의미

모델은 자료에 존재하는 source_id/passage_id 또는 API snapshot ID를 인용한다. URL 문자열을 모델에게 새로 만들어 출처로 등록하게 하지 않는다. 최종 독자 출처 URL은 서비스가 source_id에서 붙인다.

사실과 판단을 같은 필드에서 재분류하는 규칙만 두지 않고 구조적으로 구분한다. 각 사실은 원문 인용문·출처·주체·시점·수치/단위가 있으면 함께 내고, 선정/전망에는 그 사실의 ID를 근거로 연결할 수 있다. R4의 selected_player/selection_reason 두 표시 필드는 유지한다. 감독·선수·팀은 DB 한글명 우선/누락 AI 번역이며 번역과 원문 fact identity를 분리한다.

기계 검증은 다음을 확인한다.

1. 참조한 자료가 이 실행의 해당 생성 입력 묶음에 실제로 들어갔는가.
2. 인용문이 그 출처의 저장된 원문 구간에 실제로 있는가. 번역된 한국어 인용을 원문 그대로인 것처럼 비교하지 않는다.
3. 모델이 주장한 주체·시즌·대회·날짜·수치/단위가 인용된 구간과 명시적으로 모순되지 않는가. 다른 선수의 9골이나 과거 시즌 숫자를 현재 기록으로 사용하지 않는다.
4. API 사실은 실제 필드와 비교하고, 웹 자료는 인용문과 맥락을 함께 보존한다. API 문자열에서 같은 숫자를 찾는 기존 단독 규칙을 웹 사실의 검증기로 재사용하지 않는다.
5. 존재하는 인용문이라도 주장을 뒷받침하는지 모호하면 unverified다. 단순 문자열/숫자 존재만으로 사실 진실을 증명했다고 표시하지 않는다.

웹 근거의 확인 수준은 api_confirmed와 web_attributed를 구분한다. web_attributed는 실제 수집 문서와 원문 인용에 연결됐고 명시적 맥락 모순이 발견되지 않았다는 뜻이며 독립적인 진실 판정/전문 사실확인기관의 검증을 뜻하지 않는다. 본문에 쓰는 웹 사실은 출처를 연결해 해당 보도의 내용으로 설명할 수 있다. 모호한 함의는 자동으로 confirmed로 올리지 않는다. 이 프리뷰 수준의 채택 기준도 본 설계 승인 대상이다.

### 7.1 판정 소유자와 V0/S1 경계

R1~R4의 생성 뒤, 본문 조립 앞에서 하나의 공통 근거 판정기가 채택 수준/제외 사유를 소유한다. 단독 섹션 실행도 이 판정기를 거친다. 각 claim에는 확인 수준, 판정기 버전, 근거 묶음 ID/hash, 인용 passage/API 항목 ID, 필드별 판정 결과를 보존한다. 이 계약 확장이 V0·S1·저장·관리자 화면에 함께 전달되어야 한다.

V0는 승인된 판정 수준과 현재 입력 묶음/실행/경기/자료 버전의 참조 폐쇄, 누락·상충을 검사한다. 다른 근거 규칙으로 문장을 다시 심사하거나 기존 grounding URL 필수 규칙을 덧붙이지 않는다. 새 passage_id가 기존 URL/snapshot 전용 검증기에 들어가 다시 탈락하는 구 경로를 같은 작업에서 교체한다.

S1은 채택된 claim과 판단을 조합한다. 사실의 새 수치/선수/사건을 발명하거나 새 근거를 찾지 않는다. S1/V1은 최종 표현이 선택된 사실 필드의 범위를 넘는지 확인하지만, 사실 판정 자체를 별도 규칙으로 다시 실행하지 않는다. 선택된 사실에는 없는 새 사실이 최종 문장에 추가되면 그 추가 문장만 제외하고 진단하며 자동 모델 수리 호출을 하지 않는다.

### 7.2 구조화 사실의 필수 범위와 한글 표시

필수는 claim 종류, 출처/전달된 passage 참조, 원문 인용, 주어의 안정 ID 또는 유일하게 매칭된 원문 표기다. 수치·시즌·대회·사건 시점은 그 claim이 실제로 주장하는 경우에만 필수다. 예를 들어 현재 부상 상태를 설명하는데 발생 날짜가 없다고 전체 상태를 버리지 않는다. 반대로 시즌 9골이라고 주장하면서 어느 선수/시즌/대회인지 인용에서 특정할 수 없으면 그 시즌 기록만 unverified다. 없는 값을 추측해 채우지 않는다.

주어는 DB ID/검증된 별칭으로 연결하고 표시 한글명이 원문 철자와 다르다는 이유로 탈락시키지 않는다. 원문 인용은 원문 언어로 저장된 passage와 비교하며, 한국어 fact 표시는 그 claim의 구조화 필드에서 만든다. 숫자/날짜/단위의 값은 검증된 필드 범위만 사용하고 임의로 새 수치를 붙이지 않는다. 소속/역할/상태 등 비수치 사실은 제한된 축구 사실 관계 종류와 원문 구간의 명시적 주어·관계 연결을 기록한다. 관계를 결정적으로 대응시킬 수 없으면 unverified로 남기고 별도 AI 판정 루프를 만들지 않는다.

단순 수치 정규화는 9와 nine처럼 계획에서 명시적으로 지원하는 표현만 같은 값으로 보며, 지원하지 않는 형식을 억지로 일반화하지 않는다. 인용문 존재와 구조화 맥락의 일치가 web_attributed의 기준이고, 독립적 사실 진위 증명이라고 표시하지 않는다. 선정 이유는 채택 fact의 구조화 표현과 독립적인 AI 해석을 조합한다. 사실과 해석이 한 문장에 섞여 있더라도 미확인 사실 때문에 독립적인 선수 선정/전망을 일괄 제거하지 않는다.

검증 안 된 사실은 최종 독자 내용에서 제거한다. 분리 가능한 예측·선수 선정 이유는 유지하고, 그 사실에 종속된 전제는 단정하지 않는다. 독립적으로 남길 설명이 전혀 없으면 그 항목은 관리자 초안에만 남긴다. 모든 선정이 실패했는데 빈 이유를 만들어 완료 처리하지 않는다. 외부 전망의 발언 주체/매체는 사실이므로 출처 확인이 필요하다.

## 8. 수집 실패·시간·품질

메타데이터 누락은 독립 수집 경로의 실패 조건이 아니다. 결과 없음/본문 실패/403·404/429/시간 초과/관련 없음/날짜 불명/상충은 서로 다른 상태로 기록한다. URL HTTP 성공은 근거 채택 성공과 다르다.

API의 사용 가능한 사실은 웹 실패와 무관하게 사용한다. 부상 API 상태·사유를 원문대로 쓰고 빈 응답을 무부상으로 바꾸지 않는다. API에 없는 부상 발생 날짜·경기·원인은 모르면 단정하지 않는다.

한 문서/항목 실패는 나머지 자료를 버리지 않는다. 웹 전체 실패 시 API 근거와 독립 판단으로 해당 섹션의 수용 기준을 만족하는지 판정한다. 만족하지 못하면 draft/insufficient를 유지한다. 외부 전망·배당 등 선택 항목의 누락 때문에 사용 가능한 필수 내용을 일괄 버리지 않는다. 정상 공개 프리뷰는 기존 필수 섹션 승인/품질 게이트를 유지한다.

모델에 없는 자료를 채우라고 반복 요청하지 않는다. 수집 재시도는 같은 요청의 전송 실패/429에 한정하고 기존 전역 기한·예산 안에서 끝난다. 자료 부재를 네트워크 재시도 대상으로 세지 않는다.

웹 최근 정보는 실행의 as_of(수집 기준 시각)까지의 자료만 사용하고, 과거 맞대결/시즌 기록은 background로 구분한다. 최근 뉴스의 기본 범위는 as_of 기준 7일로 제안한다. 아직 킥오프가 7일 이상 남은 시험 경기에서 미래 기사만 허용하는 조건을 만들지 않는다. 기존 kickoff-7일 단독 필터를 이 기준으로 대체하는 것은 조정자 제안이며 이 문서 승인 대상이다. 게시 시각을 모르면 수집 시각과 혼동하지 않고 해당 자료를 최신 사건 확인으로 단정하지 않는다.

## 9. 호출·비용·병렬성 제안

| 항목 | 제안 상한 | 설명 |
|---|---|---|
| 모델 정상 호출 | 5 | R1/R2/R3/R4 각1 + S1 1 |
| 모델 실제 전송 | 8 | 재시도 포함, 기존 공유 예산 유지 |
| 모델 동시 | 2 | 기존 유지 |
| 비모델 외부 HTTP 전송 | 합계24 | API-Football/검색/추출/재시도를 모두 포함하는 기존 전역 API 상한 |
| 검색 전송 | 최대8 | 각 섹션 기본질의1, 자료부족시 다른 질의1까지. 실패 재시도도 이 수에 포함 |
| 추출 전송 | 최대4 | 각 섹션 최대1회 배치. 실행 안 URL중복 제거 |
| 추출 URL | 전체 최대16 | 섹션별 최대4개. 서비스 크레딧은 HTTP요청수와 별도 기록 |
| API-Football 전송 예약 | 최대12 | 현재 이 작업은 기존 저장 자료 사용. 미연결된 신규 수집을 구현 완료로 표현하지 않음 |
| 외부 HTTP 동시 | 2 | 같은 실행의 수집 공유 gate |
| 기한 | 전체1800초 | HTTP 개별30초, 모델 개별300초, 남은시간 우선 |

위 상한은 전부 전체 run의 합계다. 각 활성 섹션에는 검색 전송 최대2·추출 전송 최대1·URL최대4를 배분하며, 단독 섹션도 이 섹션 상한과 전역24 안에서 실행한다. E0가 먼저 각 섹션의 기본 검색/자료 확보 기회를 배분한 뒤 선택적 두 번째 검색을 수행해 한 섹션이 전체를 소모하지 않게 한다. HTTP 재시도는 각 하위 상한에도 포함한다.

이는 24에 8+4를 더하는 설계가 아니다. 기존 요청 분류의 API 예산을 모든 비모델 외부 요청에 공유하고 하위 상한이 전역 상한을 늘리지 않게 한다. 예산 부족 시 나머지 선택 수집을 중단하고 확보 자료를 평가한다. 요청/URL수/제공자 크레딧/모델 토큰을 다른 지표로 남기며 비용을 추측해 계산하지 않는다.

검색→추출의 외부 비용은 추가된다. 모델 호출 수가 같다고 전체 비용이 같다고 설명하지 않는다. 실제 비용 단가는 공식 가격과 계정 플랜을 연결할 때 확인한다. 이 설계 단계에서는 유료 서비스 요청을 하지 않는다.

## 10. 재개·실행 증거

E0가 모든 활성 섹션의 입력 자료 묶음을 모델 팬아웃 전에 고정한다. 동일 canonical URL의 원문은 run 내 한 번만 확보하고 관련 섹션마다 source/passage 참조를 배분한다. 과도한 URL 정규화로 서로 다른 문서를 합치지 않는다. 수집 상태/원문 저장은 E0가 소유하고 각 R 생성 갈래는 고정 묶음을 읽기만 한다. 병렬 writer가 같은 DB session을 공유하지 않으며 기존 job lease/fencing/단일 예산을 유지한다.

재개는 같은 실행의 고정 자료·성공 결과·남은 예산을 재사용한다. 새 시점의 자료 갱신을 원하면 새 후보 실행으로 만들고 기존 자료를 조용히 갈아 끼우지 않는다. HTTP 외부 전송 기록과 원문은 섹션 본문 처리 실패가 나도 함께 사라지지 않도록 실행 증거 저장 단위를 분리한다. 이전 R4 live 후처리 예외로 유료 응답이 롤백된 경험을 같은 설계에서 반복하지 않는다. unknown은 성공 또는 무료 재시도 가능으로 포장하지 않는다.

저장 응답의 무호출 재생, 자료 재수집, 모델 재호출, LangGraph 재개, 개발 데이터 undo를 구분한다. 생성 화면 조회는 새 외부 요청을 만들지 않는다.

## 11. 관리자 확인 화면

기존 섹션 본문을 먼저 보여주는 구조를 유지하고 진단을 펼치면 생성 입력에 실제 포함된 근거를 볼 수 있게 한다.

- 검색 질의 → 실제 결과 → 선택 URL → 본문 수집 상태 → 근거 구간 → 주장/선정 이유 연결.
- source_id별 제목·URL·수집 시각·게시 시각·원문 인용·출처 종류·확인 수준.
- 제외/미사용 사유는 metadata_missing, discovery_only, url_not_collected, retrieval_failed, passage_not_found, context_mismatch, not_in_input_bundle, truncated_by_input_limit, unverified처럼 구분해 표시한다. 공급자 메타데이터 부재를 무조건 근거 없음으로 쓰지 않는다.
- 전체 API 응답의 정렬 보기와 모델 JSON을 구분한 현재 기능을 유지한다. 신규 검색/추출 응답도 정확한 모듈/시도/원문 연결을 보존한다.
- 수집 성공률/자료 확보율과 생성 성공률/사실 채택률을 분리해 표시한다. Google metadata 유무는 진단 지표이며 새 생성 성공률의 단독 분모/조건이 아니다.

## 12. 버전·이행 순서

자료 묶음/근거 계약과 섹션 생성 입력이 바뀌므로 관련 섹션의 새 워크플로우/입력/프롬프트/검증 구현 버전을 만든다. 실제 manifest에 수집/자료 채택 규칙 버전도 결과 영향 축으로 포함한다. 매 실행의 source_id 목록 자체를 승인 버전으로 삼지 않는다. 옛 승인을 새 계약에 자동 승계하지 않는다.

기존 source/claim/read DTO는 필요한 부분만 확장하고, 새 생산자·소비자·S1·저장·검사 경로를 같은 단위에서 연결한다. 구버전 과거 결과 열람은 유지하되 기존 metadata 필수 검증과 새 검증을 새 실행에서 동시에 적용해 두 번 탈락시키지 않는다.

가장 작은 완결 단위는 R4 섹션의 자료 수집부터 본문·진단까지다. 그 경로를 저장/실행 확인한 뒤 R1/R2/R3/S1에 같은 공통 계약을 적용한다. 다른 섹션의 기존 사용을 임의 제거하지 않는다. 이후 구현 계획에서 서로 다른 파일 소유권/공통 통합 소유자를 정하며, 개발 워커가 Plans.md를 동시에 수정하지 않는다.

## 13. 수용 기준과 최소 검증

- 실제 grounding chunks/supports가 없는 기존22e1.. 원문을 입력으로 삼아도, 별도로 확보된 근거가 있을 때만 근거 연결 판정이 가능하다. 옛 raw를 수정하거나 없어졌던 인용 메타데이터를 만들어 붙이지 않는다.
- 확보 문서의 실제 인용/주체/시즌에 맞는 사실과 독립 판단은 결과에 남고, 잘못된 출처 ID·다른 선수의 수치·인용 없는 사실은 이유와 함께 제외된다.
- 한 URL 실패가 나머지 근거/결과를 지우지 않는다. 자료가 전혀 없는 경우 초안 상태를 정상 완료로 위장하지 않는다.
- 검색·추출·모델의 실제전송/시도/사용량과 저장 원문이 정확히 연결되고, 후처리 실패가 이미 받은 원문을 롤백해 없애지 않는다.
- 원문/과거본문/승인은 불변이다. DB 한글명 우선/AI 번역 구분, 선정 선수·이유 분리, 독자 진단 미노출이 유지된다.
- 직접 관측 요구의 대표 오프라인 검사와 영향 경로만 실행한다. 전수 웹 크롤링·모든 언어/브라우저/실패 조합이나 문체평가 스위트는 만들지 않는다.
- 외부 실연동은 사용자에게 정확히 알린 비용/호출 상한으로 R4 경기1건을 확인한다. 설계 승인만으로 유료 실험을 자동 시작하지 않는다. 실제 수집 근거와 본문을 사용자가 보고 섹션 버전을 승인한다.

## 14. 비목표

Google 두 필드 반환 강제, 메타데이터가 올 때까지 무한 재시도, 모델/엔진 교체, 새 ADK 경로, 범용 크롤러/벡터DB/검증 플랫폼, 축구 통계/기사의 전수 사실확인, 부족한 자료의 AI 창작, 외부 URL 존재만으로 검증 통과, 기존 계정/경기 데이터 변경, 홈페이지 자동수집/배포를 이번 작업에 포함하지 않는다.

## 15. 남은 승인과 구현 담당자 판단

사용자가 선택한 것은 자료 우선 접근이다. Tavily 1차 제공자 선택·별도 검색 비용, 제안한 웹 자료 채택 수준과 뉴스 기준일, 수집 상한/기존 예산 재배분은 이 문서의 제안이며 아직 사용자 승인으로 기록하지 않는다.

본문 추출 라이브러리/HTTP SDK 선택, DTO의 내부 필드 이름, 기존 테이블 재사용 vs 개발 스키마 최소 확장, 병렬 파일 배정 등은 이 제약 안에서 구현 계획 작성자가 정한다. 새 기술 선택이 계정 비용/완료 조건을 바꾸면 사용자에게 명시한다.

- [LangChain 자료 우선 생성 설명](https://docs.langchain.com/oss/python/deepagents/retrieval): 검색 후 생성하는 구조 참고. 벡터DB가 본 기능에 필수라는 뜻 아님.
- [LangGraph retrieval 예제](https://docs.langchain.com/oss/python/langgraph/agentic-rag): 문서/출처를 모델 앞단에 두는 그래프 참고, 예제 전체 패키지/벡터경로 채택 아님.

- [Brave Search API](https://api-dashboard.search.brave.com/app/documentation/web-search): 대체 검색 제공자 비교.
- [Google URL context](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/url-context): URL별 수집상태 확인이 가능한 대안, 새 핵심 의존성으로 채택하지 않음.
