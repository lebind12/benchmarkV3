# Features — 운영 에이전트의 기능 요구사항

이 디렉토리는 **운영 에이전트가 사용자와 정한 기능/페이지 요구사항**의 정본 위치다. 새 작업은 `docs/spec/agentic-workflow.md`를 따른다.

전체 개발(FULL)에서 한 파일 = 한 feature다. 개발 전 운영자가 QUICK / FULL 선택을 확인하며, 빠른 수정(QUICK)에는 새 기능 문서를 만들 필요가 없다. 운영 에이전트는 이 파일과 서비스 기획을 바탕으로 개발 브리프와 독립 테스트 목표를 분리한다. 기존 spec / devplan / testplan은 필요한 상세 근거로 재사용한다.

상위 워크플로 문서: `@docs/spec/agentic-workflow.md`

## 파일 이름 규약

```
<feature_id>.md
```

`feature_id` 는 kebab-case, 페이지/기능을 식별할 수 있는 짧은 슬러그.
예: `main-fixtures-list`, `team-detail-squad`, `broadcast-livescore`.

## 템플릿

새 feature 작성 시 아래를 복사해서 채운다.

```markdown
---
feature_id: <slug>
title: <한 줄 제목>
created: YYYY-MM-DD
priority: MVP            # MVP | post-MVP
status: requirements-only
---

## 1. 개요
한두 문장으로 이 기능이 무엇이고 왜 만드는지.

## 2. 사용자
- 주 role: USER | STREAMER | ADMIN | public
- 부가 role: (있다면)

## 3. 사용자 흐름
- 사용자는 ... 화면에 진입한다
- ... 정보를 본다
- ... 동작을 한다
- 결과로 ... 한다

## 4. 페이지 / URL 후보
- 페이지 이름: <이름>
- URL 제안: `/path/...`
- 방송용 페이지 여부: yes | no

## 5. 표시 데이터 (개념)
- A: ... (데이터 소스를 아는 경우 명시 — 모르면 비워둠)
- B: ...

## 6. 인터랙션
- 클릭/입력/정렬/필터/페이지네이션 등

## 7. 비기능 요구
- 데이터 신선도: 6h / 실시간 / N/A
- 접근성: 키보드, 색 대비, 스크린리더 라벨
- 성능: 초기 렌더 임계치, 번들 회귀 한도
- 반응형: 데스크탑 / 모바일 포함 여부

## 8. 디자인 참고
- 시안 경로 (있다면)
- 색/타이포 제약
- 방송용 페이지인 경우: 크로마키 `#00B140` 배경, 1920×1080 송출 기준

## 9. MVP 여부 / 우선순위
- MVP 포함: yes / no
- 우선순위 (1=최우선): 1~10

## 10. FE 팀이 결정해도 되는 것
- 컴포넌트 분해
- Pinia store 모양
- 빈 상태 / 로딩 / 에러 표현
- 페이지네이션 여부

## 11. FE 팀이 결정해서는 안 되는 것 (메인 확인 필요)
- URL 규칙 변경
- 방송용 페이지 여부 전환
- 인증 요구 변경
- 새 외부 데이터 의존성 추가

## 12. 미확정 / 메모
- ...
```

## 작성 규칙

1. **frontmatter** 는 반드시 채운다 (도구가 파싱).
2. 기존 `requirements-only` / `in-fe-pipeline` 등 frontmatter 상태는 과거 문서와의 호환을 위해 보존한다. 새 FULL 작업의 진행 상태는 work-flow가 정본이며, 작업에 연결한 계획·브리프를 변경해야 하면 새 버전과 새 작업으로 연결한다.
3. **§10/§11 권한 경계는 빈 항목 금지** — 적어도 1줄씩.
4. **데이터 소스를 모르면 §5 항목을 비워두고** "FE 팀이 mock 으로 추론" 메모.
5. **시안 이미지** 는 `designs/` 디렉토리 별도 관리. 본 markdown 은 경로만 참조.

## 현재 개발 흐름

1. 운영자가 사용자에게 QUICK / FULL을 한 번 확인한다. 이미 선택한 작업의 하위 작업에는 선택을 재사용한다.
2. FULL이면 서비스 계획과 기능 요구사항을 확정하고, 개발 브리프·독립 테스트 목표와 소유 파일을 지정한다.
3. `developer`가 프론트 mock → endpoint 계약 → 백엔드 구현 → 통합 순서를 따르고, 별도 `behavior-tester`가 운영자가 정한 동작을 검증한다.
4. 운영자가 코드·diff·실행 증거를 검토해 수정 또는 머지를 결정한다. 자세한 상태·보고 형식은 `docs/spec/agentic-workflow.md`를 따른다.

QUICK은 같은 문서의 빠른 수정 절차를 따른다. 이전 `fe-planner`와 `FE_DONE_AWAITING_BE` 절차는 역사 자료이며 새 작업을 트리거하지 않는다.
