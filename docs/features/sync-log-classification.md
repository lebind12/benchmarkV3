# 수집 로그 원문 분류 — 2026-10-25

## 실제 조사

기존 WorkerSyncLog 최근 30개와 ManagementRun 최근 1개에서 보관 로그 8,200줄을 읽기 전용 분석했다. 원본/실행 상태를 변경하지 않는다. 주요 형식: 경기 상세 처리 2,544, 선수/라인업/통계/이벤트 응답 완료 각각 937/928/928/927, 선수 페이지 처리 843 및 페이지 응답 완료 842. 과거 시즌 접근 제한 failed 메시지 32개, 중복 락으로 실행 건너뜀 20개가 포함됐다. 과거 접근 제한 응답은 현재 요금제를 판정한 결과가 아니다.

## FE 흐름·응답 요구

- 실행 상세의 정상 진행 로그도 단계·대상·경기 ID·페이지·기록 수가 보이는 한국어로 표시한다. 원문은 펼쳐 확인한다.
- 보관 로그의 단계별 분류/건수와 필터: 실행 제어, 수집 준비, 카탈로그, 팀, 경기 목록, 순위, 선수 기록, 경기 이벤트/라인업/경기 통계/경기 선수 기록, 오류/미분류.
- 실패는 명시적인 실패 형식 및 원인 근거를 조합해 요금제·시즌 접근 제한/API 인증·호출 제한·응답 지연·DB 오류 등으로 분류한다. 숫자 429나 timeout 단어만으로 임의 문장을 오류로 확정하지 않는다. 기존 explicit info 진행 요약은 오류에 중복 합산하지 않는다.
- GET /runs/{id} 로그에 optional analysis `{code,title,action,category,category_label,level,stage,target,classified}` 추가. 기존 원문/code/level 보존. 서버가 분류 결과를 제공하며 FE는 그것을 우선한다.
- 기존 실행 목록에도 보관 로그 기반 오류 통계를 제공한다. log_statistics_scope=retained인 경우 '보관 로그 기준'으로 안내한다. 신규 실행의 전체 누적 오류 카운터를 보관 꼬리로 덮어쓰지 않는다. 대상별 저장 수는 복원하지 않는다.
- 미분류는 남기되 실제 인식 가능한 로그를 일괄 '기존 처리 기록'으로 내리지 않는다. 조회 시 분석만 수행하고 기존 DB 원문/상태/실행량을 수정하지 않는다. 보관 정책·호출 정책 변경/배포/재시작 없음(별도 로컬 fixture 서버 제외).

## 구현 순서

FE 계약·분류 UI/목업 → 원문 기반 서버 분류·기존 이력 집계 → 실제 API 연결 → 패턴/부정 사례/통합/브라우저 및 페이지 이탈 복원 회귀 확인. 실제 데이터 쓰기·유료 AI/API 호출 없음.

## 구현·검증

- `sync_log_analysis.py`가 실제 관측된 원문 형식을 한국어 제목/단계/대상/페이지·경기 ID로 변환한다. 기본 진행 상태는 info이며 명시적 실패 문맥과 원인 근거가 있는 경우만 오류로 분류한다. 기존 explicit info 요약은 중복 오류로 세지 않는다. 정상 조회 완료와 상세 적재 처리를 구분한다.
- 실제 원본 재조회 시점의 보관 로그 **8,806줄 중 8,806줄**을 인식했다(기존 30개 + 현재 1개; 수집 진행/보관 시점에 따라 표본 수는 변동). 이 표본의 커버리지이며 미래의 모든 형식을 보장하지 않는다. 기존 API 시즌 접근 제한은 당시 응답 근거이고 현재 계정 요금제를 추측하지 않는다.
- 원문/기존 실행 상태/저장 행 수는 변경하지 않는다. 기존 실행 목록/상세의 통계는 동일한 보관 로그를 읽어 계산하고 목록에는 원문 대신 통계만 반환한다(최근 7일/최대100개, 기존 각 실행의 로그 보관 상한 유지). 원문 전체를 FE 목록으로 보내지 않는다. 현재 실행의 전체 누적 카운터를 보관 꼬리로 덮어쓰지 않는다.
- FE에 보관 로그의 단계별 분류 건수/필터를 추가했다. 상세의 한국어 설명·리그/시즌·경기/페이지 정보를 기본 표시하고 원문은 별도로 펼친다. 원인별 오류 통계와 단계별 건수는 다른 기준임을 안내한다. 미분류 수는 별도 집계한다.
- 페이지 이탈 확인 과정에서 실행 탭에 돌아온 진행 작업의 ID가 URL에 유지되지 않아 완료 시 상세가 사라지는 부분을 보완했다. 명시적으로 열어 둔 과거 작업은 덮어쓰지 않는다. 뉴스 페이지로 이동→관리 실행 복귀→서버 작업 성공→이력 조회를 실제 API로 검증한다. 새로고침/취소·재접속 기존 회귀도 유지한다.
- Python 분류 unit **37개**, 격리 PostgreSQL 관리 integration **18개**, 관련 FE unit **39개**, 목업 E2E **18개**, 실제 Vue→FastAPI→전용 PostgreSQL E2E **9개**, TypeScript/Vite build·변경 Python Ruff·diff 공백 점검 통과. 외부 API/Upstash는 고정 테스트 fixture로 구분한다.
- 검증 화면: `out/management-live/log-classification.png`. 기존 로컬 `/admin?tab=history`에서 적용된다. DB migration/운영 설정/배포 없음. 기존 5173/8000 개발 서버를 재시작하지 않았고 별도 8016 테스트 서버만 변경된 fixture로 실행했다.

## 종류별 로그 섹션 후속 — 2026-10-25

사용자가 긴 전체 목록 대신 종류별로 로그가 쌓이는 접기/펼치기 섹션을 요청했다. 원문을 한 덩어리로 묶는 대안 대신 현재 종류별 섹션 방식을 유지하라는 최종 지시를 따랐다.

- 실제 로그가 있는 종류만 생성하며 0건 섹션은 표시하지 않는다. 기본은 모두 접힘이며, 펼친 섹션 안에서 시간순 로그와 기존 개별 한국어 설명/원문 보기를 제공한다.
- 같은 작업의 polling 갱신 시 열린 상태를 유지한다. 같은 종류는 건수와 내부 목록이 증가하며 새 종류는 접힌 상태로 추가된다. 보관 범위에서 빠진 종류는 섹션도 제거된다. 다른 작업을 열면 접힘/필터를 초기화한다.
- 오류/경고는 해당 종류 헤더에 건수·색상으로 표시한다. 기존 원인 통계/수준 필터를 유지하며 원인이나 실패·경고를 선택하면 맞는 비어 있지 않은 섹션만 보여주고 펼친다. 전체 접기로 긴 화면을 다시 줄일 수 있다. 펼친 로그 영역도 높이를 제한해 내부에서 스크롤한다.
- 접힌 목록은 DOM에 생성하지 않는다. 이 후속은 FE와 TS 테스트·문서만 변경했으며 Python/DB/API 계약을 수정하거나 원본 백엔드를 재시작하지 않았다.
- 관련 FE unit 44개(신규 섹션 동작 5개 포함), 목업 E2E 18개, 기존 실제 API E2E 9개 및 TypeScript/Vite build 통과. 390px 화면·0건 숨김·폴링 상태 유지·새 종류 추가/제거·시간순·오류 필터·개별 원문을 확인했다. 화면: `out/management-mock/grouped-logs-mobile.png`.
