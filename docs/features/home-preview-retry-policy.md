## 지금 보완한 것

분석 adapter는 항목 근거와 부모 인덱스에 쓰인 ID가 입력 sources에 실제 등록되어 있는지 확인한 뒤, 부모 인덱스에 빠진 실제 ID만 합집합으로 보완한다. 본문/수치/선수/사실은 고치지 않는다. 미등록 ID는 실패시킨다. 프롬프트에도 합집합을 명시했다. 새 생성 버전 prompt10. 관련 단위10/격리 저장 통합20 PASS. 자동 재생성은 켜지 않았다.

## 권장 재시도 규칙

1. **전체 재생성 대신 실패 단계만 재개.** 수집→원문 검색→분석→선택 원인 단계별 입력 해시·출처·시각·결과·실패를 비공개 checkpoint로 저장한다. 유효한 API/검색/분석 결과는 재사용한다. 현재 실패 시 checkpoint가 남지 않는 부분과 단계 재개는 추가 구현이 필요하다.
2. **일시 오류만 최대1회.** 연결/응답 timeout, HTTP408/429/500/502/503/504가 대상이다. provider Retry-After가 있으면 따르고, 없으면 10초+0~5초 jitter 후 재시도한다. 지연이 실행 예산이나 킥오프 경계를 넘으면 다음 슬롯으로 이월한다. 401/403/404/그 밖의400은 설정/요청 수정 전 자동 반복하지 않는다. 이전 맨유 오류는 코드가 없으므로 자동 재시도 가능 오류로 확정하지 않는다.
3. **검증 실패는 자동 재호출하지 않음.** 잘못된 경기/선수·미등록 근거·창작 수치·시점 위반·잘린 JSON/차단은 원인을 수정한다. 위 부모 인덱스처럼 등록된 참조만 기계적으로 보완 가능한 경우는 추가 호출0회다. 수정 후 명시적 단계 재시험도 아래 예산을 소비한다.
4. **선택 검색은 부분 성공을 허용.** 부상 원인 실패 때문에 정상 요약/선수/배당을 폐기하지 않는다. 검증된 원인이 없으면 미확인으로 남긴다. 매체3곳 미달/원문 날짜 미확인/인용 불일치는 데이터 부족이지 통신 오류가 아니므로 개수를 맞추기 위한 자동 반복 검색을 하지 않는다.
5. **추가 AI 예산은 슬롯당 합계1회.** 각 단계1회가 아니라 모든 단계가 공유한다. 기본3회+추가1회=경기당 슬롯 최대4회, 4슬롯 최대16회. timeout/실패/수동 단계 재시도도 포함하고 슬롯·카운터를 초기화하지 않는다. API-Football 내부 재시도는 별도 기존 client 정책이며 실제 호출 횟수는 계속 기록한다. 이 상한은 현재 ‘전체 실행 명시적 재시도1회’보다 좁게 제한하는 변경안이다.
6. **시간·소유권 재검사.** 슬롯 실행 총300초 안에서 대기와 재시도 응답/검증 시간을 확보할 수 있을 때만 재시도한다. fixture identity/NS/활성 target/24시간 창/킥오프/worker owner를 다시 확인한다. 중복 실행을 막고 실패 시 이전 유효 publication을 유지한다. 성공했던 독립 단계 결과와 원래 시각은 보존한다.

## 구현 전 필요한 검증

- stage, HTTP status, 허용된 provider error code, finishReason, elapsed_ms, Retry-After, retryability, request 수를 기록한다. 인증정보/헤더/원문 오류 body/프로젝트 URL은 저장·노출하지 않는다. 지금처럼 HTTPStatusError만 남는 진단 공백을 먼저 막는다.
- 단계 checkpoint 저장·무효화/재개, 공통 추가1회 예산, 300초/킥오프 경계, 재기동/owner 변경, retry-after 초과, timeout 불확실 완료와 누적 비용을 고정 응답 테스트로 검증한다.
- 단계별 부분 성공과 검증 거절을 구분하고 public GET에는 내부 오류를 노출하지 않는다.
- 구현/테스트 이후 요청한 미완료2경기를 단계 재시험하고 4개 실제 공개 저장본을 브라우저에서 확인한다. 현재 상태를 4개 신규 생성 성공으로 표현하지 않는다.

## 사용자 후속 확정과 구현 — 2026-10-25

사용자가 시간 제한 확대·재시도 구현·4경기 전체 재시험을 요청했다. 이전 정책안의 공유 추가1회/300초 및 중간 구현4회/900초 설명을 아래가 대체한다.

- 원인 검색 응답180초, 전망/분석90초, 연결15초. 메인 전용 HOME_PREVIEW_CAUSE_TIMEOUT_SECONDS/HOME_PREVIEW_REQUEST_TIMEOUT_SECONDS로 조정한다. 실행/owner lease는1200초다. 타 AX/방송 provider는 변경하지 않았다.
- timeout·408/429/500/502/503/504만 **단계별 최대1회** 재시도한다. 모델 요청은 단계별 최대2회/슬롯 전체 최대6회. 정상 기본3회, 최악4슬롯24회. 실패/timeout/수동 단계 재개도 같은 누적 카운터와 단계 상한을 사용한다. 실제로 한 경기의 검색 timeout과 분석429가 이어져 공유1회 정책으로는 복구하지 못한 것이 변경 근거다.
- Retry-After 우선. 없으면429는30~35초, 기타 일시 오류10~15초 jitter. 서버 대기가60초보다 길거나 남은 실행/킥오프 예산으로 요청을 완료할 수 없으면 즉시 반복하지 않는다. 400/401/403/404·안전 차단·불완전 출력·근거 검증 실패는 자동 반복하지 않는다.
- HTTP 요청 직전 카운터·stage·시각·timeout을 DB에 기록하고 이후 허용된 HTTP/provider code·응답 시간·종료 이유·재시도 지연을 기록한다. 오류 본문/인증/헤더/프로젝트 URL은 저장하지 않는다. fixture identity/NS/활성 target/owner/킥오프를 요청·재시도 전에 재검사한다.
- 기존 불변 HomePreviewSnapshot에 evidence/analysis/causes checkpoint를 비공개 저장하고 attempt에는 ID를 기록한다. DB 스키마 변경은 없다. 같은 attempt/slot의 재개는 identity/model/prompt/attempt/input hash·6시간 범위를 검증하고 성공한 API/검색/분석 단계를 재호출하지 않는다. 원인만 실패한 부분 성공도 남은 예산에서 명시적으로 재개할 수 있고 과거 version을 수정하지 않는다.
- 원인 discovery에도 실제 responseSchema로 코드 enum/필드/nullable 값을 제한한다. 등록된 HTTPS 원문 기사 URL은 Google redirect와 별개로 원문 fetch·DNS/redirect 안전 검사·선수/구단/날짜/인용 검증 후에만 채택한다. 홈페이지만 반환한 후보/미등록 호스트는 거절한다. API와 충돌하거나 검증되지 않은 원인·발생일은 창작하지 않는다.
- 일반 GET은 DB만 읽고 자동 생성 OFF·6시간/최대4슬롯·진행 중 신규 생성 금지를 유지한다. 실제4경기 결과/검증 정본은 `home-preview-generation-verification.md`다. 전체 생성 성공과 모든 외부 사실 확보를 구분한다.
