# 구현 전 요구사항 작성

이 문서는 계획의 분량을 늘리기 위한 절차가 아니다. 요청을 구현 가능한 동작으로 바꾸고, 요청받은 일을 빠뜨리지 않도록 [계약 JSON](requirement-contract.json)을 작성한다. 원문은 workspace 밖에 그대로 보존한다.

1. **문제와 사용자 흐름:** 누가 어떤 상황에서 무엇을 하며 결과를 어떻게 확인하는가? 추상적 형용사만 있으면 실제 예시와 관찰 기준으로 구체화한다.
2. **원문 → 요구사항:** 기능·제약·명시적 선택을 각각 ID로 연결한다. 여러 요구가 담긴 문장을 한 요약으로 줄여 일부를 없애지 않는다. 기존 정책은 constraints에 함께 연결한다.
3. **수용 시나리오:** 정상·실패·경계/권한·저장/재조회 중 해당하는 것을 구체화한다. “컴포넌트 있음”, “모델이 완료라고 말함”은 동작의 증거가 아니다.
4. **미정 사항:** 조회 가능한 코드·문서부터 확인한다. 결과에 큰 영향을 주는 미정 정책은 blocking 질문, 제안은 가정으로 표시한다. 승인 없는 중요 가정을 확정값으로 만들지 않는다. 이미 받은 답은 재질문하지 않는다.
5. **범위:** owned_paths는 실제 담당 경로, out_of_scope는 사용자가 제외했거나 요청 밖인 범위다. 필수 기능을 임의로 “MVP 이후”로 이동하지 않는다. 추가 아이디어도 자동 필수화하지 않는다.
6. **검증 계획:** FULL은 각 필수 요구에 실제 로컬 명령을 연결한다. 기존 테스트/설정 중 보호할 파일은 verification_files로 동결한다. 신규 테스트만으로 모든 요구가 충족됐다고 자기 인증하지 않는다. 검증 수단이 없으면 해결할 미정 사항으로 남긴다.

QUICK은 같은 구조를 짧게 작성한다. 낮은 영향 문구·스타일에 의미 없는 테스트를 추가하지 않는다. verification_commands가 빈 경우에도 독립 검토자가 실제 파일/변경 내용을 읽어 수용 시나리오별 근거를 내야 한다.

예를 들어 “번역을 편집할 수 있게 해줘”만으로 바로 CRUD를 구현하지 않는다. 기존 정책을 읽어 편집 대상, 편집 권한, 사람이 고친 값의 보호, 저장 충돌, 수정 이력, 전체 서비스 적용 범위를 구체화한다. 기존 정책에 답이 있는 사항은 재질문하지 않고, 없는 중요한 선택만 묻는다.

source_coverage의 인용은 원문에 실제로 존재해야 한다. 모든 ID가 연결됐다는 구조 검사만으로 의미적 완전성이 증명되지는 않는다. 별도 명세 검토자가 **원문 전체**를 읽고 요구 누락·필수 항목의 선택화·테스트 부실을 확인한다.
