# 하네스 재구성: 기술 선택 근거

## 목적과 근거 범위

이 문서는 운영자 주도 작업 흐름의 기록 도구 선택을 설명하며, 정책 정본은 [운영 흐름 명세](../spec/agentic-workflow.md)다.
아래 현황은 저장소 파일에서 확인한 내용이다.
대안별 비용과 장점 평가는 정성적 판단이며 벤치마크 결과가 아니다.
외부 워크플로 제품의 최신 기능·가격·호환성은 조사하지 않았다.

## 세 가지 대안

| 대안 | 확인된 장점과 맞는 점 | 비용·한계와 판단 |
|---|---|---|
| 기존 Node 스크립트 재사용 | `scripts/harness-flow.mjs`는 endpoint/feature 흐름을 처리한다. | 기존 역할·상태 전이에 새 운영자 주도 흐름을 얹으면 과거 의미와 새 책임을 함께 유지해야 한다. |
| 새 Python + jsonschema CLI | `pyproject.toml`은 Python 3.11 이상과 `jsonschema>=4.23`을 선언한다. | 별도 CLI 코드와 스키마의 유지보수, Python 실행 환경은 필요하다. |
| 외부 워크플로 엔진 | 장기 실행·분산 조정이 필요해질 때 검토할 수 있다. | 제품 선정, 별도 운영 인프라, 비용 및 마이그레이션 검토가 추가된다. |

### 기존 Node 흐름

`scripts/feature-flow.sh`는 `scripts/harness-flow.mjs`를 호출한다.
Node 구현에는 endpoint와 feature 각각의 상태, 담당 역할, 전이 규칙이 정의돼 있다.
이 흐름은 기존 기록과 당시의 FE/BE 세부 생명주기를 재현하는 데 적합하다.
새 명세는 운영자가 브리프를 정하고 개발·독립 테스트를 분리하며 최종 병합을 판단한다.
따라서 옛 상태 기계를 그대로 새 작업의 정본으로 쓰면 책임 경계를 중복 표현하게 된다.
기존 Node 파일과 이전 상태 기록은 보존 가치가 있으므로 삭제나 강제 변환 대상으로 삼지 않는다.
새 Python 흐름과 병행하는 동안 과거 상태 파일은 조회용 이력으로 취급한다.

### 새 Python CLI

`pyproject.toml`의 런타임 의존성에 `jsonschema>=4.23`이 이미 선언돼 있다.
`scripts/work-flow.py`는 표준 라이브러리와 그 의존성을 사용한다.
`.codex/schemas/`의 JSON Schema로 브리프, 테스트 브리프, 보고서, 상태의 모양을 검사한다.
CLI는 `PLANNED`부터 `MERGED` 또는 `ESCALATED`까지 명시적 전이를 기록한다.
수정 후 재작업은 새 revision을 만들고 기존 제출·테스트·승인 참조를 제거한다.
제출 커밋, 테스트 보고서, 증거 파일, 검토 파일은 경로와 SHA-256으로 연결한다.
제출 및 병합 SHA는 로컬 Git에서 확인하고, 병합 대상에 제출 커밋이 조상인지 확인한다.
원자적 파일 저장과 단일 상태 디렉터리 잠금 구현도 코드에서 확인된다.
이런 검증은 JSON 형식 오류와 오래된 참조를 찾는 bookkeeping에 유용하다.
반면 새 구현은 추가 유지보수 대상이며 실제 사용 환경에서의 내구성은 별도 검증이 필요하다.
따라서 Python 선택은 현재 선언된 런타임에 맞춘 작은 로컬 도구라는 판단이다.

### 외부 엔진

외부 엔진은 실행 대기, 재시도, 분산 조정 같은 요구가 생길 때 후보가 될 수 있다.
현재 운영 명세는 현재 대화의 운영자가 에이전트를 생성하고 판단하는 모델이다.
저장소 자료는 외부 엔진 도입이 이 모델에 주는 구체적 이점을 입증하지 않는다.
도입 시 공급자·배포 방식·인증·비용·장애 대응을 별도 조사해야 한다.
그러므로 지금 외부 엔진을 고르는 것은 근거가 확인되지 않은 운영 복잡도를 더한다.

## 선택과 보장 범위

새 작업은 Python CLI와 `.codex/state/work-flow/`를 사용하고 기존 Node 기록을 보존한다.
이는 저장소 구성에 대한 선택이며 전 서비스 적용이나 성공적인 장기 운영을 뜻하지 않는다.
CLI는 에이전트를 자동 생성하지 않고, 인증·신원 확인 경계가 아니다.
`--by` 값은 명령 호출자가 제공하는 식별자 주장이다.
상태 파일의 이벤트 기록은 누가 실제로 도구를 실행했는지 독립적으로 증명하지 않는다.
파일 해시는 연결된 파일의 내용이 바뀌었는지 확인하지만 파일 내용의 진실성을 증명하지 않는다.
특히 해시는 테스트가 실제 실행되었음을 증명하지 않는다.
운영자는 원본 코드와 Git diff를 읽고 별도 인스턴스가 실제 수행한 테스트를 독립 확인해야 한다.
CLI는 자식 에이전트를 생성하거나, 검토 결정을 내리거나, Git 병합을 수행하지 않는다.
`merged` 기록은 실제 병합 이후에 운영자가 실행하며, 배포도 자동화하지 않는다.
작업 완료 가드는 기록된 상태가 `MERGED`인지 검사하는 CLI 명령이다.
이는 모든 완료 경로에 자동 연결된 훅이라는 뜻은 아니다.
동시 실행 규모나 원격 내구성 요구가 확인되면 잠금·저장 방식을 재평가한다.

## Codex 설정 근거와 적용

[공식 subagents 문서](https://learn.chatgpt.com/docs/agent-configuration/subagents)는 명시적 생성 시 모델 선택과 자식 설정을 설명한다.
[공식 설정 참조](https://learn.chatgpt.com/docs/config-file/config-reference)는 `service_tier = "fast"`가 priority 티어에 대응한다고 설명한다.
저장소의 `.codex/config.toml`은 루트 `service_tier = "fast"`로 설정돼 있다.
같은 파일은 기본 자식 모델 `gpt-6.1-sol`, 추론 수준 `medium`, 동시 자식 상한 3을 지정한다.
루트 대화 모델은 설정에서 덮어쓰지 않는다.
역할 파일은 모델 고정을 피하고, 작업에 따라 운영자가 생성 시 모델을 정한다.
개발·독립 테스트·복잡한 판단에는 Sol medium을 기본으로 삼는다.
범위가 명확한 기술 비교에는 Terra medium을 선택할 수 있다.
기존 자료의 단순 요약·서식화에는 Luna medium을 선택할 수 있다.
약한 근거나 중요한 구조 결정은 Sol로 격상한다.
역할 설정이 현재 대화에 즉시 반영되는지는 이 문서만으로 확인되지 않는다.
역할을 쓸 수 없으면 해당 역할 파일을 읽고 default/worker에 지침과 모델을 명시한다.
이 설정은 계획 및 저장소 상태의 설명이며 런타임 재로딩 보장은 아니다.
