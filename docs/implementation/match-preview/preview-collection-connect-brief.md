## 역할과 선행 수용

실제 DeepSeek 구현 작업이다. 확인된 실행기는 `dsh-tui`, 모델은 `deepseek-ai/deepseek-v4.1-flash-1017`, 사용자 설정 `max`를 유지한다. 모델/백엔드를 전환하거나 하위 워커를 만들지 않는다. GPT 조정자는 계획·사실 조사·수용, 별도 DeepSeek 세션은 독립 검토를 담당한다.

사용자는 과거2/미래2 실제 생성 시험을 통과 처리했고 2026-12-06 맨유–코번트리의 자료가 부족한 본문도 충분하다고 확인했다. 사진·한글 이름의 ID 연결은 수집 연결 뒤 구조화 단계다. 이 항목이나 매체 후속 관측을 지금 수정하지 않는다. 기존 홈 구현의 편집은 종료됐고 실제 표시 수용도 끝났다.

## 목표와 계약

현재 API 경기 자료를 갱신하는 수집이 성공·부분 실패·실패로 종료돼도 기존 DB에 남은 대상 경기로 프리뷰 생성을 시도한다. 명시적 사용자 취소에는 새 생성을 시작하지 않는다. 수집 상태를 프리뷰 성공/실패로 덮어쓰지 않고 별도 결과로 남긴다.

입력은 수집 실행 식별자·원래 종료 상태와 DB 경기 후보다. 결과는 원래 수집 상태를 보존한 채 경기별 생성/건너뜀/실패 이유와 생성된 실행 ID를 연결한다. 기존 관리자 결과 표시가 충분하면 UI를 추가하지 않는다. 본문이나 structured 내부 필드는 수집 경계에서 해석하지 않는다.

자동 후보는 현재 NS·0 < 남은 시간 <=6시간, 우선순위·킥오프·외부 경기 ID 순서, 기존 회차 한도를 유지한다. 성공한 리그에만 후보를 제한하지 않는다. 과거/먼 미래 생성 범위를 자동 수집에 확대하지 않는다.

실제 생성은 기존 `app/services/match_preview.py`의 `generate_match_preview()`를 `trigger=collection`, 시스템 호출로 사용한다. 관리자 ID 위장, 두 번째 생성 엔진, 새 AI 검증 게이트를 만들지 않는다. 기존 관리자와 같은 LangGraph·모델 전송/검색 구성과 모듈별 최대3회 재시도를 재사용한다.

프론트·공용 렌더·홈 문서 조회·본문 스키마·ID/사진 해석기·생성 프롬프트·기존 원문·승인 행·Plans.md·제품 모델 설정은 범위 밖이다. 이전 구현의 전체 삭제나 일반화도 하지 않는다.

## 이미 확인한 코드 출발점

- management_runs의 정상 종료 경로는 현재 전체 succeeded일 때만 `run_home_preview_after_sync()`를 호출한다. 상위 예외의 failed 경로도 별도로 있으므로 부분 실패 조건 하나만 바꾸고 완료하지 않는다. 명시 취소는 별도 `SyncCancelled`다.
- `run_home_preview_after_sync()`는 현재 `run_cycle(db.SessionLocal, execute=True)`를 호출하며, run_cycle은 옛 ProductionPreviewGenerator/process_fixture를 사용한다. collection 진입을 단일 생성 서비스로 옮기는 것이 이번 핵심이다. CLI·보조 호출부 영향은 현재 지원 경로만 확인한다.
- `generate_match_preview()`는 collection에서 actor_id=None을 받아 시스템 actor로 저장하고 기존 bundle pipeline을 호출한다. 자동 후보/회차 중복/승인 판정을 자체 완결했다고 가정하지 않는다.
- 기존 `home_preview_generation`은 경기/킥오프 직전 수집 slot으로 중복을 막는다. `PreviewPipelineRun`의 active dedup은 동시 실행용이므로 이미 끝난 같은 회차의 중복 억제까지 보장한다고 간주하지 않는다.
- `app/preview/pipeline.py`에 승인 판정 경로가 있고 `approvals.py`에 버전별 승인이 있다. 기존 승인 정책과 저장 증거를 보존한다. 관리자 시험 허용을 자동 공개 생성 승인으로 바꾸거나 버전 불일치를 자동 승인으로 우회하지 않는다. 승인된 실행 가능 버전이 없으면 분명한 건너뜀/실패 사유를 남기고 정상 승인 완료로 꾸미지 않는다. 현재 저장 승인 상태 확인을 위해 실제 DB를 탐색하지 말고 합성 검사와 코드 계약으로 확인한다.

## 수용 기준

1. 수집 succeeded/partial_failed/failed 뒤 DB 후보를 처리한다. 명시 취소는 후속 생성 미호출, DB 연결·경기 식별 불가 등 실제 실행 불가는 별도 사유로 남긴다. 기능 비활성 설정은 존중한다.
2. 후보 A가 예외/실패여도 B 처리를 계속한다. 손상된 세션을 다음 경기에서 재사용하지 않는다. DB 공통 장애를 정상 성공으로 표시하지 않는다. 프리뷰 실패는 원래 수집 상태·이미 저장된 자료를 덮어쓰지 않는다.
3. 관리자 저장본의 존재는 수집 새 생성을 막지 않는다. 자동 실행 중복은 기존 경기/회차 의미를 유지하며 완료·실패 이력도 고려한다. 실패 경기의 새 자동 재시도 정책은 추가하지 않는다. 생성 실행 내 기존 재시도는 유지한다.
4. 같은 생성 서비스와 실제 preview_dev 저장 경로를 사용하고 생성 실행 ID를 결과에 연결한다. 새 정상 저장본이 기존 홈 최신 선택 경로의 후보가 되는 것을 직접 연결 근거로 확인한다. 공개 조회/승인 기준을 느슨하게 만들지 않는다.
5. 사용자 승인 워크플로우 정책과 현재 자료 부족 처리 그대로다. 12월6일 사례의 최소 구성 수용을 새 자동 길이/출처 수 제한으로 바꾸지 않는다.

## 검증·제외 범위·종료

직접 명령: `.venv/bin/python -m pytest tests/unit/test_home_preview_collection.py -q`

대표 검사는 수집 실패+기존 DB로 서비스 호출, 한 경기 실패 뒤 다음 경기, 같은 자동 회차 중복 억제, 관리자 기존본 후 수집 새 실행, 취소 시 미호출이다. 승인 정책과 preview_dev 세션 배선은 이 연결 검사의 실제 변경 경로에서 확인한다. 생성기를 모의했으면 모델/실제 저장 성공이라고 표현하지 않는다. 새 검사의 이유와 실패 시 사용자가 겪는 결과를 짧게 설명한다. 테스트 개수 목표·전체 회귀·미지원 DB/플랫폼 행렬은 없다. 추가 명령이 필요하면 구체적 변경 영향과 최소 명령을 조정자에게 먼저 알린다.

이번에는 실제 DB·외부 API·모델 호출·운영 수집·마이그레이션 적용·서버 재시작·브라우저·배포·승인 POST·환경 비밀값 탐색을 하지 않는다. 새 프리뷰 쓰기는 명시적 preview_dev로 설계하고 기존 경기/계정 영역에 쓰는 경로를 새로 만들지 않는다. 기존 운영 수집 본래 쓰기와 이번 프리뷰 쓰기를 구분한다. 현재 원래 DB 연결의 권한이 제한됐다고 주장하지 않는다.

구현과 직접 검사가 충족되면 편집을 종료하고 보고서에 변경 파일·실행 명령/결과·실제 확인과 합성 검사의 구분·미해결 사항을 남긴다. 실패 명령을 성공으로 표시하지 않는다. 같은 원인 수정/검증을 두 차례 반복하면 범위를 넓히지 말고 최소 원인/해결 범위를 보고한다. 독립 검토는 조정자가 별도로 배정한다.

완료 시 이번 활성 Task/Dispatch로 `worker_done` 한 번을 보내고 `EDITING STOPPED`, 백그라운드 작업 수를 보고한다. 과거 settled/failed Dispatch나 새 probe를 사용하지 않는다. 이후 새 배정 전 추가 조사·테스트·편집을 시작하지 않는다.
