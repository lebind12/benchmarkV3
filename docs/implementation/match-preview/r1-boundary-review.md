## 1. 질문 1 — 미확인 과거 사건이 의견 문구로 통과하는가

### 1.1 결론: 좁은 형태로 **통과한다**

후보 실행 `7c0af3c0-4f55-4270-9266-be58c65d8f6b` v4
(`section_result` `18e03e19-1671-4600-a0e2-b386eb2a2bba`, 878자, 2026-11-10T15:38:17Z,
스탬프 `section_form@dff5ef9da8f20f8a`)에 다음 문장이 남아 있다.

> Rodrigo Muniz(Fulham)는 **최근 득점으로 자신감을 얻은 만큼** 이번 맨시티전에서도
> 풀럼의 최전방을 책임질 것으로 기대됩니다.

같은 항목의 원문은 `최근 뉴캐슬전에서 동점골을 터뜨렸으며, 경기당 평균 2.8회의 유효

가리키는 축약 전제(`최근 득점으로 자신감을 얻은 만큼`)가 **다른 문장에 남아** 미래
전망의 근거로 쓰인다. 미래 전망 자체는 정상 유지 대상이지만, **전망의 전제가 된 과거
사건은 이 실행의 자료로 추적되지 않는다.**

### 1.2 근거 3중 확인

1. **자료 범위.** 저장된 D0 사실은 `api:standings-13`, `api:standings-4` 두 건뿐이다
   (두 팀 순위·폼). 후보 R1 원문 `95f5e638-7f73-41df-a439-a88450d58630`의
   `groundingMetadata`가 비어 있고, `form._grounding_urls()==set()`로 **검색 출처 0건**임을
   확인했다. 즉 선수 득점·슈팅 지표를 뒷받침하는 입력이 이 실행에는 없다.
2. **필터 재현.** 저장 원문·저장 D0로 같은 함수를 그대로 호출하면
   `form._filter_judgment_text()`가 `2.8회`·동점골 문장은 **drop**, `최근 득점으로…`
   문장은 **keep**으로 돌려준다. `_clauses()`(`form.py:419`)의 판정 기준이
   (a) 숫자 `_NUMBER`, (b) 부상·결장류 `_EVENT_WORDS`, (c) **완료·과거 서술**
   `_PAST_EVENT`(`form.py:104`) 세 가지뿐이고, `최근 득점으로 자신감을 얻은`은 셋 다
   해당하지 않기 때문이다.
3. **본문 재현.** 저장 원문·저장 D0·저장 조립 경로로 다시 조립한 본문이 저장 v4와
   **글자 단위로 일치**했다(`True`). 즉 이 문장은 사후 변형물이 아니라 현재 코드가
   만든 결과다.

### 1.5 가장 작은 조치 (실행 패치 아님, 산문)

- 항목 안에서 **덜어낸 사실 문장에 의존하는 전제 절**을 같은 판정에서 함께 종속
  처리한다. 즉 "이 항목에서 제거된 사실이 전제로 쓰인 문장"은 전제만 들어낸 뒤
  순수 전망으로 남기거나, 종속 관계를 확인할 수 없으면 그 문장도 제외하고 사유를 남긴다.
- 대상은 **이미 지목된 세 문장뿐**이다. 판정 규칙을 동의어·정규식 목록으로 넓히거나
  범용 진실 판정기를 만드는 변경은 이 결함의 최소 해결이 아니다.
- 대표 확인은 숫자 없는 축약 과거 사건 1건이면 충분하다. 기존 대표 사례
  `test_unverified_statistic_not_smuggled_through_as_opinion`은 **숫자가 있는** 경우만
  고정하므로 이 형태를 잡지 못한다.

### 1.6 부수 실패 — 덜어낸 사실의 관리자 기록이 저장되지 않는다

- 재검증 경로 `sections.revalidate_section_from_stored_response`(`sections.py:701`)는
  `validated.diagnostics`를 **메모리에만** 두고 새 R1 결과 행을 저장하지 않는다.
  실측: 두 실행 모두 모듈별 `preview_results` 행이 1건뿐이고 R1 행은 옛 버전
  (`mp05-form-1` / `mp05-form-1-nomime-1`)이다. 즉 "무엇을 왜 덜어냈는지"가 실행 기록에
  남지 않는다.
- 게다가 섹션 결과 진단은 **글자 단위로 쪼개져 저장**된다. `sections.py:855–859`의
  `diagnostics=( "…" "…" f"…." )`에는 튜플을 만드는 마지막 쉼표가 없어 값이 `str`이 되고,
  `store.save_section_result`가 `[str(item) for item in diagnostics]`로 펼친다.
  DB 실측: v4·v5 `diagnostics = ["저","장","된"," ","원","문", …]` (문자 배열).
  같은 모양의 재조립 경로(`sections.py:690–694`)는 쉼표가 있어 정상 1건 문자열이다.
- 요구 위반: 설계 §5 "빠진 부분·충돌·보완 시도는 관리자 기록에 남긴다", §6.1의 검증
  탈락 기록. **현재 저장된 후보는 이 기록을 읽을 수 있는 형태로 갖고 있지 않다.**
- 최소 조치: 재검증에서 진단을 1건짜리 목록으로 넘기고, 재검증이 만든 R1 검증
  진단(덜어낸 문장 포함)을 실행 기록에 남긴다. 새 표·마이그레이션은 필요 없다.

## 2. 질문 2 — 결과 스탬프·승인이 같은 본문/버전을 가리키는가

### 2.1 통과한 부분

- **옛 이력 보존.** 기준 v1–v4, 후보 v1–v3은 `section_form@9f0d2e9bcb33c26d`를 그대로
  유지하고, 새 후보 v5·v4만 `@dff5ef9da8f20f8a`다. 일괄 backfill 없음, 승인 0건. DB에서
  직접 확인했다.
- **단일 원천.** `version_manifest.constituents_for_workflow`(`:80`)가 D0·R1·compose_body
  실제 상수를 쓰고, `runner.section_workflow_version`(`:217`)과
  `approvals._current_constituents`(`:198`)가 같은 함수를 읽는다. 현재 후보는
  `section_form@dff5ef9da8f20f8a`로 evidence와 일치한다.
- **옛 결과가 현재 후보를 덮지 않는다.** `_current_constituents`가 저장 결과 역산을
  중단했으므로, 옛 실행을 승인해도 현재 후보가 바뀌지 않는다. 이 부분은 45b442a의
  의도대로 동작한다.

### 2.2 실패 — 승인 기록이 검토한 본문의 버전이 아니다

`approve_section_version`(`approvals.py:408`)은 버전을 **섹션 결과 행의 스탬프**가 아니라
`_constituents_from_results(...)`(`approvals.py:135`)로 **저장된 모듈 결과 행**에서 다시
계산한다. 그런데 재검증은 모듈 결과 행을 새로 쓰지 않으므로, 그 행들은 여전히 옛
구현 버전이다.

실제 저장 행으로 계산한 값(읽기 전용, 함수 직접 호출):

| 대상 | 저장된 구성 | 승인 시 기록될 버전 |
|---|---|---|
| 기준 `6e59041a` v5 | D0 `mp05-stored-d0-1`, R1 `mp05-form-1`/`mp05-form-prompt-1`, compose `mp05-compose-1` | `section_form@bf3b6e2ba968e123` |
| 후보 `7c0af3c0` v4 | D0 `mp05-stored-d0-1`, R1 `mp05-form-1-nomime-1`/`mp05-form-prompt-1`, compose `mp05-compose-1` | `section_form@7a18bceabdf61629` |
| 현재 후보(manifest) | D0 `mp05-stored-d0-1`, R1 `mp05-form-2`/`mp05-form-prompt-2`, compose `mp05-compose-2` | `section_form@dff5ef9da8f20f8a` |

즉 사용자가 화면에서 보고 승인하는 v4/v5 본문은 **새 검증·조립 코드**
(`mp05-form-2`, `mp05-compose-2`)가 만든 것인데, 승인 기록에는 **옛 구현 버전**이 남는다.
AGENTS.md가 요구하는 "결과에 영향을 주는 구성 모듈/프롬프트/구현/출력 계약 버전 집합"이
**검토 대상 결과와 다른 집합**이 된다. 45b442a 보고의 "실행과 승인 후보가 같은 원천을
쓴다"는 이 경로에서 성립하지 않는다.

사용자에게 보이는 결과도 어긋난다. 승인 직후 `section_approval_status`는
`active.workflow_version`(`@7a18…`/`@bf3b…`)과 `current_version`(`@dff5…`)을 비교하므로
**방금 승인한 최신 후보가 곧바로 SUPERSEDED로 표시**된다. "옛 결과를 승인하면
SUPERSEDED"는 의도된 동작이지만, 여기서는 **최신 후보를 승인해도** 같은 표시가 난다.

### 2.3 가장 작은 조치 (산문)

- 승인 버전의 원천을 **검토한 섹션 결과 행이 실제로 가진 스탬프**로 맞춘다. 즉
  `section_result_id`가 가리키는 행의 `workflow_version`을 승인 기록의 축으로 쓰고,
  구성 집합도 그 스탬프를 만든 manifest와 같은 값으로 남긴다.
- 또는 재검증이 **새 R1 결과 행**(`mp05-form-2`)을 남기게 해 저장 결과 기반 계산과
  본문 스탬프를 일치시킨다. 기존 행을 고치거나 backfill하는 방식은 필요 없다.
- 대표 확인은 "재검증 후보를 승인하면 기록된 버전 == 그 섹션 결과 스탬프" 1건이면
  충분하다. 현재 `test_old_result_versions_do_not_become_the_current_candidate`와
  `test_module_runner`의 승인 검사는 `test-*` 버전을 쓰므로 이 불일치를 잡지 못한다.

## 4. 판정

- **질문 1:** 부분 실패. 미래 전망·선정 결론은 정상 유지되지만, **덜어낸 과거 사건이
  전제로 남는 형태**가 두 저장 사례에서 확인된다. 외부 인용 부재·의견 결론 자체는
  실패 사유로 삼지 않았다.
- **질문 2:** 옛 이력 보존과 현재 후보 계산은 통과, **승인 기록의 버전 동일성은 실패**.
  옛 결과가 새 코드를 조용히 승인하지는 않지만, 그 반대 방향(새 코드 본문이 옛 버전으로
  기록됨)이 실제 저장 행에서 재현된다.
- 이 문서는 **범위 한정 판정**이다. 전체 프로젝트 수용 판정이 아니며, MP-09/S1, 검색
  확보, 권한·보안·API 연결은 보지 않았다.
