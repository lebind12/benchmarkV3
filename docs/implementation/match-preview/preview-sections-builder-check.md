# 프리뷰 섹션 구성 설계 — 구현 계획 작성자 관점 확인 질문

작성: 2026-11-11 (KST). 검토 대상: `docs/superpowers/specs/2026-11-11-preview-sections-design.md`.

이 설계 문서에는 번호가 붙은 절이 없다. 그래서 아래 인용은 전부 **원문 행 번호**(예: `36행`)
로 적었다. 참조하는 대상은 검토 시점의 작업 사본(`?? docs/superpowers/specs/`)이다.

이 문서는 설계 승인 심사가 아니다. 이 설계를 받은 구현 계획 작성자가 **저자에게 다시
물을 수 없는 상태에서 "여기서 잘못 짐작하면 계획의 구조가 달라지는" 지점**만 모은 것이다.
사용자가 확정한 요구(두 묶음 조사, 주제별 상한 2/2/3, 배당 정규시간 1X2 소수점, 최종
전망·스코어 후행, 결정적 화면 조립, 브라우저 없는 수집, 기사 본문 채택 시 API 교차검증
없음, Google 인용 metadata 비강제, 새 검증 엔진 없음)는 다시 묻지 않고 계획의 고정
입력으로 둔다.

## 1. 한 줄 결론

설계는 실행 순서와 자료 소유권을 꽤 좁혀 두었고, 조사·수집·작성·조립의 경계도 이미
정해져 있다. 그래도 구현 계획을 확정하려면 **문서가 아직 답하지 않은 결정 다섯 개**가
필요하다. 1·2번은 "이 설계로 프리뷰가 실제로 만들어지는가"를, 3번은 승인·버전·화면의
단위 수를, 4번은 관리자 조정 기능의 실제 범위를, 5번은 어떤 수집 자료가 자격이 있는지를
정한다. 다섯 개 모두 나중에 고치면 저장 구조나 승인 근거를 다시 만들어야 하는 종류다.

## Q1. 최종 AI 전망 호출의 착수 조건은 '세 작성 결과 전부'인가, '확보된 자료만으로도'인가

**문서 위치.** `36행`은 "세 작성 결과와 배당 정리, DB 경기력 자료가 준비되면 최종 AI
요청1회"라고 하고, 이어서 "완료/자료 없음/실패로 종료된 갈래를 구분해 받고 … 확보된
자료만 사용"이라고 한다. 앞 문장은 세 갈래 전부를 전제로 읽히고, 뒤 문장은 부분 자료로도
진행하는 것으로 읽힌다. `27행`은 "최종 AI 전망은 확보된 각 섹션 결과와 DB 자료를 읽는다"고만
한다.

**왜 짐작이 필요한가.** 현재 코드는 S1 호출 **전에** V0의 `core_evidence_satisfied`를
검사한다. 이 값은 "참조가 붙은 채택 FACT claim이 하나 이상"일 때만 참이고
(`validation.py:512-517`, FACT 참조 규칙 `:444-453`), 거짓이면 S1을 부르지 않고 실행을
`unavailable`로 끝낸다(`synthesis.py:1458-1467`, `pipeline.py:627-643`, `:1019-1029`).
새 설계는 기사 본문 채택에 API 교차검증을 요구하지 않고(`62-64행`), 접근하지 못한
페이지는 DB 자료로 보완한다고만 한다(`25행`). 그런데 기사 수집이 전부 실패하고 DB
자료(순위·최근 경기)만 남는 경기는 정확히 이 게이트에 걸린다. 기존 시험에서도 그 경기의 프리뷰 성격 기사는
0건이었다(연결 사실 조사 §6).

**답에 따라 계획이 갈리는 지점.**

- **전부 준비 필요**로 정하면: 자료가 얇은 경기는 최종 전망이 아예 생성되지 않는다.
  6회 예산(`43행`) 중 6번째 호출은 쓰이지 않고, 관리자 초안 화면에 "무엇이 없어 못
  만들었는지"를 남기는 별도 표현이 필요하다. 실행 상태 어휘도 손봐야 한다.
- **부분 진행**으로 정하면: 기존 V0/S1 게이트를 새 기준으로 바꿔야 한다. 새 검증 엔진을
  만들지 않기로 했으므로(`64행`), ① 그대로 두고 claim 참조만 새 정보 원문 스냅샷에
  맞추는지 ② DB 사실도 통과시키도록 완화하는지 ③ 최종 호출 앞 게이트에서 빼는지 중
  하나를 골라야 하고, 이 선택이 `validation.py`·`synthesis.py`의 소유권과 버전 축을 바꾼다.
- 어느 쪽이든 **자료 없음으로 끝나 모델 호출을 시작하지 않은 갈래의 몫은 예약으로 남는다**.
  `retry.py:313-326`은 호출 등록만 하고 반납 경로가 없으며 `:363-367`이 그 예약을 재시도
  상한으로 쓴다. 부분 진행을 택하면 이 몫을 반납하는 규칙도 함께 정해야 한다. 안 그러면
  자료가 얇은 실행일수록 남은 갈래의 재시도 여유가 줄어드는 반대 결과가 난다.

**묻는 것.** 세 작성 결과 중 일부가 `자료 없음` 또는 실패로 끝났을 때 최종 AI 요청을
보내는가. 보낸다면 착수 조건은 무엇인가(작성 결과 최소 1개 / DB 경기력 자료만으로도 /
아무것도 없을 때만 생략). 그리고 기존 `core_evidence_satisfied` 게이트는 유지·완화·제외
중 무엇인가.

## Q2. '필수 섹션'은 어느 것인가 — 부상·배당 자료가 빈 경기도 정상 완료가 되는가

**문서 위치.** `37행`은 "전체 정상 완료 여부는 필수 섹션과 승인 버전을 확인해 정한다"고
하고, "자료가 부족하면 관리자 초안에서 확보된 본문을 확인할 수 있게 하고 정상 프리뷰
완료로 위장하지 않는다. 독자에게 내용 없는 섹션의 오류 문구를 넣지 않는다"고 한다.
`56행`은 부상 인원이 적으면 줄이라고 하고, `58행`은 배당 누락값 추정을 금지한다.

**왜 짐작이 필요한가.** 문서는 "필수 섹션"이라는 말을 쓰지만 **목록을 주지 않는다**. 현재
코드에도 필수 표시가 없고, 승인 게이트는 등록된 섹션 워크플로우 전부를 요구한다
(`pipeline.py:184-186`, `:1083-1092`; 등록부 `registry.py:257-311`). 그런데 이 설계의
출발점 자체가 자료가 비어 있을 수 있는 상태다. 연결 사실 조사에 따르면 `public.injury`
표는 전체 0행이고(§3.2), 배당은 표가 없으며 제품 수집 경로도 연결되지 않았다(§3.4).
모든 섹션이 필수라면 이런 경기는 항상 초안이고, 일부만 필수라면 어느 것인지가 승인·게이트·
화면의 기준이 된다.

**답에 따라 계획이 갈리는 지점.**

- **전부 필수**: 관리자 화면의 기본 결과가 항상 "초안"이 되고, 독자 노출 조건을 새로
  만들어야 한다. 지금 독자 경로는 S1 본문이 있으면 부분 결과도 그대로 내보낸다
  (`preview_admin.py:701-745`, `section_preview.py:83-121`). 여기에 "필수 섹션 본문이
  모두 있는가"를 넣으면 응답 계약과 404 사유가 바뀐다.
- **핵심 N개만 필수**: 어느 섹션이 핵심인지가 승인 요구 목록·관리자 라벨·독자 노출을
  좌우한다. 예를 들어 매체·배당이 선택이면 그 두 섹션이 빈 경기도 정상 프리뷰가 된다.
- **완료 상태 어휘**: 지금 실행 성공 여부는 최종 상태의 `unavailable_reason` 하나로
  정해진다(`pipeline.py:1019-1029`). 갈래 하나가 결과를 남기지 못하면 투영 단계는 진단만
  남기고 실행은 `SUCCEEDED`/`READY`로 남는다(`:776-782`). 부분 완료를 별도 상태로 저장할지,
  기존 `quality`로만 표현할지가 저장·API 계약을 바꾼다.
- 승인 근거는 본문이 있는 섹션 결과만 쓸 수 있으므로(`approvals.py:403-406`), 빈 섹션의
  **버전 승인**은 다른 경기 실행에서 받아야 한다. 정상 완료를 경기 단위로 판정하면 이
  두 단위(버전 승인 / 경기별 완료)를 화면이 구분해 설명해야 한다.

**묻는 것.** 새 기본 경로의 필수 섹션 목록은 무엇인가. 부상·배당 자료가 없는 경기도
"정상" 완료가 될 수 있는가. 안 된다면 그 실행은 어떤 상태·라벨로 남고, 독자 화면에는
부분 본문이 나가는가.

## Q3. 사용자가 승인하고 화면이 확인하는 단위는 몇 개인가 — 배당·AI 스코어의 소속

**문서 위치.** `51-58행`의 독자 섹션 표는 화면 블록 6개(AI 경기 전망, AI 예상 스코어, 주목
선수, 주목할 부상 선수, 외부 매체 전망, 배당 현황)를 정한다. `39행`은 R4/R2/R3/S1의 역할을
정리하고, `78행`은 "파일 소유권과 버전 변경 범위"를 구현 계획에서 확정하라고 한다. 반면
`AGENTS.md:65-69`는 승인 단위를 "섹션 워크플로우 버전"으로 못박는다.

**왜 짐작이 필요한가.** 파일 분해를 묻는 것이 아니다. **사용자가 버전을 승인하고 관리자
화면이 결과를 확인하는 단위**가 몇 개인지가 문서에 없다. 현재는 5개이고
(`registry.py:257-311`), 그중 `section_outlook`이 배당과 매체 전망을 함께 담는다
(`:279-287`). 새 경로에서는 AI 전망과 예상 스코어를 한 호출로 함께 만들고(`36행`, `53-54행`),
배당은 모델 없이 정규화한다(`35행`). 그래서 다음이 정해지지 않았다.

- AI 전망 + AI 예상 스코어: 한 워크플로우(승인 1건)인가, 두 워크플로우인가.
- 외부 매체 전망 + 배당 현황: 한 워크플로우(현 `section_outlook` 개정)인가, 둘인가.
  둘이면 배당 워크플로우는 모델 호출이 없어 `43행`의 정상 6회 산술과 예약 계산에서 빠진다.
- `section_form`(R1): `39행`은 R1의 별도 검색·산문 생성을 새 정상 호출에 중복하지 않고
  옛 모듈·섹션 버전과 승인을 보존해 새 기본 구성에서 분리한다고 한다. 그러면 기본 경로의
  승인 요구 목록에서 빠지는지, 기존 승인은 어떤 상태로 화면에 남는지.

**답에 따라 계획이 갈리는 지점.**

- 한 호출 결과를 두 승인 단위로 나누면, 같은 섹션 결과 행을 두 워크플로우가 근거로
  쓰는 규칙과 버전 스탬프가 필요하다. 저장은 `preview_section_results`의 `workflow_id`
  단위(`store.py:531-600`)이고 승인은 `workflow_id`당 활성 1건(`approvals.py:461-480`)이라
  지금 구조로는 그대로 맞지 않는다.
- 배당을 별도 워크플로우로 두면 승인 화면에 모델 없는 워크플로우가 생기고, 조립 단계가
  그 결과를 표로 배치한다. 합치면 R3 결과 payload에 배당 표가 남는다.
- `section_form`을 빼면 `required_workflows()`(=`SECTION_WORKFLOW_IDS` + 종합,
  `pipeline.py:184-186`)와 기본 실행 승인 게이트가 바뀌고, 기존 승인 행을 "새 기본 경로
  아님"으로 표시하는 상태가 필요하다.

**묻는 것.** 새 기본 경로의 섹션 워크플로우 목록(승인 단위)과, 위 6개 독자 블록이 각각
어느 워크플로우 결과에서 나오는지. `section_form`은 유지·개정·기본 경로 제외 중 무엇인가.

## Q4. '조정'이 이번 1차에서 실제로 지원해야 하는 동작은 무엇인가

**문서 위치.** `9행`은 "원문 수집·작성 입력·실제 응답·저장 본문이 연결돼 사용자가 조정할
수 있어야 한다"고 하고, `70행`은 "한 섹션을 조정할 때 다른 성공 섹션을 자동 재호출하지
않는다"고 한다. `66행`은 관리자 검사에서 무엇을 볼 수 있는지 나열한다.

**왜 짐작이 필요한가.** 문서는 조정의 **대상**을 말하지 않는다. 현재 제품에는 본문 편집
경로가 없다(프리뷰 관리자 API의 PUT/PATCH/DELETE 0건). 승인 근거는 저장된 섹션 본문
행이고(`approvals.py:367-414`), `72행`은 "재처리 본문은 파일만 만든 상태를 관리자 화면
저장 완료로 표현하지 않는다"고 한다. 조정이 재실행인지, 수집 후보 교체인지, 본문 직접
편집인지에 따라 필요한 화면과 저장 구조가 완전히 다르다.

**답에 따라 계획이 갈리는 지점.**

- **재실행만**: 기존 모듈 재실행·섹션 실행 경로로 충분하다(`pipeline.py:1321-1390`,
  `runner.py:625-700`). 새 저장 구조가 없고, 예산은 같은 실행의 남은 몫을 쓴다.
- **수집 후보 교체**: 관리자가 후보 URL을 선택·제외하는 입력이 새로 필요하고, 그 선택이
  섹션 입력 해시·버전 축에 들어간다(`62행`의 "실제 작성에 전달한 구간"과는 다른 축이다).
- **본문 직접 편집**: 섹션 결과에 편집 버전을 만들고, 승인 근거가 "모델이 만든 본문"이
  아니라 "관리자가 고친 본문"임을 남기는 규칙이 필요하다. 승인 화면과 버전 비교 화면이
  같이 바뀌고, `72행`이 구분한 "파일만 만든 재처리 본문"과도 다시 구분해야 한다.

**묻는 것.** 이번 1차에서 조정이 반드시 지원해야 하는 동작은 무엇인가(섹션 재실행 /
후보 출처 교체 / 본문 직접 편집 / 위 전부). 그리고 조정 실행은 같은 실행의 남은 예산을
쓰는가, 새 실행으로 예산을 새로 받는가.

## Q5. 수집 자료의 시점 기준 — 킥오프 이전 규칙을 어느 섹션에 적용하는가

**문서 위치.** `31행`은 DB 자료를 "경기 기준시점"과 함께 저장한다고 하고, `58행`은 배당에
수집시각을 요구한다. `33-35행`은 하나의 공통 수집 서비스가 만든 기사 본문을 여러 섹션이
나눠 쓴다고 한다.

**왜 짐작이 필요한가.** 현재 코드는 **매체 전망에만** "게시 시각이 킥오프 이후면 제외"
규칙을 적용하고, 게시 시각이 없으면 허용한다(`outlook.py:869-875`, `:976-982`). 새 경로는
같은 수집 본문을 선수·부상 섹션에도 쓴다(`34-35행`). 선수·부상 기사에도 킥오프 이전
기준을 적용할지, 적용하면 게시 시각을 못 뽑은 페이지를 어떻게 할지가 정해지지 않았다.
브라우저 없는 추출에서 게시 시각은 자주 비므로, 이 규칙이 실제 채택량과 초안 비율을
크게 바꾼다.

**답에 따라 계획이 갈리는 지점.**

- **전 섹션 동일 기준**: 수집 단계에서 게시 시각 추출·검증이 필수 기능이 되고, 시각이
  없는 문서는 제외하거나 약한 등급으로 따로 남겨야 한다. 수집 실패를 자료 부족으로
  처리하는 경로가 늘고 초안이 늘어난다.
- **매체 전망만**: 선수·부상은 시점 필터 없이 쓰고, 오래된 기사가 섞일 위험은 `62행`의
  자료 성격 표시로만 구분한다. 계획에서 시각 추출을 필수로 만들지 않는다.

**묻는 것.** 킥오프 이전 기준을 어느 섹션 자료에 적용하는가(전부 / 외부 매체 전망만 /
배당·전망만). 게시 시각이 없는 문서는 채택·제외·보류 중 무엇인가.
