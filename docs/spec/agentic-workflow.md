# 요구사항 계약과 외부 실행 제어

2026-10-28 후속 결정: [외부 제어 전환](../decisions/2026-10-28-external-harness-control.md).
새 작업의 실행 정본은 `scripts/harness-run.sh`와 `scripts/harness_runtime/`다.
이전 `work-flow`, `feature-flow`, `endpoint-flow`의 상태·보고서·승인은 과거 이력이며 새 엔진의 완료를 대신하지 않는다.

## 사용자와 운영자

현재 루트 대화가 운영자다. 별도 관리자 AI를 필수로 추가하지 않는다. 운영자는 사용자 요청 원문, 기획·정책 결정, 작업 범위와 결과 설명을 맡는다. 구현 방법은 개발자에게 맡기되 필수 요구사항 삭제·검증 생략·완료 상태 확정은 개발자의 권한이 아니다. 실제 병합 판단은 운영자가 하고 배포는 사용자가 명시적으로 요청해야 한다.

새 독립 개발 요청은 제품 파일을 바꾸기 전에 QUICK/FULL을 한 번 선택받는다. 요청에서 명시했거나 같은 작업의 후속 수정이면 재사용한다. 무응답을 선택으로 간주하지 않는다. 조사·읽기 전용 범위 파악은 기다리는 동안 진행할 수 있다.

- QUICK: 기존 기능의 국소 수정. 짧은 목표·범위·수용 시나리오로 계약을 작성한다. 낮은 영향 문구·스타일은 별도 테스트 명령 없이 독립 검토자의 실제 파일 조회로 확인할 수 있다. 가짜 테스트·서비스 계획·커밋·포트폴리오 보고서를 요구하지 않는다.
- FULL: 새로운 기능·흐름·구조·권한·외부 연동. 원문 전체의 요구사항과 실패·경계 시나리오를 정하고 적절한 로컬 검증 명령을 연결한다. 기술·사용자·운영 조사는 실제 불확실성에 맞춰 수행하며 확정 자료를 재사용한다.
- QUICK에서 새로운 정책이나 범위 확장이 필요하면 이유와 추가 범위를 제시해 선택을 받는다. 실패한 FULL의 조건을 낮춰 QUICK으로 우회하지 않는다.

## 구현 전에 요구사항을 구체화한다

운영자는 원문과 기존 정책을 정리하고 `draft` 또는 직접 작성으로 계약을 준비한다. [JSON 템플릿](../harness/templates/requirement-contract.json), [작성 안내](../harness/templates/requirements.md), `.codex/schemas/requirement-contract.schema.json`을 따른다.

1. `source_coverage`: 원문 그대로의 인용과 요구사항 ID 연결. 모델 요약으로 원문을 대체하지 않는다.
2. `requirements`: 필수 여부, 구체적 동작, 관찰 가능한 수용 시나리오. 명시된 요구를 임의로 선택·MVP·후속 범위로 바꾸지 않는다.
3. `questions`, `assumptions`: 중요한 미정 질문과 확인이 필요한 가정. 이미 확정된 내용을 다시 승인받지 않는다.
4. `owned_paths`, `constraints`, `out_of_scope`: 수정 소유 범위, 기존 정책, 명시된 제외 범위. 구현 방법을 불필요하게 고정하지 않는다.
5. `verification_commands`, `verification_files`: 요구사항별 실제 검증 명령과 변경되면 검증이 무효화될 기존 테스트/설정 파일.

중요 질문·가정이 미정이면 `WAITING_REQUIREMENTS`다. 조회·조사로 답할 수 없는 결정만 사용자에게 묻는다. 필드가 채워진 것과 원문 의미가 모두 반영된 것은 다르므로, 실행기는 구현 전 별도 읽기 전용 세션에서 원문 전체와 계약의 누락을 검토한다. ID 개수만으로 의미적 완전성을 주장하지 않는다.

프론트 목업 → endpoint 목록/응답 계약 → 백엔드 → 통합 순서는 유지한다. 운영자는 이 순서에 맞는 작업 범위와 인계물을 정한다. 엔진의 개발 단계 내부 구현 순서를 모두 자동 판독한다고 주장하지 않는다.

## 구현 판단과 변경 범위

[Karpathy 지침 반영 결정](../decisions/2026-10-28-karpathy-guidelines.md)의 네 원칙을 기존 기획·개발·독립 검토에 적용한다. 역할이나 승인 단계를 추가하지 않는다.

- 중요한 모호함은 기존 코드·정책·결정으로 먼저 해소한다. 결과·권한·데이터·범위가 달라지는 해석만 차이·권장안·이유와 함께 질문한다. 일반적인 구현 선택과 이미 정해진 사항을 다시 묻지 않는다.
- 모든 필수 요구와 기존 정책을 충족하는 가장 단순한 구현을 선택한다. 현재 요구나 필수 의존성에 필요 없는 추상화·설정 옵션·미래 기능을 도입하지 않는다. 필요한 구조 변경은 이유를 설명하며 코드 줄 수나 개인 취향으로 금지하지 않는다.
- **단순화는 구현 방법에만 적용한다. 기능·오류 처리·권한·데이터 보호·수용 기준의 생략과 후속 이월을 허용하지 않는다.**
- 기존 구조와 스타일을 존중한다. 요청과 무관한 리팩터링·인접 주석/포맷 변경·기존 dead code 삭제를 섞지 않는다. 이번 변경으로 불필요해진 import/변수/함수만 함께 정리하고, 기존 무관한 문제는 보고만 한다.
- 개발자는 주요 변경을 요구사항 ID 또는 필수 의존성과 연결해 설명한다. 독립 검토자는 실제 diff와 주변 코드를 읽고 관련성을 확인한다. 기존 타인의 변경을 이번 작업에 귀속하지 않으며 기준본이 없으면 그 한계를 명시한다. 허용 경로 검사만으로 변경 내용의 적절성까지 증명하지 않는다.
- 불필요한 변경/복잡도가 있으면 검토자는 파일·변경 위치·이유를 기존 `coverage_gaps`에 기록하고 FAIL로 제출한다. 필요한 구조 변경의 근거는 `summary`에 남긴다. 기존 완료 게이트가 비어 있지 않은 `coverage_gaps` 또는 비-PASS를 재작업으로 돌린다. 의미적 판정 자체는 검토 모델의 판단이며 기계적 보장이 아니다.

버그 수정은 운영자가 기존 재현 근거를 확인하거나 구현 전에 적절한 최소 재현을 수행한다. 조건·기대/실제 결과·명령·대상 코드 버전·근거 경로를 기획 맥락과 계약의 `constraints`에 연결하고, `scenarios`와 외부 검증 명령에 같은 조건의 수정 후 확인 및 관련 회귀를 반영한다. 재현 불가 시 한계와 대체 확인을 명시하며 실행하지 않은 결과를 꾸미지 않는다. 동결 검증 파일을 고쳐 통과시키지 않는다. 낮은 영향 문구·스타일 수정에는 재현 테스트를 강제하지 않는다.

실제 외부 세션은 `requirements.py`의 기획 프롬프트와 `controller.py`의 명세·개발·코드 검토 프롬프트를 사용한다. `.codex/agents/`의 역할 지침만 수정한 것을 실행기 반영으로 간주하지 않는다. 이번 직접 하네스 수정은 기존 사용자 결정대로 정적 확인만 수행하고 실제 개발 사용 피드백으로 효과를 평가한다.

## 외부 실행기를 기본 진입점으로 사용한다

운영자는 기존 작업을 보존한 별도 worktree를 준비하고 [실행 안내](../harness/external-control.md)에 따라 `init`과 `run`을 호출한다. 설치된 제어 코드가 있는 checkout 자체를 개발 workspace로 사용하지 않는다. 상태는 workspace 밖 SQLite와 원본 증거 파일에 저장한다. 개발자에게 상태·승인 파일 쓰기 권한을 주지 않는다.

`요구사항 준비 → 독립 명세 검토 → 개발 세션 → 외부 검증 명령 → 독립 구현 검토 → VERIFIED`

- 개발·검토는 서로 다른 `codex exec` 세션이다. 하위 세션 안에서 운영자를 또 만들거나 QUICK/FULL을 재질문하거나 전체 하네스를 재시작하지 않는다.
- 모델은 `--model`로 작업별 선택하며 운영 대화 모델은 고정하지 않는다. 기본 개발/검토 모델은 `gpt-6.1-sol`, 추론 medium이다.
- 명세·코드 검토는 읽기 전용이다. 검증 명령은 원본 workspace를 읽고 별도 scratch에만 쓰며 네트워크 접근을 허용하지 않는다. 의존성 준비·외부 조사·승인된 환경 설정은 운영자가 실행 전에 수행한다.
- 실행기는 실제 명령·시각·종료 코드·로그 지문·코드 지문을 기록한다. 코드 검토자는 실제 관찰 명령 또는 외부 검증 명령의 근거를 제시해야 한다.
- 검증 실패는 동일 요구사항을 유지한 제한 재작업으로 돌아간다. 한도 소진·권한 거절·환경 오류를 성공이나 범위 축소로 처리하지 않는다.
- `VERIFIED`는 그 코드 지문에서의 검증 완료다. 코드가 이후 바뀌면 기존 완료를 무효화한다. Git 병합·push·배포를 자동 실행하지 않는다.

엔진을 거치지 않은 native 대화의 final 응답을 가로채는 전역 훅은 설치하지 않는다. 공식 완료 상태의 강제력은 이 진입점으로 실행한 작업에 적용된다. 운영자는 엔진 실패를 native 직접 구현·자기 완료 선언으로 조용히 우회하지 말고 막힌 원인과 필요한 조치를 설명한다.

## 범위 변경과 재개

사용자 후속 결정은 원문을 덮어쓰지 않고 `request_additions`와 새 계약 버전으로 보존한다. `change`는 실제 사용자 메시지·출처와 이전/새 계약 digest가 연결된 receipt를 요구한다. 운영자가 실제 대화와 대조하며, JSON만으로 같은 OS 사용자의 신원을 인증했다고 표현하지 않는다. 개발 세션은 이 기록을 만들지 않는다.

새 계약은 이전 명세 검토·구현 검토·PASS를 무효화한다. `cancel`은 중단이며 파일 되돌리기가 아니다. 장애 후 `resume`은 중단 사실을 보존하고 다시 실행한다. 미완료 작업을 완료로 추정하지 않는다.

## 이상현상과 하네스 개선

범위 축소, 명세 누락, 의미 없는 반복, 검사 생략, 과도한 절차 부담은 `feedback`으로 원본 근거와 함께 기록한다. 실행 이벤트와 관찰은 실제 수집한 범위만 의미하며 Codex의 모든 내부 도구나 추론을 수집하지 않는다. 원인은 코드·환경·하네스·미확정으로 구분한다.

일반적인 자동 생성 후보는 `.harness/AGENTS.md`의 사용자 승인 경계를 따른다. 사용자가 하네스 자체를 직접 수정하라고 지시하며 별도 절차를 정하면 그 최신 지시가 우선한다. 수정 대상 하네스가 자기 변경의 성공을 인증하도록 만들지 않는다. 이번 전환은 사용자 명시 지시에 따라 기존 하네스 절차·비교 평가를 적용하지 않고 직접 반영했으며, 실제 개발 사용 피드백으로 후속 개선한다.

역할은 필요한 만큼만 사용한다. 조사·기획 검토 근거는 재사용하며 매 수정에 전체 팀을 생성하지 않는다. 서비스 포트폴리오는 주요 사용자 흐름이 완성됐을 때 서비스 전체 단위로 다룬다. `Plans.md`, 도메인 정책, 병렬 worktree 소유권, 외부 게시·배포 승인 경계는 유지한다.
