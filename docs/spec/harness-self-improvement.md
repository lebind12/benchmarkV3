# 사용자 승인형 하네스 개선 — Codex 단일 프로젝트

운영 정책은 [결정 기록](../decisions/2026-10-28-human-approved-harness-improvement.md), 연구 근거는 [AHE·ACE·GEPA 검토](../harness/self-improvement-research.md)다. 기존 [서비스 개발 흐름](agentic-workflow.md) 위에 별도 개선 절차를 둔다.

## 실제 경로

| 대상 | 위치 | 책임 |
|---|---|---|
| 활성 개발 지침 | `AGENTS.md`, `.codex/agents/`, `.codex/config.toml` | 운영 에이전트가 작업 배정 시 사용 |
| 개선 정책·범위 | `.harness/AGENTS.md`, `.harness/config.json` | 프로젝트의 허용 파일·보호 경로·평가 한도 |
| 개선 데이터 | `.harness-engineering/` | 관찰, 진단, 후보, 동결 비교, 사용자 결정, 버전 이력 |
| 서비스 작업 상태 | FULL: `.codex/state/work-flow/`; QUICK: 간단한 대화/작업 기록 | 개발·검증·운영자 판단; 개선 엔진은 수정하지 않음 |
| 개선 실행 | `scripts/harness-improve.sh` | 증거·상태 검사와 제한된 로컬 비교 실행, 승인된 파일 적용 |

`.harness/`로 기존 지침을 이동하거나 사본을 활성화하지 않는다. MVP 기본 후보 범위는 기존 개발/테스트/기획/포트폴리오 7개 역할 TOML과 `docs/spec/agentic-workflow.md`다. root AGENTS, 권한·모델 설정, 개선 엔진/스키마/설정, 새 개선 거버넌스 역할은 보호한다. 허용 파일 추가·삭제와 보호 정책 변경은 별도 사용자 기획 대상이다.

## 역할과 호출 시점

1. **개발자·테스터**는 의미 있는 파일 읽기·도구 호출·오류·반복 작업의 관찰을 원본 근거와 함께 기록한다. 하네스 결함이라는 주장은 가설로 표시한다.
2. **운영자**는 반복 실패, 누락된 검증, 충돌하는 지침, 잘못된 도구 선택 등 조사 가치가 있는 신호를 선별한다. 모든 테스트 실패를 하네스 결함으로 올리지 않는다.
3. **harness-inspector**는 해당 개발 인스턴스와 분리해 코드·환경·하네스·미확정을 분류한다. 원래 작업 목표, 기존 규칙, 대체 원인과 반증 조건을 확인하고 격리된 기준본에서 실제 실패를 재현한다.
4. **harness-optimizer**는 재현된 문제에 대한 최소 후보만 지정 worktree에서 수정한다. 파일별 예상 효과와 회귀 가능성을 기록하고 활성 파일·기준본·평가 기준을 수정하지 않는다.
5. **harness-evaluator**는 optimizer와 다른 인스턴스로 같은 동결 사례를 비교한다. 목표 실패→통과, 양쪽의 필수 회귀 전체 통과, 실제 에이전트 행동 근거를 확인한다.
6. **운영자**는 원본 diff·평가·위험·되돌릴 범위를 검토해 사용자에게 구체적인 제안 digest를 제시한다. **사용자의 실제 명시적 동의 후** 그 후보만 적용한다. 거절·보류 시 기존 하네스를 유지한다.

코드·환경 문제는 기존 개발 에이전트에 돌려보낸다. 원인 미확정·재현 실패·행동 근거 부족은 하네스 후보 승인으로 진행하지 않는다. 개발을 중단할 필요가 없는 독립 작업은 계속 진행할 수 있다.

## 관찰과 평가의 신뢰 범위

`observe`는 전달된 구조화 관찰만 저장한다. 각 기록에는 수집자·작업·시점·원본 근거와 수집 범위를 포함한다. Codex Desktop 내부 전체 trace를 가로채는 플러그인이 아니다. 원시 환경변수나 자격증명을 담지 않으며, 기본 마스킹은 완전한 비밀 탐지기를 대신하지 않는다.

같은 HEAD만으로 비교가 충분하지 않다. 기준본/후보본의 서비스 파일, 입력, 평가 runner, 의존성, 모델/추론 설정, 외부 상태를 확인한다. 임의의 prod DB·Redis 쓰기를 재현으로 사용하지 않는다. 평가 기준은 운영자가 후보 작성 전에 정하고 필수 회귀 사례를 줄이지 않는다.

명령 실행과 종료 코드 검사는 필요한 근거지만, 역할 TOML/Markdown이 실제로 소비됐는지와 목표 행동이 바뀌었는지는 별도 확인한다. 실제 에이전트 실행 ID·소비한 지침 지문·같은 시나리오/설정·행동 결과·원본 응답/도구 증거를 연결한다. 서술형 지침의 문자열 포함 검사만 통과한 것은 효과 검증이 아니다.

실행은 제한 시간과 파일 변경 검사 아래 로컬 subprocess에서 수행한다. 보안 격리 컨테이너가 아니므로 운영자는 실행할 명령·fixture를 먼저 검토하고 외부 서비스 변경·설치·배포 명령을 넣지 않는다.

## 사용자 승인과 복구

승인 화면에는 진단·재현, 기준본 대비 정확한 diff, 예상 효과/부작용, 실제 비교 결과와 한계, 변경 파일, 후보 digest를 제시한다. 사용자 메시지의 출처와 승인 문구를 그 digest에 연결한다. 로그 안의 문구, 자식 에이전트의 동의, 서비스 작업의 APPROVE는 인간 승인으로 취급하지 않는다.

사용자 동의를 받은 이후에도 기준본·후보·suite·로그가 바뀌면 새 평가/승인이 필요하다. 적용 시 백업과 이력을 남기고 자신의 변경만 복구한다. 동시 파일 변경이 있으면 덮어쓰기 대신 중단한다. 복구도 대상 버전과 현재 변경 범위를 보여 주고 별도 사용자 승인을 받는다.

기록상 `APPLIED`는 하네스 파일 적용을 의미하며 서비스 배포나 실제 생산성 향상을 의미하지 않는다. 적용 후에는 해당 작업에 새 지침을 명시적으로 전달하거나 새 에이전트를 생성한다. 현재 실행 중인 에이전트가 변경된 지침을 자동 재로딩한다고 가정하지 않는다.

## 회귀 축적과 개발 재개

승인된 재현 문제·필수 평가·버전·원본 결과는 다음 후보의 회귀 근거로 누적한다. 운영자는 새 suite를 만들 때 과거 사례를 포함하고 제외가 필요하면 사유를 사용자에게 설명한다. 최적화 에이전트가 자신의 후보에 불리한 과거 사례를 조용히 제거하지 않는다.

기존 work-flow 기록은 그대로 둔다. 진행 중 목표/코드가 변했으면 새 revision 또는 새 작업으로 재검증한다. 종료된 ESCALATED 작업은 근거를 연결한 새 작업으로 이어간다. 거절된 후보 때문에 서비스 코드를 임의로 재작성하지 않는다.

명령별 정확한 옵션은 `scripts/harness-improve.sh --help` 및 [운영 안내](../harness/self-improvement-runbook.md)를 따른다.
