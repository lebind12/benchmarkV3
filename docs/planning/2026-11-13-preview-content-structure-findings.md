# 프리뷰 본문 구조화와 DB 내부 ID 연결 조사

확인: 2026-11-13 03:27 KST. GPT 조정자의 코드 조사와 기존 관리자 조회 API의 저장 payload 대조 결과다. 독립 코드 리뷰나 구현 완료 보고가 아니다. 제품·테스트 코드, DB 저장 행, 승인 기록은 변경하지 않았고 생성·수집도 실행하지 않았다.

## 사용자 목적과 결론

프리뷰에 나오는 선수·팀을 DB 내부 ID로 연결하고, DB의 한글 이름과 관련 정보를 재사용하려는 목적이다. 홈의 현재 표시 결과는 이미 사용자가 수용했다.

현재도 내부 ID와 번역 테이블을 일부 사용한다. 응답 전체를 문자열 하나로만 저장하는 구조는 아니다. 그러나 섹션마다 ID 확인·저장 방식이 다르고, 본문 속 이름은 참조 관계 없이 문자열로 남는다. 필요한 것은 섹션별 구조화 본문과 검증된 엔티티 참조를 일관되게 저장하는 계약이다. JSONB라는 저장 형식 자체가 장애물은 아니다.

## 실제 저장본 대조

대상은 홈에서 수용한 맨체스터 시티–풀럼 경기(외부 경기 ID 1557474)의 기존 실행 `d96fe824-bc38-4402-bb2c-9f16fdee4b3b`이다. 관리자 detail GET의 results에서 다음 저장 행을 확인했다. DB 콘솔로 직접 SELECT한 결과는 아니다.

| 섹션·결과 행 | 실제 저장 내용 | 의미 |
|---|---|---|
| 주목 선수 / `d85ddee6-44e8-485c-8f6f-672a08139f88` | 엘링 홀란드 533, 필 포든 531, 로드리고 무니즈 138, 에밀 스미스 로우 122가 player_id로 저장됨. 각 항목은 selected_player·selection_reason·team·player_id·evidence로 구성됨. | 내부 선수 ID 연결은 이미 있다. team은 문자열이며 team_id는 저장돼 있지 않다. |
| 부상 / `692220b1-1f0f-4f71-8a79-5cd641c6aaae` | 마크 게히·조슈아 킹 모두 player_id=null. team_id는 각각 13·4. player_name·team·status·summary·evidence도 존재함. | 사진이 표시되는 사실만으로 선수 ID가 저장돼 있다고 결론낼 수 없다. 현재 조회 코드에는 이름으로 ID를 보강하는 경로가 있다. |
| AI 전망 / `0500d3a4-c4da-4ff9-b5ef-5250c23e2de4` | structured.forecast에 lean=home, score="2-1", reasoning 목록. 전망 문장은 body에 들어 있고 structured.forecast에는 없음. | 점수·이유 일부는 구조화됐지만 본문 전체를 구조화 값만으로 재현할 수 없다. |

이 저장본의 주목 선수 이름은 “로드리고 무니즈”인데 AI 전망의 이유 문장에는 “호드리구 무니스”가 쓰여 있다. 본문 문자열에 해당 인물의 ID 참조가 없어 카드의 한글 이름을 확인하는 것만으로 문장 표기까지 일치시키지는 못한다.

## 이미 활용할 수 있는 DB 연결

- `public.player.id`와 `public.team.id`가 내부 ID다. 외부 API ID는 각각 external_id로 분리돼 있다.
- 한글 표기는 `public.player_translation.player_id`, `public.team_translation.team_id`로 연결하며 name_ko·short_name_ko를 읽는다. 기존 이름 해석기는 이 JOIN을 이미 수행한다.
- 사진 경로는 확인한 외부 ID로 만든다. 현재 이름 조회가 선수 통계나 DB photo_url까지 전부 읽는 것은 아니다. 관련 정보 재사용은 필요한 자료별 조회가 추가돼야 한다.
- 홈 공개 응답에서 내부 ID를 빼는 것은 공개 응답의 필드 선택 정책이다. 서버에서 내부 ID를 저장·활용하지 못한다는 의미가 아니다.

## 설계 제안 — 아직 구현 확정 아님

권장 방향은 **섹션별 구조화 본문 + 검증된 선수·팀 연결 관계 + 생성 당시 원문 보존**이다.

본문은 버전이 있는 섹션별 JSONB 구조로 둘 수 있다. 선수·팀 연결을 관계형으로 관리하면 DB 조인과 외래 키 검증에 유리하다. 이 경우 연결 행에는 섹션 결과, 확인한 내부 선수·팀, 본문에서의 역할, 자료 기준 시점을 담는 방향을 검토한다. 내부 ID를 JSONB에만 두는 더 작은 변경도 가능하지만 DB 외래 키가 그 JSON 값을 직접 보장하지는 않으므로 서버 검증에 의존한다.

새 화면은 구조화 내용과 연결된 DB 한글 이름을 이용해 현재 디자인으로 그린다. 생성 당시 표기·근거는 별도로 보존한다. 번역 수정이 과거 문서의 표시에도 반영돼야 하는지와 생성 당시 표시를 고정해야 하는지는 표시 정책으로 구분한다.

다음 설계 단위는 주목 선수·부상의 공통 참조 계약과 AI 전망의 문단·점수·근거 구조다. 현재 홈 디자인, 기존 승인본, 과거2/미래2 표본 및 수집 연결의 합의는 유지한다. 이번 조사로 새 마이그레이션·생성·수집 연결을 시작하지 않는다.

## 확인 범위의 한계

ORM·생성·저장·조회 코드를 읽고 기존 실행 하나의 저장 payload를 관리자 API에서 확인했다. 모든 과거 기록의 ID 품질, 실제 DB DDL·외래 키 추가 권한, 마이그레이션 실행 가능성을 검사한 것은 아니다. 이 항목들은 설계 선택 후 필요한 범위에서 확인하며 현재 확인된 코드상 보완점과 구분한다.
