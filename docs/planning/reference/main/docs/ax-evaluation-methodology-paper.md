## 초록

자연어 데이터 검색 에이전트는 사용자의 질문을 해석하고, 필요한 데이터를 조회하며, 계산 결과를 자연어로 설명한다. 이 과정에서 SQL이 실행되거나 응답 형식이 올바르다는 사실만으로 답변의 정확성을 보장할 수 없다. 잘못된 시즌을 조회한 쿼리도 정상 실행될 수 있으며, 정확한 표를 반환한 뒤 그 의미를 잘못 설명할 수도 있기 때문이다. 본 문서는 Databricks, Uber, Snowflake, Anthropic의 공개 평가 사례와 Text-to-SQL 의미 평가 연구를 검토하고, 축구 대화형 검색에 적용할 정확도 우선 평가 방법을 제안한다. 제안 방법은 기대 행동, 질문 해석, 결과 데이터, 계산, 설명, 한계 표시를 구분하고, 해당 과제의 필수 조건을 모두 충족했을 때 정확한 완료로 판정한다. 또한 독립 정답 제작, 데이터 경계 사례, 대화 단위 검증, 채점기 검증, 반복 실행 및 평가 누출 방지 절차를 제시한다. 시간·재질문·비용은 초기부터 관측하되, 정확도 확보 이후의 최적화 대상으로 둔다. 본 문서의 수치 예제는 학습용 합성 데이터이며 프로젝트의 실측 성능을 나타내지 않는다.

**주제어:** 자연어 검색, Text-to-SQL, 에이전트 평가, 의미 정확도, 대화 문맥, 정답 데이터, 회귀 평가

## 1. 서론

### 1.1 왜 일반적인 테스트만으로 부족한가

전통적인 소프트웨어 테스트는 주어진 입력에 대해 정해진 출력이 나오는지를 검사한다. 자연어 검색에서도 이 방식은 유효하지만, 무엇을 출력의 정답으로 삼아야 하는지가 더 복잡하다. 같은 질문을 여러 SQL로 해결할 수 있고, 같은 사실을 여러 문장으로 설명할 수 있으며, 질문이 모호한 경우에는 결과를 내놓기 전에 사용자에게 확인하는 것이 올바른 행동일 수 있다.

“지난 시즌 EPL에서 가장 효율적으로 득점한 선수는 누구인가?”라는 질문을 생각해 보자. ‘지난 시즌’은 기준 날짜와 대회 시즌에 따라 달라진다. ‘효율적’은 90분당 득점, 슈팅 대비 득점, 또는 다른 지표를 의미할 수 있다. 지표를 90분당 득점으로 정하더라도 최소 출전 시간을 적용할지 결정해야 한다. 이 선택에 따라 답변이 달라지므로, 자연스러운 문장을 생성했다는 사실은 정확성의 충분한 증거가 아니다.

따라서 평가의 출발점은 모델에게 문제를 많이 묻는 일이 아니라 **어떤 답변과 행동을 올바르다고 볼 것인지 명시하는 일**이다.

### 1.2 본 문서의 질문과 범위

본 문서는 다음 세 질문을 다룬다. 첫째, 검색 에이전트의 정확도를 어떤 단위로 정의할 것인가? 둘째, 정답과 채점기를 어떻게 신뢰할 수 있게 만들 것인가? 셋째, 정확도를 확보한 뒤 시간과 재질문을 줄일 때 무엇을 보존해야 하는가?

대상은 저장된 축구 데이터를 조회하는 대화형 검색이다. 경기 결과를 미래에 예측하는 모델의 예측력은 다루지 않는다. 예측 평가는 관측된 미래 결과와 예측 확률을 비교해야 하므로, 저장 데이터 조회의 정답 평가와 별도 문제다.

학습 순서는 2장의 사례 비교, 3장의 개념 정의, 5장의 계산 예제, 6~8장의 실제 평가 설계를 권한다. 수식은 정의를 모호하지 않게 하기 위한 보조 수단이며 각 수식의 의미를 본문에 설명한다.

## 2. 관련 연구와 기업 사례

### 2.1 실행 결과를 정답과 비교하는 접근

Databricks의 2024년 Genie 발표는 자주 묻는 질문과 기준 SQL을 준비하고, 생성 쿼리의 결과를 기준 결과와 비교하는 방식을 설명한다. 지침을 변경한 뒤 같은 벤치마크를 재실행하는 개선 절차도 제시한다. 이는 생성 문장의 인상보다 검증 가능한 결과를 중심에 놓는 접근이다. [1]

Snowflake Cortex Analyst의 공식 문서는 평가에 선택된 검증 쿼리를 임시 의미 모델에서 제거하고, 생성 결과와 정답을 비교하며, 과거에 맞혔던 문제의 실패를 추적한다. 이 문서는 다중 턴 평가의 한계와 상대 날짜에 따른 정답 변화 가능성도 명시한다. [2]

두 사례에서 배울 점은 평가 문제를 입력으로 실행하고 독립된 기준과 비교하는 구조다. 다만 쿼리 결과 비교만으로 최종 설명이나 여러 턴에 걸친 과제 완수를 모두 검증할 수는 없다. 이러한 확장은 본 문서의 제안이다.

### 2.2 전체 평가와 단계별 평가를 병행하는 접근

Uber QueryGPT는 실제 질문의 의도, 필요한 스키마, 기준 SQL을 사람이 검증한 평가 세트를 사용한다. 질문만 제공하는 전체 경로와 올바른 의도·데이터셋을 제공하는 분리 경로를 평가해 앞 단계 오류의 영향을 구별한다. 의도, 테이블 선택, 실행 여부, 결과 유무, SQL 유사성 등을 따로 관측한다. [3]

이는 오류 원인을 찾는 데 중요하다. 잘못된 결과가 이름 해석에서 시작됐는지, 올바른 이름을 해석하고도 집계를 잘못했는지에 따라 수정할 부분이 달라진다. 다만 부분 단계가 정확하다는 사실을 전체 서비스의 정확도로 대체해서는 안 된다.

### 2.3 과제 결과와 채점 방식의 확장

Databricks의 2026년 Genie Code 발표는 내부 실제 사용에서 추출한 401개 과제를 대상으로 최종 답변의 정확성과 유용성을 평가했다고 설명한다. 이 사례는 평가 대상을 SQL 한 문장에서 사용자 과제로 넓힌다는 점에서 참고할 수 있다. 공개 글만으로 정답 세트와 심사 기준 전체를 재현할 수 없다는 한계도 있다. [4]

Anthropic의 에이전트 평가 가이드는 과제, 반복 실행, 채점기, 실행 기록, 최종 결과를 구분하고 코드·모델·사람 채점의 역할을 설명한다. 에이전트는 여러 단계에서 오류를 누적할 수 있으므로, 중간 과정과 최종 결과를 함께 다루는 평가 구조가 필요하다는 관점을 제공한다. [5]

### 2.4 단일 데이터에서의 결과 일치가 갖는 한계

Zhong, Yu, Klein은 Text-to-SQL의 의미 정확도를 근사하기 위해 여러 시험 데이터베이스에서 쿼리 결과를 평가하는 test-suite accuracy를 제안했다. 이 연구는 문자열이나 한 가지 데이터 상태만으로 쿼리의 의미를 평가하는 문제를 다룬다. [6]

이 원리를 프로젝트에 적용하면, 실제 데이터에서 우연히 동일한 결과가 나온 쿼리를 구별하기 위해 최소 출전 시간 경계, NULL, 동률, 다중 소속 등을 포함하는 작은 데이터셋을 추가할 수 있다. 이는 연구의 평가 원리를 응용하는 제안이며, 해당 논문의 시험 데이터 생성 절차를 그대로 재현했다는 의미는 아니다.

### 2.5 사례 비교

| 접근 | 핵심 평가 대상 | 장점 | 별도로 보완할 영역 |
|---|---|---|---|
| Genie 벤치마크 | 기준 SQL 대비 결과 | 수치와 결과를 직접 비교 | 설명과 대화 완결성 |
| Cortex Analyst 평가 | 검증 쿼리·변경 전후 결과 | 예시 제외와 회귀 추적 | 여러 턴의 문맥 |
| QueryGPT 평가 | 의도·스키마·SQL 등 | 오류 발생 단계 진단 | 최종 사용자 답변 검증 |
| 과제 단위 에이전트 평가 | 과제의 최종 결과 | 사용자 목적과 가까움 | 정답·심사 기준의 신뢰성 |
| Test-suite 평가 | 여러 데이터에서 쿼리 결과 | 우연한 결과 일치 탐지 | 자연어 설명과 제품 정책 |

## 3. 평가 문제의 정의

### 3.1 질문, 턴, 과제, 실행의 차이

**턴(turn)**은 사용자 입력 하나와 시스템 응답 하나의 상호작용이다. **과제(task)**는 사용자가 이루려는 목표다. “득점 순위를 보고 상위 두 선수의 전년 기록을 비교하기”는 여러 턴으로 이루어진 한 과제일 수 있다. **실행(trial)**은 동일한 과제를 처음부터 한 번 수행하는 것이다.

이 구분이 없으면 ‘20개 테스트’가 서로 다른 질문 20개인지, 질문 하나를 20회 반복한 것인지 알 수 없다. 전자는 질문 다양성을, 후자는 같은 조건에서의 변동을 주로 보여준다.

### 3.2 평가 과제의 구성

과제 i를 다음 요소로 정의한다.

`Tᵢ = (질문, 이전 대화, 데이터 버전, 기준 시각, 정책, 기대 행동, 정답 근거)`

여기서 정책은 최소 출전 시간, 동률 처리, 시즌 선택, 지원 범위 같은 의미 규칙이다. 정답 근거에는 기준 SQL만 들어가는 것이 아니다. 모호한 질문이라면 확인해야 할 정보가, 미수집 질문이라면 알려야 할 누락 범위가 포함된다.

정답은 하나의 완성 문장보다 **답변이 만족해야 할 조건의 집합**으로 정의하는 편이 적절하다. “A와 B가 공동 1위다”와 “A, B의 수치는 동일하다”는 필요한 문맥과 조건을 충족한다면 모두 허용할 수 있다.

### 3.3 결과와 실행 과정의 관계

결과 평가는 사용자가 받은 정보가 정확한지 확인한다. 과정 평가는 어떤 조회와 계산을 거쳤는지 확인한다. 두 평가는 목적이 다르다. 결과가 틀렸을 때 과정 기록은 원인을 설명하지만, 지정한 도구 순서를 따랐다는 사실만으로 결과가 맞다고 볼 수 없다.

반대로 정확하고 안전한 다른 실행 경로를 사용했다는 이유만으로 실패 처리해서도 안 된다. 과정의 필수 제약은 권한, 읽기 전용 실행, 데이터 범위, 근거 보존처럼 이유가 명확한 항목에 둔다.

## 4. 정확도의 계층적 정의

### 4.1 기대 행동의 정확성

질문에 언제나 수치로 답해야 한다고 가정하면, 자료가 없는 상황에서 숫자를 만드는 모델을 보상하게 된다. 본 문서는 답변 생성 전에 기대 행동을 정의한다.

| 상황 | 기대 행동 | 대표 실패 |
|---|---|---|
| 명확한 질문과 충분한 자료 | 결과 제공 | 다른 시즌·조건으로 대체 |
| 복수의 합리적 해석 | 필요한 정보 확인 | 임의 지표 선택 |
| 조건을 만족하는 행이 없음 | 0건 안내 | 자료 미수집이라고 오인 |
| 자료 미수집·부분 수집 | 누락과 한계 안내 | NULL을 0으로 변환 |
| 미지원 범위 | 지원 한계 설명 | 지원되는 다른 질문에 몰래 답변 |

첫 단계에서 불필요한 확인 질문을 했더라도, 이후 원래 질문에 정확히 답하면 정확한 과제 완료가 가능하다. 이때 확인 질문 횟수는 효율 지표로 남긴다. 그러나 필요한 확인 없이 추측한 답변, 또는 확인만 반복하고 완료하지 못한 과제는 정확한 완료가 아니다.

### 4.2 다섯 정확도 차원

결과를 제공하는 과제는 다음 다섯 차원으로 평가한다.

1. **해석 정확성:** 대상, 대회, 시즌, 필터와 요청 범위를 보존했는가?
2. **데이터 정확성:** 반환 ID, 값, 단위와 순서가 정답에 부합하는가?
3. **계산 정확성:** 집계, 비율, 증감, 동률과 결측 처리가 맞는가?
4. **설명 정확성:** 서술이 실제 결과와 연결되고 과도한 결론을 내리지 않는가?
5. **완결성과 한계:** 질문의 필수 부분에 답하고 필요한 누락·범위를 밝혔는가?

자료 없음 안내에는 일부 차원이 적용되지 않는다. 이 경우 적용 여부를 미리 정하고 ‘해당 없음’으로 기록한다. 응답을 본 뒤 불리한 항목을 제외하지 않는다.

### 4.3 평균 점수보다 필수 조건의 결합을 사용하는 이유

필수 조건 k의 통과 여부를 `gᵢₖ ∈ {0, 1}`로 두고, 과제 i에 적용되는 필수 조건 집합을 `Kᵢ`라고 하자. 과제의 정확한 완료를 다음과 같이 정의한다.

`Sᵢ = 완료 여부 × ∏(k ∈ Kᵢ) gᵢₖ`

즉 완료했고 모든 필수 조건이 맞을 때만 1이다. 올바른 선수 이름, 좋은 문장, 빠른 속도가 잘못된 득점 수치를 상쇄하지 못하게 하는 방식이다. 어떤 조건에서 실패했는지는 별도 항목별 점수로 보존한다.

이 규칙은 모든 문체 차이를 중대 오류로 취급하자는 의미가 아니다. 문장의 자연스러움과 길이는 필수 정확도 조건에서 분리한다. 허용 가능한 소수점 반올림, 동률 순서, 동의 표현 역시 정답 규칙에 먼저 포함한다.

## 5. 축구 데이터로 이해하는 평가 예제

### 5.1 합성 데이터와 정답

아래는 계산을 설명하기 위해 만든 가상 선수 데이터다. 실제 선수 기록이 아니다. 질문은 “시즌 S의 리그 L에서 900분 이상 뛴 선수 중 90분당 득점 상위 2명을 보여줘”다.

| 선수 ID | 선수 | 출전 시간 | 득점 | 90분당 득점 | 자격 |
|---|---|---:|---:|---:|---|
| 101 | 선수 A | 900 | 10 | 1.00 | 충족 |
| 102 | 선수 B | 1,800 | 15 | 0.75 | 충족 |
| 103 | 선수 C | 90 | 3 | 3.00 | 미충족 |
| 104 | 선수 D | 900 | 8 | 0.80 | 충족 |
| 105 | 선수 E | 900 | NULL | 산출 불가 | 지표 결측 |

산식은 `득점 × 90 ÷ 출전 시간`이다. 출전 시간 조건을 먼저 적용하고 득점이 알려진 선수를 비교하면 정답 순서는 A, D다. E의 득점은 0이 아니라 알 수 없는 값이다. 이 예제의 정책은 지표 결측 선수를 순위에서 제외하고 누락을 알리는 것으로 고정한다.

학습용 기준 SQL은 다음과 같다. 실제 프로젝트 테이블과 연결된 코드가 아니며, 선수×리그×시즌당 한 행으로 집계된 자료를 가정한다.

```sql
SELECT player_id, goals * 90.0 / minutes AS goals_per90
FROM player_season_totals
WHERE league_id = :league_id
  AND season_id = :season_id
  AND minutes >= 900
  AND goals IS NOT NULL
ORDER BY goals_per90 DESC, player_id ASC
LIMIT 2;
```

보조 정렬 `player_id ASC`는 예제를 재현하기 위한 정책이다. 실제 서비스에서 공동 순위 표시와 상위 N명 절단을 어떻게 처리할지는 별도로 결정해야 한다.

### 5.2 같은 질문에서 발생하는 서로 다른 오답

| 응답 | 판정 | 실패 원인 |
|---|---|---|
| C, A를 반환 | 오답 | 최소 출전 시간 누락 |
| B, A를 반환 | 오답 | 총득점으로 정렬 |
| A, D와 1.00, 0.80을 반환 | 데이터 항목 통과 | 나머지 설명·한계도 확인 필요 |
| A, D를 반환하고 “도움 효율이 높다”고 설명 | 오답 | 지표 설명 불일치 |
| E의 득점을 0으로 표시 | 오답 | 결측 의미 변경 |
| A, D를 “리그 최고의 공격수”라고 단정 | 오답 | 측정 지표를 넘어선 결론 |

이 예제는 수치 비교와 설명 비교를 동시에 해야 하는 이유를 보여준다. 표가 정확하더라도 최종 답변 전체는 틀릴 수 있다.

### 5.3 우연한 결과 일치를 잡는 방법

시험 데이터에 C가 없다면 최소 출전 조건을 빠뜨린 SQL도 우연히 A, D를 반환할 수 있다. 이 한 번의 실행만으로는 필터 오류를 발견하지 못한다. C처럼 출전 시간이 짧지만 비율이 높은 선수를 추가하면 잘못된 SQL의 결과가 달라진다.

이는 오류를 드러내도록 데이터를 설계하는 예다. 899분·900분·901분을 가진 선수를 두면 `>`와 `>=`의 차이를 검사할 수 있다. 같은 시즌에 두 팀 기록이 있는 선수는 집계 누락이나 중복을 드러낸다. 동률 선수는 보조 정렬과 공동 순위 정책을 검증한다. 이러한 작은 시험 데이터는 실제 snapshot을 대체하지 않고 보완한다.

## 6. 신뢰할 수 있는 평가 세트 제작

### 6.1 정답 역시 검증 대상이다

정답 데이터, 즉 ground truth는 자동으로 진실이 되는 것이 아니다. 기준 SQL이 시즌 필터를 잘못 적용하면 올바른 시스템을 오답으로 평가할 수 있다. 따라서 질문의 의미 규칙을 먼저 합의하고, 기준 SQL을 원천 행과 대조하며, 작은 사례는 직접 계산해야 한다.

가능하면 정답 작성자와 검토자를 나눈다. 한 사람이 작업한다면 작성과 검토를 시간적으로 분리하고, 다른 계산 방식으로 확인한 기록을 남긴다. LLM은 질문이나 SQL의 초안을 만들 수 있지만 그 출력이 검수 없이 기준답이 되지는 않는다.

### 6.2 시험 데이터의 두 종류

실제 데이터 snapshot은 현실적인 이름, 분포와 누락을 보여준다. 반면 작은 합성 fixture는 특정 오류를 확실하게 드러내기 좋다. 실제 자료만 사용하면 드문 경계 사례가 빠질 수 있고, 합성 자료만 사용하면 현실의 복잡성을 과소평가할 수 있다.

따라서 평가 세트는 실제 질문 기반 문제와 경계 조건 문제를 함께 갖되 결과를 나눠 보고한다. 현재 사용자 트래픽을 대표하는 점수와 어려운 사례를 균등하게 넣은 진단 점수는 같은 의미가 아니다.

### 6.3 개발·검증·독립 평가의 분리

개발 세트는 실패를 보고 수정하기 위한 자료다. 검증 세트는 후보 설정을 선택하는 데 사용한다. 독립 평가 세트는 선택된 설정의 성능을 확인하는 데 사용한다. 비용이 제한된 초기 단계에서는 개발 세트와 별도로 보관하는 평가 세트부터 시작할 수 있다.

중요한 것은 파일 이름보다 사용 방식이다. 독립 문제의 정답을 보고 프롬프트를 고쳤다면 그 문제는 더 이상 새로운 문제를 대표하지 않는다. 이후에는 회귀 사례로 보존하고 독립 평가를 보강한다. 같은 질문의 한국어 표현 변형이나 동일 집계 구조의 유사 문제는 묶음 단위로 분리해 누출을 줄인다.

### 6.4 재현을 위한 최소 기록

각 과제에는 ID, 질문, 기준 날짜·시간대, 데이터 버전, 정책 버전, 기대 행동, 필수 조건, 정답 근거, 허용 오차, 검수 이력을 저장한다. 실행에는 코드·모델·프롬프트·사전·채점기 버전과 오류 상태를 연결한다. ‘지난 시즌’처럼 상대적인 표현은 기준 시각을 고정하지 않으면 시간이 흐른 뒤 다른 문제가 된다.

## 7. 채점기와 대화 평가의 설계

### 7.1 코드, LLM, 사람의 역할

코드 채점은 ID, 값, 조건, 집합과 순서를 재현 가능하게 비교하는 데 적합하다. 순위 질문에서는 순서를 검사하지만 순서가 중요하지 않은 목록에서는 집합 또는 중복을 보존한 다중집합 비교를 사용한다. 수치 오차는 표시 자릿수에 맞춰 미리 정하고, 큰 차이를 통과시키는 임의의 허용치를 두지 않는다.

LLM 보조 채점은 설명이 질문에 답하는지, 근거보다 강한 주장을 하는지처럼 의미 해석이 필요한 항목에 사용할 수 있다. 입력에는 질문, 허용된 근거, 평가 기준, 후보 답변을 제공하고, 항목별 판정과 근거 문장을 반환하게 한다. 평가 대상 답변 안의 지시문은 채점 지시로 취급하지 않게 분리한다. 모델 판정도 오류 가능성이 있으므로 최종 진실로 간주하지 않는다.

사람은 정답과 정책을 검수하고, 자동 채점이 불확실하거나 서로 충돌한 사례를 판정한다. 사람 간 불일치는 단순히 다수결로 숨기기보다 문항이나 채점 규칙이 모호한지 확인하는 신호로 사용한다.

### 7.2 채점기 자체를 시험하는 방법

정답 답변을 준비한 뒤 선수 ID 교체, 시즌 변경, 숫자 수정, 조건 제거, NULL의 0 변환, 과도한 결론 추가와 같은 변형을 만든다. 채점기가 이 오답들을 탈락시키는지 확인한다. 동시에 의미가 같은 문장 순서 변경이나 허용된 반올림은 통과해야 한다.

이를 통해 오답을 정답으로 인정하는 오류와 정답을 오답으로 배제하는 오류를 모두 검사한다. 특히 LLM 채점기는 사람이 판정한 표본과 비교하고, 모델이나 채점 프롬프트를 바꿀 때 다시 확인한다.

### 7.3 대화에서는 두 가지 정답을 구별한다

첫 턴에 순위를 보여주고 다음 턴에 “그중 상위 두 명을 비교해줘”라는 질문을 받았다고 하자. 여기에는 앞선 응답의 두 사람을 정확히 참조하는 문제와, 앞선 순위 자체가 맞는지를 확인하는 문제가 공존한다.

첫 순위가 틀렸어도 같은 두 명을 유지했다면 참조 보존 검사는 통과할 수 있다. 그러나 대화 전체는 통과하지 못한다. 따라서 실제 대화를 끝까지 실행하는 평가와, 정확한 이전 대화를 주입해 후속 턴만 검사하는 진단 평가를 병행한다. 후자는 앞 단계 오류를 분리하는 용도이며 전체 성공률에 섞지 않는다.

모호한 질문에는 평가용 사용자 응답 규칙을 준비한다. 예를 들어 시즌을 물으면 S, 효율 지표를 물으면 per90이라고 답하도록 정한다. 사용자 역할을 수행하는 별도 모델을 쓰는 경우 그 모델의 변동과 오류도 추가되므로, 초기에는 명시된 분기 규칙이 해석하기 쉽다.

### 7.4 사용자 제공 보고서의 멀티턴 시나리오 반영

사용자 제공 보고서 [7, 2~3쪽]는 대화를 일곱 가지 흐름으로 나눈다. 이 분류를 채택하되, 각각의 질문이 실제로 답변 가능한지와 지시 대상이 하나로 정해지는지를 먼저 검토한다. 아래는 원문 시나리오의 요약과 본 문서의 보완이다.

| 시나리오 | 검증할 능력 | 평가 전 정해야 할 조건 |
|---|---|---|
| 순위 → 개인 선택 → 폼 비교 → 과거 1위 재참조 | 순위 지시, 대명사, 과거 결과 복원 | 표시 행과 공동 순위 구별, 폼 정의, xG·득점 상황 자료 가용성 |
| 도움 순위 → 미드필더 → 25세 이하 → 빅6 제외 → 이적료 정렬 | 조건 누적과 정렬 변경 | 나이 기준일, 빅6 목록, 이적료 단위·시점·결측 |
| 라리가 → PK 제외 → PK 복원·세리에A 전환 → 과거 라리가 3위 | 부분 수정·되돌리기·과거 참조 | PK 집계 정의, 대회 수집 여부, 원래 결과의 식별자 |
| 팀 → 경기 → 득점자 → 선수 부재 경기의 팀 성적 | 엔티티 종류 전환 | 여러 경기·득점자 중 선택, 부재의 정의와 관측 가능성 |
| 폼 좋은 선수 → 수비수 → 태클·인터셉트 → 최근 10경기 | 모호함 구체화와 지표·기간 변경 | 초기 해석의 승인 여부, 두 지표의 결합 방식, 팀 경기와 선수 출전 경기 구별 |
| 선수 기록 → 같은 나이의 다른 선수 → 비교 대상 추가·제거 | 비교 범위와 대상 집합 관리 | 나이 기준일, 역사 자료 보관 범위, 헤더 골 지표 가용성 |
| 이름 정정 → 미지원 지표 → 대안 요청 | 정정 수용, 확인, 지원 한계 | 동명이인 시험 데이터, 대안과 원래 지표의 차이 명시 |

이 시나리오는 기능 지원 목록이 아니다. 최신 2시즌만 보관하는 서비스에서 오래전 동일 나이의 기록 비교는 필요한 자료가 없을 수 있다. 그 경우 정확한 한계 안내가 기대 행동이다. xG, 전진 패스, 압박, 이적료가 실제 DB에 있는지는 별도 확인해야 한다.

각 시나리오는 두 갈래로 만든다. 하나는 데이터와 대상이 명확해 끝까지 결과를 얻을 수 있는 정상 흐름이다. 다른 하나는 동률·여러 득점자·지표 미수집처럼 확인이나 한계 안내가 필요한 흐름이다. 초반부터 미지원 자료 때문에 모든 대화가 중단되면 후반의 문맥 유지 능력을 측정할 수 없기 때문이다.

원문의 ‘4턴쯤에서 조건을 잃는 실패가 흔하다’, ‘대부분의 도구가 조건 누적·수정에서 실패하기 쉽다’는 서술에는 비교 실험 근거가 제시되지 않았다. 따라서 본 문서는 이를 **우선 검증할 가설**로 취급한다. 초기에는 해당 시나리오를 충분히 포함하되 실제 실패 분석 없이 빈도나 우월성을 단정하지 않는다.

### 7.5 대화 상태는 값뿐 아니라 변경 연산으로 검증한다

현재 상태를 `B(t)`, 사용자 요청에 따른 변경을 `Δ(t)`라고 하면, 기대 상태는 `B(t) = apply(B(t-1), Δ(t))`로 표현할 수 있다. 상태에는 대상 ID, 대회, 시즌, 기간, 필터, 지표, 정렬, 표시 개수와 참조한 과거 결과가 들어간다. 이는 평가용 의미 표현이며 모델에 동일한 내부 구조를 강제하는 제안은 아니다.

변경은 추가(add), 교체(replace), 제거(remove), 유지(preserve), 과거 참조(refer), 초기화(reset)로 구분한다. ‘PK를 다시 포함하고 리그만 바꿔줘’에서는 PK 제외 조건을 제거하고 대회를 교체하되 나머지를 보존해야 한다. ‘아까 라리가 결과’는 최신 상태를 라리가로 바꿔 재조회하는 것과 같지 않을 수 있다. 평가 과제에 원래 결과 ID·행·시점을 남겨야 한다.

| 턴 | 입력 | 기대 상태 변화 | 보존해야 할 조건 |
|---|---|---|---|
| 1 | 시즌 S, 리그 L 도움 순위 | 범위와 지표 설정 | 없음 |
| 2 | 미드필더만 | 포지션 필터 추가 | 시즌·리그·도움 |
| 3 | 25세 이하 | 나이 필터 추가 | 기존 범위·포지션 |
| 4 | 빅6 제외 | 팀 제외 조건 추가 | 기존 범위·포지션·나이 |
| 5 | 나이 조건만 빼줘 | 나이 필터 제거 | 시즌·리그·포지션·빅6 제외 |

마지막 턴에서는 나이 조건을 보존하면 오답이다. 따라서 ‘조건 유지율’은 모든 과거 조건의 유지율이 아니라 **이번 요청에서 유지하도록 기대된 조건의 보존율**로 정의한다. 삭제·교체 성공률도 별도로 측정해야 조건을 무조건 남기는 시스템이 높은 점수를 받지 않는다.

### 7.6 모호한 질문의 정답은 해석별 조건과 결과를 묶는다

원문 데이터 예시는 `acceptable_interpretations: 2`와 승자 한 명을 저장한다. 그러나 허용 해석의 개수만으로는 무엇이 허용되는지 판정할 수 없다. 득점과 도움의 가중치가 정해지지 않으면 ‘폼이 더 좋은 선수’의 단일 승자를 고정하기도 어렵다. [7, 4쪽]

보완된 정답은 해석별로 기간·지표·필터·집계 규칙·기대 결과·필수 설명을 묶은 목록이다. 채점 시 그중 **하나의 완전한 해석 묶음**을 만족하는지 확인한다. 한 해석의 기간, 다른 해석의 지표, 세 번째 해석의 승자를 섞어 통과시키지 않는다. 정답 결과는 승인된 해석마다 별도로 계산한다.

정책은 세 가지로 구분할 수 있다. ‘확인 필수’는 사용자 선택 없이는 답을 확정하지 않는다. ‘명시된 가정 허용’은 허용된 기준을 먼저 밝히고 그 기준의 결과만 제공할 수 있다. ‘기존 승인 기준 재사용’은 이전에 사용자가 선택한 기준을 이어받는다. 단지 임의의 기준을 공개했다는 이유만으로 합리적인 해석이 되는 것은 아니다.

예를 들어 ‘태클과 인터셉트 기준으로 비교’에는 두 수치를 나란히 보여주는 행동이 허용될 수 있다. 우승자 한 명을 고르려면 합계, per90, 가중 점수 중 무엇을 사용할지 추가 기준이 필요하다. 그 기준 없이 승자를 선언하는 행동은 평가에서 제외하지 않고 오류로 기록한다.

### 7.7 전체 대화, 정답 문맥 주입, 오류 회복을 분리한다

원문은 실제 히스토리로 이어가는 End-to-end와 정답 히스토리를 주입하는 Teacher forcing을 구별한다. [7, 5쪽] 본 문서에서는 후자를 모델 학습 기법과 혼동하지 않도록 **정답 문맥 주입 평가(oracle-history evaluation)**라고 부른다. 정답 문맥에는 사용자 발화뿐 아니라 이전 답변의 ID·값·표·선택 상태가 필요하다.

두 방식의 차이가 크면 앞선 오류나 문맥 처리의 영향을 의심할 수 있지만, 그것만으로 회복 불능의 원인을 확정할 수는 없다. 히스토리의 길이·표현·누락, 제공자 오류, 모델 변동 등이 함께 작용할 수 있기 때문이다. 가능한 한 형식과 실행 조건을 맞추고, 어느 턴의 어떤 상태가 달랐는지 비교한다.

회복 능력은 별도 시험으로 측정한다. 잘못 연결된 선수나 누락된 필터를 포함한 동일한 초기 상태를 만들고, 사용자가 ‘그 선수가 아니라 B’ 또는 ‘25세 이하 조건을 유지해줘’라고 정정하게 한다. 이후 정정한 조건을 반영하고 영향을 받지 않는 조건을 보존하는지 확인한다. 이 점수를 정상 흐름의 성공률과 섞지 않으면 문맥 이해와 오류 회복을 구분할 수 있다.

## 8. 지표와 실험 설계

### 8.1 대표 지표와 보조 지표

N개 과제의 정확한 완료 여부를 Sᵢ라고 할 때 대표 지표는 다음과 같다.

`정확한 과제 완료율 = (Σ Sᵢ) / N`

필요한 확인을 거쳐 정답을 제공하거나, 자료가 없는 과제에서 기대한 한계 설명을 정확히 완료한 경우도 성공이 될 수 있다. 제공자 오류와 시간초과는 의미 오답으로 이름 붙이지 않지만 과제 완료율에서는 실패다. 정상 응답만 대상으로 한 내용 정확도를 별도로 보고할 수 있으나 전체 완료율을 대신하지 않는다.

| 지표 | 계산 단위 | 용도 |
|---|---|---|
| 정확한 과제 완료율 | 전체 과제 | 대표 품질 판단 |
| 결과 답변 정답률 | 실제로 결과를 제공한 답변 | 잘못된 답변의 노출 확인 |
| 기대 행동 일치율 | 사전에 정한 턴 또는 과제 | 확인·결과·한계 안내 판단 |
| 대화 전체 통과율 | 다중 턴 과제 | 문맥 누적 오류 확인 |
| 항목별 실패율 | 해석·데이터·계산·설명·완결성 | 개선 위치 진단 |

결과 답변 정답률의 분모가 0이면 100%가 아니라 산출 불가로 기록한다. 어려운 문제를 모두 거절해 높은 정답률을 만드는 것을 막기 위해 완료율과 함께 해석한다.

### 8.2 반복 실행과 표본 수

동일 문항을 여러 번 실행하면 결과의 안정성을 확인할 수 있다. 예를 들어 같은 과제를 5회 실행해 3회 통과했다면 해당 과제의 관측 성공률은 3/5다. 이것을 서로 다른 질문 5개에 대한 일반화 성능으로 설명해서는 안 된다.

여러 번 중 한 번이라도 맞힌 비율은 ‘여러 시도 안에 성공할 가능성’을 평가한다. 한 번의 실제 사용자 요청이 성공할 확률과는 다르다. 서비스가 재시도 후 답변을 선택하는 기능을 제공하지 않는다면 최선의 결과만 골라 대표 정확도로 보고하지 않는다.

초기에는 여섯 질문군의 약 60개 과제로 시작할 수 있지만 이는 운영 제안이지 통계적 충분성을 보장하는 수치가 아니다. 반복 횟수와 문제 수는 평가 비용 및 발견된 실패 유형에 따라 늘린다. 문항 수, 반복 수, 성공 건수를 항상 함께 보고한다.

### 8.3 비교 실험과 불확실성

버전 A와 B를 비교할 때는 같은 데이터와 같은 문제를 사용하고, 모델 설정 및 실행 조건을 기록한다. A만 맞힌 과제, B만 맞힌 과제, 둘 다 맞힌 과제, 둘 다 틀린 과제를 나누면 총점만 볼 때 놓치는 퇴행을 발견할 수 있다.

다음 표는 설명용 가상 결과다.

| | B 정답 | B 실패 |
|---|---:|---:|
| A 정답 | 45 | 3 |
| A 실패 | 7 | 5 |

전체 60개에서 A는 48개, B는 52개를 맞혔다. B의 총점은 높지만 기존에 맞히던 3개를 잃었다. 그 3개가 잘못된 선수 선택이나 수치 조작이라면 평균 상승만으로 개선을 승인하기 어렵다.

표본이 작거나 질문이 유사하면 몇 건 차이로 비율이 크게 움직인다. 충분한 표본이 확보되면 신뢰구간을 함께 산출하되, 표현 변형과 반복 실행의 상관을 고려해 원래 과제군 단위로 재표집하는 방법을 검토할 수 있다. 어떤 방법을 쓰든 평가 세트가 실제 사용을 얼마나 대표하는지까지 자동 보장하지는 않는다.

### 8.4 정확도 확보 이후의 성능 개선

초기 실험에서도 시간, 재질문, 호출 수, 비용은 기록한다. 다만 정확도와 가중 합산해 빠른 오답을 보상하지 않는다. 이후 정확도 기준을 충족한 후보들 사이에서 지연과 비용을 비교한다.

예를 들어 최소 출전 시간을 묻는 질문을 제거하면 빨라질 수 있지만, 근거 없이 임계값을 선택한다면 정확도 퇴행이다. 반대로 사용자가 이미 말한 조건을 다시 묻지 않도록 개선하고 같은 정답을 유지했다면 정확도와 효율을 함께 개선한 것이다. 필수 안전 제한과 무한 반복 방지 예산은 정확도 우선 단계에서도 유지한다.

### 8.5 단계별 진단 지표의 정확한 사용법

첨부 보고서의 Slot F1, 엔티티 연결, 실행 결과, 근거 충실성, 상태 유지 지표를 보조 지표로 도입한다. [7, 4~5쪽] 전체 과제의 정확한 완료가 대표 기준이라는 원칙은 유지한다.

**슬롯 F1.** 슬롯은 `(지표, 도움)`, `(시즌, S)`, `(나이, ≤25)`처럼 정규화된 의미 항목이다. 예측 항목 집합 P와 정답 집합 G에 대해 precision은 ‘예측한 항목 중 맞은 비율’, recall은 ‘필요한 항목 중 맞힌 비율’이다. `F1 = 2PR / (P + R)`에서 P와 R은 각각 이 두 비율을 뜻한다. 집합 기호와 비율 기호를 혼동하지 않도록 구현에서는 별도 이름을 사용한다.

리그·시즌 등 필수 슬롯의 누락은 F1이 높아도 최종 정답 실패다. 예를 들어 슬롯 10개 중 필터 한 개를 놓치면 precision 1, recall 0.9, F1 약 0.947이지만 결과 대상은 달라질 수 있다. 따라서 슬롯별 점수와 전체 상태 완전 일치를 함께 보고한다. 빈 집합의 분모 처리와 micro/macro 집계 방식은 실행 전 고정한다. 비적용 사례는 임의의 100점으로 채우지 않는다.

**엔티티 연결과 지시어 해소.** 명확한 대상은 정확한 내부 ID와 종류를 비교한다. 모호한 대상은 후보 집합과 확인 행동을 비교한다. ‘2등’은 표시 행 2번째와 공동 순위의 2위를 구분하고, ‘그 선수’가 여러 명일 수 있는 사례를 포함한다. 이름만 일치해도 다른 선수 ID라면 실패다.

**근거 충실성(Faithfulness).** 숫자와 이름의 출현 여부만 확인하지 않는다. `(선수 ID, 지표, 대회, 시즌/기간, 값, 단위)`의 연결과 비교 방향을 검사한다. ‘A 10골, B 8골’인 표를 보고 ‘B가 A보다 2골 많다’고 설명하면 모든 숫자가 근거에 있어도 오답이다. 또한 잘못 조회된 표를 충실하게 설명한 경우 충실성은 통과할 수 있지만 독립 정답 대비 정확성은 실패한다.

**되묻기 precision/recall.** 확인 필수 사례에서 실제 확인하면 TP, 확인 필수인데 임의 답변하면 FN, 직접 답변이 요구되는 명확한 사례에서 불필요하게 물으면 FP다. `precision = TP/(TP+FP)`, `recall = TP/(TP+FN)`으로 계산한다. 질문 내용이 빠진 정보를 실제로 해결하는지도 확인해야 한다. ‘질문을 더 자세히 해주세요’라는 일반 문장만 출력했다고 자동으로 TP가 되지는 않는다. 확인과 명시적 가정이 모두 허용되는 사례는 강제 이진 분류에서 분리해 정책 적합성을 채점한다. 초기에는 recall과 위험한 추측을 우선 보고, 불필요한 확인은 효율 개선 대상으로 기록한다.

**기준 명시율과 한계 안내.** 기준 명시율은 필요한 사례 중 지표·기간·필터를 충분히 공개한 비율이다. 기준의 타당성은 별도로 판정한다. 예측·미존재 자료·미지원 지표를 모두 ‘거절’로 묶지 않고, 범위별 기대 안내와 근거 없는 대체 여부를 확인한다. 사용자가 대안을 요청하면 차이를 밝힌 대안을 제시할 수 있지만 같은 지표인 것처럼 바꾸면 실패다.

### 8.6 결과 비교와 오류 분석의 보완

| 결과 유형 | 최종 정답 판정 | 보조 진단 |
|---|---|---|
| 정수·단일 값 | 값·대상·단위 완전 일치 | 차이 크기 |
| 비율·xG 등 실수 | 정의·정밀도별 사전 허용 오차 | 절대/상대 오차 |
| 정확한 통계 순위 | ID·값·정렬 및 동률 정책 일치 | 상위 항목 누락·위치 오류 |
| 필터 결과 목록 | 기대 집합 또는 중복을 보존한 결과 일치 | 집합 precision/recall |
| 설명·해석 | 필수 주장·근거 연결·한계 충족 | 주장별 충실성 |

원문이 제시한 ±0.01은 예시이며 모든 지표의 공통 오차로 사용하지 않는다. NDCG@k는 관련성 등급이 정의된 추천·검색의 순위 품질을 요약할 때 유용하지만, 정확한 득점 순위를 요구하는 문항의 완전 일치를 대체하지 않는다. 일부 순서가 틀려도 높은 점수가 나올 수 있기 때문이다. 공동 순위와 상위 N명 경계는 허용 정책을 먼저 정한다.

태그별 교차표는 채택하되 단일 지표 조합으로 원인을 확정하지 않는다. Slot F1이 높고 실행 정확도가 낮으면 SQL뿐 아니라 핵심 슬롯 누락, 데이터 버전, 정답 오류, 집계 규칙도 확인한다. 실행 정확도가 높고 충실성이 낮으면 설명 생성 외에 결과 직렬화·셀 참조 연결도 점검한다. 지표는 조사할 위치를 좁히는 증거이며 원인을 자동 증명하지 않는다.

## 9. 프로젝트 적용 절차와 검증 가능한 가설

첫째, 시즌·동률·누락·다중 소속의 의미 규칙을 정한다. 둘째, 실제 데이터와 작은 경계 데이터를 준비하고 정답을 검수한다. 셋째, 의도적으로 틀린 답변으로 채점기를 시험한다. 넷째, 현재 서비스의 실제 실행 경로를 연결하고 개발 평가를 수행한다. 다섯째, 수정에 사용하지 않은 독립 문제로 확인한다. 마지막으로 정확도 회귀 평가를 유지하면서 시간과 재질문을 줄인다.

이 순서에서 검증할 수 있는 가설은 다음과 같다. 아래는 실험으로 확인해야 할 제안이며 입증된 결과가 아니다.

| 가설 | 비교 방법 | 확인할 결과 |
|---|---|---|
| 독립 결과 채점은 상태 검사만으로 놓친 오류를 찾는다 | 같은 응답에 두 채점 방식 적용 | 수치·순위 오류 추가 탐지 |
| 경계 데이터는 우연히 통과한 쿼리를 구별한다 | 실제 snapshot과 경계 fixture 비교 | 조건 누락·집계 오류 발견 |
| 정확한 문맥 주입은 오류 원인 분리에 도움이 된다 | 전체 대화와 후속 턴 단독 평가 | 초기 오류와 후속 해석 오류 분리 |
| 설명 채점은 표가 맞아도 발생하는 오답을 찾는다 | 표 채점과 설명 채점 병행 | 지표 오인·과도한 결론 발견 |

2026-10-26의 선행 조사에서 기존 프로젝트 계획은 이러한 원칙 상당수를 이미 포함했다. 다만 당시 확인한 대화 실행기는 이전 검색 경로를 사용했고, 최종 수치·순위를 독립 정답과 비교하는 범위가 부족했다. 이는 당시 파일을 검토한 결과이며 2026-10-27의 최신 구현 상태를 재검증한 주장으로 읽어서는 안 된다. 구체적인 검토 근거는 선행 보고서에 보존되어 있다.

## 10. 타당성의 위협과 한계

**정답 오류:** 잘못된 기준 SQL이나 모호한 정책은 평가 전체를 왜곡한다. 원천 행 검토와 채점기 시험이 필요하다.

**표본 편향:** 개발자가 쉽게 생각한 질문만 모으면 실제 사용자 표현과 새로운 조합을 과소평가한다. 실제 사용에서 발견한 실패를 지속적으로 추가하되 독립 평가의 역할을 보존해야 한다.

**평가 누출:** 같은 의미의 문제를 예시와 시험에 나누면 새로운 질문을 해결하는 능력이 과대평가될 수 있다. 그룹 단위 분리가 필요하다.

**데이터 변화:** 데이터가 갱신되면 정답이 달라질 수 있다. 자료 시점을 고정한 비교와 실제 운영 관찰을 구분해야 한다.

**채점 편향:** LLM과 사람 모두 그럴듯한 문장에 영향을 받을 수 있다. 검증 가능한 수치를 먼저 비교하고 판정 근거를 기록해야 한다.

**환경 차이:** 테스트 대역이나 이전 구현의 통과는 현재 모델·실제 서비스 경로의 통과를 의미하지 않는다. 평가 대상의 버전과 연결 경로를 명시해야 한다.

**공개 사례의 재현 한계:** 기업 글은 내부 데이터와 평가 세부사항을 모두 공개하지 않을 수 있다. 본 문서는 이 자료를 방법 설계의 참고 근거로 사용하며 각 회사의 성능 우위를 독립 입증하지 않는다.

## 11. 결론

자연어 검색 에이전트의 정확도는 실행 성공이나 문장의 자연스러움으로 충분히 설명되지 않는다. 사용자의 의도, 데이터와 계산, 설명, 대화 문맥, 자료의 한계를 함께 검증해야 한다. 이를 위해 정답을 조건의 집합으로 정의하고, 독립적인 기준 결과와 대조하며, 필수 조건을 모두 충족한 과제를 정확한 완료로 판정하는 체계를 제안했다.

정확도 평가는 모델에 점수를 붙이는 절차인 동시에 제품이 어떤 상황에서 무엇을 해야 하는지 명확히 하는 설계 과정이다. 이 기준이 안정된 뒤 시간·재질문·비용을 개선하면, 시스템이 빨라지는 과정에서 답변의 의미가 손상되는지 확인할 수 있다. 본 문서는 그 평가 체계의 설계안을 제시했으며 실제 정확도 향상에 대한 결론은 후속 실험을 통해 확인해야 한다.

## 부록 B. 이해 확인 문제

1. SQL이 정상 실행됐는데도 답변이 틀릴 수 있는 이유를 두 가지 설명하라.
2. 최소 출전 시간 필터를 빠뜨린 SQL이 통과하지 못하도록 어떤 데이터를 추가할 수 있는가?
3. 첫 순위가 틀렸지만 후속 질문에서 같은 선수들을 유지했다면 무엇은 통과하고 무엇은 실패하는가?
4. 결과를 제공한 10건이 모두 맞고 나머지 90건은 불필요하게 거절했다면, 결과 답변 정답률만으로 평가할 때 어떤 문제가 생기는가?
5. 같은 질문을 100번 반복하는 것과 다른 질문 100개를 실행하는 것은 무엇이 다른가?
6. 불필요한 재질문을 줄이는 변경이 정확도를 손상시키지 않았는지 어떻게 확인할 것인가?

### 해설

1. 잘못된 시즌이나 조건으로 조회할 수 있고, 올바른 수치를 다른 지표의 값으로 설명할 수도 있다.
2. 최소 시간보다 적게 뛰었으나 per90 값이 높은 선수를 추가한다. 임계값 바로 전후의 기록도 비교한다.
3. 이전 응답에 대한 참조 보존은 통과할 수 있지만 최초 결과 정답과 대화 전체 성공은 실패한다.
4. 답변 정답률은 100%지만, 100개 모두 답할 수 있었던 과제라면 정확한 완료율은 10%에 그친다.
5. 반복은 특정 문제의 변동을, 다양한 질문은 문제 범위에 대한 대응 능력을 주로 보여준다.
6. 같은 정확도 평가에서 조건·지표·범위가 유지되는지 확인하고, 모호한 질문을 임의 해석하는 실패가 늘지 않았는지 별도로 검사한다.

### C.2 한 문항의 정답 기록 예

다음은 값이 확인된 가상 상태를 사용하는 명세 예시이며, 실제 DB의 기록을 의미하지 않는다.

| 항목 | 예시 |
|---|---|
| 문항 ID | MT-FILTER-05 |
| 이전 상태 | 리그 L, 시즌 S, 도움 내림차순, 미드필더, 25세 이하, 빅6 제외 |
| 사용자 질문 | 나이 조건만 빼고 다시 보여줘 |
| 기대 연산 | 나이 조건 제거; 나머지 조건 유지 |
| 기대 행동 | 저장 자료가 충분하면 결과 제공 |
| 결과 정답 | 고정 fixture에서 나이 조건을 제외한 기준 SQL의 ID·도움·순서 |
| 설명 조건 | 나이 제한만 해제했다는 설명, 나머지 범위의 모순 없음 |
| 금지 행동 | 포지션이나 팀 제외 조건까지 제거, 과거 시즌으로 전환 |
| 보조 지표 | 제거 성공, 유지 대상 조건 보존, 슬롯 F1, 상태 완전 일치 |
| 최종 판정 | 정답 결과·설명·조건을 모두 충족하면 통과 |

### C.3 추가 학습 문제와 해설

**문제 1.** 필수 조건 10개 중 시즌만 틀려 슬롯 점수가 높게 나왔다. 최종 정답으로 인정할 수 있는가?

**해설:** 인정할 수 없다. 슬롯 점수는 부분 진단이고, 시즌은 결과 의미를 바꾸는 필수 조건이다.

**문제 2.** 전체 대화 점수는 낮고 정답 문맥 주입 점수는 높다. 시스템이 오류에서 회복하지 못한다고 결론 내릴 수 있는가?

**해설:** 앞선 오류 또는 문맥의 영향을 의심할 수 있지만 원인을 확정하지 못한다. 정정 입력을 가진 회복 실험과 동일 조건의 실행 기록 비교가 필요하다.

**문제 3.** ‘폼’을 득점과 도움으로 해석한다고 밝히면 항상 정확한가?

**해설:** 아니다. 허용 정책과 사용자 문맥에 맞아야 하고, 기간·최소 출전·지표 결합도 정해야 한다. 기준 명시와 기준 타당성은 별도다.
