## 1. 조사 목적과 결론

이 보고서는 자연어 질문을 해석해 DB를 조회하고 답변을 생성하는 AX 기능의 평가 방법을 조사하고, 축구 검색 프로젝트에 적용할 정확도 평가 체계를 제안한다. 사용자가 정한 순서는 **답변 정확도 확보 → 정확도를 유지하면서 시간·재질문·비용 개선**이다.

조사 결과, 가장 직접적인 참고 사례는 Databricks Genie, Uber QueryGPT, Snowflake Cortex Analyst다. 공통적으로 사람이 검증한 질문과 정답을 준비하고, 변경 전후 결과를 반복 비교한다. 다만 SQL 결과 비교, 단계별 진단, 최종 과제 평가의 범위는 사례마다 다르다. 따라서 한 회사의 정확도 수치나 채점 방식을 그대로 채택하지 않고 다음을 결합하는 것이 적절하다.

1. 검수된 정답과 실제 반환 ID·수치·순서를 비교한다.
2. 이름·조건 해석, 조회, 계산, 설명의 오류를 분리한다.
3. 재질문·자료 없음·미지원 안내도 기대 행동으로 평가한다.
4. 개별 턴뿐 아니라 대화가 최종 과제를 정확히 해결했는지 판정한다.
5. 개발용 예시와 독립 평가 문제를 분리하고, 기준 데이터와 채점 규칙을 고정한다.

이 다섯 항목은 조사 자료를 종합한 **프로젝트 적용 제안**이며, 특정 회사가 동일한 방식으로 운영한다고 주장하는 것은 아니다.

## 3. 기업 사례별 평가 방식

### 3.1 Databricks Genie: 정답 SQL의 결과와 비교

공식 글은 자주 묻는 질문과 표현 변형을 벤치마크에 넣고, 각 질문을 정확하게 답하는 SQL을 연결하는 방법을 설명한다. 생성 쿼리의 결과가 기준 쿼리 결과와 일치하면 Correct로 분류하고, 개선 후 같은 벤치마크를 다시 실행한다. 사용자 요청에 따라 관리자가 SQL을 검토·수정하는 절차도 제공한다. [S1]

**적용 제안:** 축구 질문별로 검토한 기준 SQL과 기대 결과를 만들고, 프롬프트·사전 변경 전후 결과를 비교한다.

**적용 한계:** SQL 결과가 맞는 것만으로 최종 한국어 설명과 대화 전체가 정확하다고 볼 수 없다. 선수·시즌·지표를 설명에서 잘못 연결하는 오류는 별도 채점한다. 표현 변형은 같은 질문군으로 관리해 개발용과 독립 평가용에 나뉘어 들어가지 않게 한다.

### 3.2 Uber QueryGPT: 전체 평가와 구성 요소 평가 분리

Uber는 실제 사용 로그에서 질문을 선택하고, 의도·필요 스키마·정답 SQL을 사람이 검수했다. 질문만 입력하는 전체 흐름과, 정확한 의도·데이터셋을 제공해 앞 단계 오류의 영향을 줄이는 분리 평가를 운영한다. 의도, 테이블 선택, 실행 성공, 결과 유무, LLM이 평가하는 SQL 유사성을 각각 관측한다. 실행 간 변동과 복수의 유효 SQL이 존재할 수 있다는 한계도 설명한다. [S2]

**적용 제안:** 최종 답변 정확도를 대표 지표로 두되 이름 해석·조건 해석·SQL·계산·설명은 원인 진단용으로 분리한다. 예를 들어 올바른 선수 ID를 주입했을 때 결과가 맞는지 확인하면 이름 해석 오류와 이후 오류를 구별할 수 있다.

**적용 한계:** 결과 유무와 SQL 유사성은 보조 신호다. 조건에 맞는 선수가 실제로 없으면 0건이 정답이다. 정답 SQL과 유사해도 시즌이나 필터 하나가 틀리면 결과는 오답이다.

### 3.3 Snowflake Cortex Analyst: 평가 누출·회귀·버전 관리

공식 문서는 검증된 질문·SQL을 평가 정답으로 사용하고 생성 결과를 비교하는 방식을 설명한다. 평가에 선택한 검증 쿼리는 임시 의미 모델에서 제거해 동일 예시를 그대로 참고하는 것을 방지한다. 이전에 맞았지만 현재 틀린 사례를 회귀로 추적하며 채점 기준 버전을 고정할 수 있다. 또한 다중 턴 평가 미지원과 상대 날짜에 따른 정답 변화 가능성을 명시한다. [S3]

**적용 제안:** 데이터 snapshot, 기준 날짜, 사전·프롬프트·모델·채점기 버전을 실행 기록에 남긴다. 독립 평가 문제를 보고 프롬프트를 수정했다면 그 문제는 개발 회귀군으로 옮기고 새로운 독립 문제를 보강한다.

**적용 한계:** 이 제품의 평가 기능만으로 우리 대화형 검색을 검증할 수는 없다. 후속 조건 변경과 이전 결과 참조는 별도 대화 시나리오로 평가해야 한다.

### 3.4 Databricks Genie Code: 사용자 과제 전체의 결과 평가

Databricks는 내부 실제 사용에서 추출한 401개 과제로 에이전트를 비교했다고 발표했다. 자료 탐색, 코드 관련 작업, 정확한 수치 조회 등을 포함하고 동일한 20분 예산을 적용했다. 독립 심사자가 답변의 정확성과 유용성을 평가하며 시간초과는 실패로 집계했다. [S4]

**적용 제안:** 개별 SQL 성공보다 사용자가 요청한 최종 비교·분석을 정확하게 완성했는지 평가한다. “순위 조회 → 상위 선수 선택 → 직전 시즌과 비교”는 하나의 과제로 채점할 수 있다.

**적용 한계:** 회사 내부 과제이며 공개 글만으로 전체 문제와 채점 규칙을 재현하기 어렵다. 20분 예산이나 발표 정확도를 우리 검색의 목표값으로 채택하지 않는다.

### 3.5 Anthropic: 코드·모델·사람 채점의 조합

Anthropic은 평가 과제, 반복 실행, 채점기, 실행 기록, 최종 결과를 구분한다. 코드 기반·모델 기반·사람 평가의 강점과 한계를 설명하고, 새로운 능력을 측정하는 평가와 기존 기능의 회귀를 막는 평가를 구분한다. 자동 평가와 실제 운영 피드백을 함께 활용하는 접근을 제시한다. [S5]

**적용 제안:** ID·수치·정렬·조건은 프로그램으로 채점한다. 자유 서술은 명시된 기준으로 보조 심사하고, 사람이 정답 및 심사 결과를 검수한다. 반복 실행은 일관성을 확인하는 데 사용하며 독립 문항 수가 늘어난 것으로 세지 않는다.

**적용 한계:** 범용 에이전트 평가 가이드이므로 축구 시즌·다중 소속·per90·누락 데이터의 정답 정의는 프로젝트가 직접 만들어야 한다.

## 4. 기존 프로젝트 평가 설계의 강점과 보완점

기존 계획에는 SQL 실행과 의미 정답의 분리, 고정 데이터, 개발/독립 평가 분리, 실패·시간초과 기록, 단계별 평가, 소수 표본의 한계가 이미 포함되어 있다. 새 원칙을 추가하기보다 이를 현재 구현에 연결하는 것이 우선이다. [P1]

| 확인 사항 | 판단 | 필요한 조치 |
|---|---|---|
| 기존 대화 평가 실행기가 이전 SearchService 경로를 사용 | 새 에이전트 전체 성능의 증거로 사용할 수 없음 | 현재 Planner·SQL·계산·답변 경로용 평가 연결 |
| 대화 채점은 상태·일부 조건·선수 참조 보존 중심 | 독립 정답과 수치·순위를 비교하는 범위가 부족 | 정답 결과 및 최종 설명 채점 추가 |
| 참조 보존을 이전 응답 기준으로 검사 | 잘못된 최초 결과를 일관되게 참조해도 통과 가능 | 최초 결과 정답과 후속 참조 정확성을 별도 검사 |
| 실제 모델 실행에 호출 간격 제한이 있음 | 품질 확인에는 활용 가능하나 사용자 지연과 구별 필요 | 실험용 대기를 별도 기록 |
| 개발 세트 결과와 실제 모델 오류를 보존 | 결과를 과장하지 않는 적절한 보고 방식 | 독립 평가와 구별 유지 |

기존 대화 보고서의 14턴 중 13턴 기대 충족은 이전 경로의 개발 평가 결과다. 최신 에이전트 보고서는 실제 모델 전체 질의 인수가 완료되지 않았다고 기록한다. 기능 테스트 통과나 이전 개발 결과를 현재 최종 답변 정확도로 해석해서는 안 된다. [P2][P3][P4]

## 5. 정확도 우선 평가 기준 제안

### 5.1 정답 행동부터 정의

| 입력·데이터 상태 | 기대 행동 |
|---|---|
| 질문이 명확하고 자료가 충분함 | 해당 조건의 결과 제공 |
| 질문의 의미를 하나로 정할 수 없음 | 필요한 정보 확인 |
| 정확히 조회했으나 조건에 맞는 행이 없음 | 0건임을 안내 |
| 자료가 없거나 부분 수집됨 | 누락 범위와 한계 설명 |
| 지원 범위 밖임 | 지원 한계를 설명하고 결과를 창작하지 않음 |
| 과거 대화를 참조함 | 지정한 결과와 조건을 보존 |

초기에는 불필요한 재질문 횟수를 기록하되 정확도 점수와 직접 합산하지 않는다. 필요한 확인 없이 추측해 답하는 것은 정확도 실패다. 재질문만 하고 끝난 과제는 완료로 세지 않는다. 모호한 질문의 과제에는 평가용 사용자 후속 답변과 종료 조건을 미리 준비한다.

### 5.2 최종 답변의 다섯 가지 필수 조건

| 항목 | 통과 기준 |
|---|---|
| 질문 해석 | 대상·대회·시즌·필터·요청 범위를 보존 |
| 결과 데이터 | 독립 정답과 ID·수치·단위·순서가 일치 |
| 계산·비교 | 산식·분모·기준 대상·동률·NULL 처리가 정확 |
| 설명과 근거 | 서술이 실제 결과와 연결되고 근거보다 강한 결론을 내리지 않음 |
| 한계와 완결성 | 요청을 해결하고 필요한 누락·범위·기준 시각을 표시 |

해당 과제에 적용되는 필수 조건을 모두 통과하면 **정확한 과제 완료**로 판정한다. 항목별 결과는 원인 진단용으로 보존한다. 숫자를 단순 가중 평균해 잘못된 시즌이나 선수 선택을 다른 장점으로 상쇄하지 않는다.

부분 답변의 허용 범위는 문항별로 정한다. 충분한 자료가 있는데 일부만 답했다면 불완전 답변이다. 원천 자료가 부족하고 기대 정답이 ‘가용한 부분과 누락 설명’이라면 그 행동을 정확히 수행했을 때 통과할 수 있다.

### 5.3 설명 정확도 채점

서술을 주장 단위로 나누어 다음을 확인한다.

- **근거 일치:** 선수·시즌·지표·수치를 올바르게 연결했는가?
- **비교 타당성:** 크다·작다·같다·증가했다 등의 표현이 계산과 일치하는가?
- **범위 준수:** 일부 데이터의 결과를 전체 리그의 결론처럼 확대하지 않는가?
- **요청 충족:** 질문의 핵심에 답했으며 필수 설명을 빠뜨리지 않았는가?

예를 들어 per90 득점 순위를 근거로 ‘최고의 공격수’라고 단정하는 것은 지표 범위를 넘는 주장이다. 반면 표현의 자연스러움이나 문장 길이는 초기 핵심 정확도 점수와 분리한다. 의미가 같은 표현은 허용한다.

### 5.4 대표 지표와 분모

| 지표 | 계산 | 해석 |
|---|---|---|
| 정확한 과제 완료율 | 모든 필수 조건을 충족한 과제 / 사전에 확정한 전체 평가 과제 | 대표 지표 |
| 제공 답변 정답률 | 정확한 결과 답변 / 결과를 제공한 답변 | 잘못된 답변의 노출 정도 |
| 기대 행동 일치율 | 정답 행동과 일치한 평가 단위 / 전체 해당 평가 단위 | 결과·확인·한계 안내 판단 |
| 대화 전체 통과율 | 필수 턴과 최종 결과를 모두 충족한 대화 / 전체 평가 대화 | 문맥 누적 오류 확인 |
| 반복 일관성 | 문항별 반복 통과 횟수 / 반복 횟수 | 실행 간 변동 확인 |

전체 및 질문군별 성공/전체 건수를 함께 제시한다. 제공자 장애·시간초과는 의미 오답과 별도로 분류하지만 완료율에서는 미완료다. 실행 자체의 설정 오류로 무효 처리한 실험은 기준과 제외 건수를 공개하고 재실행한다. 실패가 많다는 이유로 사후에 분모에서 제외하지 않는다.

출시 정확도 목표값은 이 보고서에서 임의 확정하지 않는다. 사용자에게 노출되는 잘못된 선수·시즌·수치·근거 없는 주장은 우선 수정할 중대 오류로 분류하고, 전체 평균 외에 별도 목록으로 관리한다. 권한·DB 안전성은 품질 점수와 별도의 필수 게이트로 유지한다.

## 6. 평가 세트와 정답 제작

초기 규모로 약 60개 과제를 제안하되 표준이나 충분성 보장으로 해석하지 않는다. 다음 여섯 질문군을 포함한다.

1. 단순 조회·순위.
2. 복합 조건·조건 제거·지표 변경.
3. 비율·다중 소속 집계·동률·NULL·0분.
4. 이름·별칭·동명이인·모호함.
5. 과거 결과 참조·시즌 변경·다단계 비교.
6. 0건·미수집·부분 수집·보관 범위 밖·미지원.

각 과제는 질문, 이전 대화, 데이터 버전, 기준 날짜, 기대 행동, 필수 조건, 기준 SQL/기대 결과, 허용 오차, 허용 표현, 금지 주장, 검수 기록을 갖는다. SQL이 필요 없는 문항에는 기대 확인 정보나 한계 안내를 정답으로 둔다.

정답은 구현 출력으로 자동 생성·갱신하지 않는다. 기준 SQL을 원천 행과 대조하고 작은 경계 데이터는 직접 계산해 검토한다. 실제 데이터 snapshot과 통제된 작은 fixture를 함께 사용한다.

개발용과 독립 평가용은 의미·집계 방식·표현 변형의 묶음 단위로 나눈다. 모델이 만든 질문 초안은 사람이 지원 범위와 정답을 검수한 뒤 채택한다. 동일 문항 반복은 표본을 독립적으로 늘린 것으로 계산하지 않는다.

## 7. 실행 순서와 완료 기준

| 단계 | 작업 | 완료 기준 |
|---|---|---|
| A. 기준 확정 | 질문군·기대 행동·정답 규칙 정의 | 모호한 정책을 정답으로 꾸미지 않고 미정으로 표시 |
| B. 정답 제작 | 대표 질문·작은 fixture·기준 SQL 검수 | 원천 데이터로 정답을 설명 가능 |
| C. 채점기 검증 | 의도적으로 틀린 시즌·수치·정렬·설명 주입 | 잘못된 답변을 실제로 탈락시키는지 확인 |
| D. 현재 경로 연결 | 최신 에이전트와 최종 응답을 평가 | 이전 구현 결과와 보고서 분리 |
| E. 개발 회귀 | 오류 유형별 수정과 동일 세트 재실행 | 수정으로 기존 정답이 깨지는지 기록 |
| F. 독립 평가 | 고정된 문제·버전으로 평가 | 질문군별 결과·실패·제약 공개 |
| G. 성능 개선 | 시간·재질문·비용 최적화 | 동일 정확도 평가에서 퇴행 여부 확인 |

초기부터 실행 시간과 호출 수를 기록하되 점수 최적화의 우선순위는 정확도에 둔다. 무한 반복 방지를 위한 실행 예산은 유지하고 초과는 미완료로 기록한다. 이후 성능 개선 시 모델·사전·프롬프트 변경마다 같은 정확도 회귀 평가를 실행한다.

## 8. 권장 결과 보고 형식

매 실행 보고서에는 다음을 포함한다.

- 실행 대상과 버전: 코드, 데이터, 모델, 프롬프트, 사전, 채점기.
- 범위: 개발/독립 평가, 과제 수, 턴 수, 반복 횟수.
- 전체·질문군별 정확한 완료 건수와 비율.
- 기대 행동 및 다섯 정확도 항목별 실패 목록.
- 중대 오류, 제공자 장애, 미완료, 무효 실행의 구분.
- 변경 전후 새로 맞힌 과제와 새로 틀린 과제.
- 보조 관측: 시간·재질문·호출·비용과 미확인 값.
- 해석 한계: 표본 규모, 미지원 범위, 사람 검수 여부.

‘정답률 90%’라는 숫자 하나보다 **어떤 질문을 몇 개 평가했고 무엇이 틀렸는지**를 확인할 수 있는 보고서가 우선이다.

## 10. 사용자 제공 보고서 검토 및 반영 기록 (2026-10-27)

검토 자료는 사용자 제공 「축구 데이터 자연어 검색 도구 평가 보고서」 PDF(6쪽, Woolee 표기, 2026-10-27)다. 공유 웹페이지는 로그인 요구로 읽지 못했고 제공된 파일 전체를 읽어 검토했다. 이 자료는 설계 제안이며 공식 기업 연구나 실측 결과와 구분한다.

핵심 반영 내용은 일곱 멀티턴 시나리오, 턴별 의미 상태와 변경 연산, 슬롯·참조·조건 유지 지표, 실제 히스토리와 정답 문맥 주입 평가의 분리다. 상세 설계는 [해설 논문 개정판](ax-evaluation-methodology-paper.md)의 7.4~7.7절과 8.5~8.6절에 반영했다.

그대로 채택하지 않은 항목도 있다. 슬롯 F1은 필수 조건의 누락을 상쇄할 수 없고, 숫자 일치는 의미 충실성을 보장하지 않는다. 허용 해석은 개수가 아니라 해석별 조건·결과 묶음으로 저장한다. 정답 문맥 주입과 전체 대화의 점수 차이만으로 회복 불능을 확정하지 않으며 별도 정정 시험을 둔다. NDCG는 정확한 통계 순위의 완전 일치를 대체하지 않는다. 특정 턴에서 조건 누락이 흔하다거나 대부분의 도구가 실패한다는 주장은 제공 문서에 실증 근거가 없어 검증 가설로만 보존한다.

100~200개 문항은 확장 후보로 두고, 작은 검수 세트와 채점기를 먼저 확인한다. 모호성·필수 확인의 정확성은 초기 평가에 포함하되 불필요한 재질문 횟수의 최적화는 이후로 둔다. 과거 기록·고급 지표·이적료 등은 실제 저장 가용성을 확인하기 전 지원 기능으로 확정하지 않는다. 이번 개정은 문서 반영이며 검색 구현이나 유료 평가 실행을 수행한 것이 아니다.
