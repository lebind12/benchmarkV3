# 정확도 채점 지침 v1

이 문서는 40개 개발용 과제(64턴)의 채점 규약이다. 실제 모델의 측정 결과는 아직 없다. 기대 답변은 예시이며 문장 일치로 채점하지 않는다.

## 1. 평가 환경

각 과제는 새 대화에서 시작한다. 동일 과제 안의 턴은 순서대로 입력하고 실제 모델 응답을 다음 턴의 대화에 포함한다. 질문, 연결된 자료, policies.json의 기준 시각·시즌·동률·결측 정책을 평가 대상에게 제공한다. 정답, SQL, 채점표는 제공하지 않는다. snapshot과 synthetic 자료를 혼합하지 않는다.

저장본은 2026-10-25 수집 파일의 EPL 2025·2026 시즌 부분집합이다. 현실의 최신 기록이나 전체 수집 완전성을 보증하지 않는다. 가상 선수와 나이·포지션·빅6 표시는 시험용 조건이다. 제품에 이 자료를 연결하는 평가 어댑터는 아직 구현하지 않았다. 실제 서비스 DB로 실행하려면 그 데이터에 맞춰 정답을 다시 만들고 검수해야 한다.

모호한 문항은 이번 v1에서 ‘먼저 확인하기’를 기대 정책으로 채택했다. 이는 모든 제품에 대한 보편적 정답이 아니다. 가정을 명시하고 바로 답하는 정책도 허용하려면 평가 전에 완전한 허용 해석과 정답을 별도로 등록한다. 결과를 보고 정답을 바꾸지 않는다.

## 2. 턴별 필수 판정

각 적용 항목을 PASS / FAIL / NOT_APPLICABLE로 기록한다. 판정 근거로 응답의 문장 또는 출력 필드를 함께 남긴다. 내부 추론 공개를 요구하지 않는다. 정규화된 검색 상태가 출력되지 않는 제품은 응답과 도구 실행 기록에서 확인 가능한 범위로 판정하고, 확인 불가능한 조건은 REVIEW_PENDING으로 기록한다.

| 항목 | 통과 기준 | 실패 예시 |
|---|---|---|
| 행동 | expected.action에 맞는 결과·확인 질문·지원 한계를 제시 | 자료가 없는데 숫자를 생성 |
| 의미 | gold_state의 대상·기간·대회·지표·필터를 모두 충족 | 도움 요청에 득점으로 답함 |
| 데이터 | 기대 ID·값·필수 순위·결과 집합이 일치 | 900분 이상을 900분 초과로 적용 |
| 근거 | 이름과 숫자를 바르게 연결하고 사실·추정·결측을 구분 | 득점 차이를 운이나 감독 효과로 단정 |
| 완결성 | must_include를 충족하며 must_not 위반 없음 | 필요한 결측이나 저장본 범위를 숨김 |

데이터 항목은 수치 정답(reference)이 있는 턴에 적용한다. 행동 문항에도 이름·숫자를 추가했다면 그 주장은 근거 항목에서 검증한다. JSON 키를 사용자에게 그대로 출력할 필요는 없다. 필수 상태는 의미를 검증하기 위한 표현이다.

- 정수 수치·ID는 정확히 일치해야 한다. 이름은 같은 ID의 검증 가능한 별칭을 허용한다.
- 소수 원값 비교 허용오차는 0.000001이다. 사용자에게 소수 둘째 자리까지 보여준 경우 정답을 같은 자릿수로 반올림한 값과 비교한다. 반올림 이전 값으로 순위를 정한다.
- 순위 요청은 내림차순, 동률은 공동 순위(1, 1, 3), 표시 순서는 ID 오름차순이다. 상위 N명은 N행이며 ‘공동 1위 모두’는 동률 전원을 포함한다.
- 비교 표의 행 순서는 사용자가 지정하지 않은 한 자유다. 순위 요청의 행 순서는 필수다. SQL의 단순 비교 행 정렬은 정답 보관 편의를 위한 것이다.
- 두 팀 기록은 선수·대회·시즌별로 합산한다. 어느 팀의 해당 수치라도 NULL이면 총합은 미상이다. 알려진 부분 합계를 전체 합계라고 하면 실패다.
- no_matches는 자료상 조건에 맞는 결과가 없다는 뜻이다. data_unavailable은 필요한 값이나 자료가 없다는 뜻이다. unsupported는 이 평가의 기록 조회 범위를 벗어난 요청이다.
- S04·S05처럼 대상 행은 있으나 요청 수치가 NULL이면 data_unavailable이다. 행을 함께 표시해도 되지만 수치 미상을 분명히 밝혀야 한다.
- clarification_required는 지정된 확인 항목을 질문해야 한다. 예시 문장과 다른 표현, 여러 항목을 한 문장으로 묻는 방식도 허용한다.

## 3. 합격 및 집계

턴 성공은 모든 적용 필수 항목 PASS일 때만 인정한다. 과제 성공은 모든 턴 성공일 때만 인정한다. 평균 점수로 숫자 창작이나 조건 위반을 상쇄하지 않는다. REVIEW_PENDING은 검수 후 확정하며 성공으로 계산하지 않는다.

주 지표는 **엄격 과제 성공률 = 성공 과제 수 / 예정 과제 수(40)** 이다. 완료된 턴 정확도와 별도로 완료율, FAIL, INCOMPLETE, REVIEW_PENDING 건수를 함께 보고한다. API 오류·시간 초과는 INCOMPLETE로 기록하고 전체 40개 분모에서 제외하지 않는다. 인프라 실패를 의미 오류와 혼동하지 않도록 원인도 분리한다.

stored_data(16), edge_fixture(9), behavior(8), multi_turn(7)의 성공률을 반드시 따로 제시한다. 특히 ‘답하지 않아야 하는’ 문항의 성공을 수치 조회 능력과 합쳐서만 설명하지 않는다. 실제 데이터와 가상 데이터 결과도 분리한다. 64턴의 턴 성공률은 진단용 보조 지표이며 긴 대화에 더 큰 가중치가 생긴다.

보조 진단에는 실패 항목, 지표별 수치 오류, 잘못 연결한 선수, 잃어버린 조건, 잘못 유지한 조건을 기록한다. 조건 일부 일치율은 원인 파악용이며 과제 성공을 대신하지 않는다.

## 4. 멀티턴 특칙

실제 응답에 따른 대화 전체 성공을 주 평가로 삼는다. 예를 들어 M01 첫 표가 틀려 후속 ‘두 번째 선수’가 바뀌었다면 과제는 실패이며 이후 오류에 선행 오류 전파 태그를 붙인다. 모델이 실제로 제시한 표와의 참조 일관성은 별도 진단으로 기록한다.

정답 대화 이력을 주입하고 후속 턴만 평가하는 실험은 oracle-history 진단으로 분리한다. 실제 이력 실험과 점수를 합치거나 차이를 특정 원인의 효과라고 단정하지 않는다. M07은 사용자 정정 수용 시험이며 모델이 스스로 오류를 회복한 성공률이 아니다. M04는 경기·이벤트 자료 부재에 대한 실패 처리 시험으로 정상적인 팀→경기→선수 탐색 능력을 증명하지 않는다.

## 5. 정확도 이후 효율 평가

먼저 정확도 판정을 고정한다. 이후 같은 자료·질문으로 응답 시간, 비용, 확인 질문 횟수, 오류로 인한 재질문을 따로 측정한다. 필요한 확인 질문과 모델 오류 때문에 발생한 재질문은 구분한다. 이 v1은 답변 결과가 정해진 턴에서 불필요한 확인만 하고 끝내면 미완료로 판정하므로, 자유로운 추가 대화를 허용하는 효율 실험과 직접 비교하면 안 된다.

현재 릴리스 합격 임계값은 정하지 않았다. 사람이 독립 검수한 정답, 별도 비공개 평가셋, 실제 지원 범위가 준비된 뒤 용도별 목표를 정한다. 이 공개 개발셋의 높은 점수만으로 운영 품질을 보증하지 않는다.
