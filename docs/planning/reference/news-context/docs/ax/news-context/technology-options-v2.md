# 기술 선택 방향 v2 — 비평 반영

상태: 보완 설계. [조사 v1](research-v1.md), [비교 v1](technology-options-v1.md), [Opus 대조](opus-design-critique-assessment-v1.md)를 근거로 우선 검증할 조합과 보류 조건을 정했다. 프로젝트 성능·모델 품질은 아직 실측 전이다.

## 1. 우선 검증하는 B안

기존 FastAPI/Pydantic·SQLAlchemy·Supabase Postgres·Vue를 유지한다. Postgres의 명칭/별명/초성/소속·시즌 후보 검색 + LLM의 문맥 해석 + 검증한 조회 계획 + 서버 DB 조회 + 버전 있는 공통 판단을 하나의 사용자 흐름으로 검증한다.

| 영역 | 우선 방향 | 선택 이유와 검증 조건 |
|---|---|---|
| 후보 생성 | 정식명·4종 번역·공통 별명/거부·초성·팀/시즌 후보, 근사 문자열 검색 | 현재 스키마와 연결 가능. 초성·별명·음역·당시 소속의 candidate recall을 따로 측정 |
| 검색 확장 | 필요 시 pg_trgm/unaccent, 모델의 라틴/한국어 표기 추정을 검색에만 활용 | 확장은 제공 가능/미설치 관찰 상태. 설치는 migration에서 관리하며 음역 추정을 정답으로 확정하지 않음 |
| 문맥 판별 | 기존 Vertex 구조화 호출을 기준으로 쉬운/어려운 사례 분기 비교 | 뉴스 모델은 자연어 검색 모델을 임의 승계하지 않음. 모든 자동 연결에 원문/DB/판단 근거 필요 |
| 자료 조회 | 의도·지표·시점·대회·집계 단위를 가진 조회 계획→서버 SQLAlchemy | 자유 생성 SQL이나 모델 수치 실행/표시를 기본으로 삼지 않음. 조회 사전의 실제 자료 확인 |
| 한국어 표시 | 기존 번역+정적 도메인 명칭+DB 사실 렌더러, 한국어 판단 근거 | 입력 언어를 바꿔도 수치·날짜·대상이 바뀌지 않아야 함 |
| 공통 판단 | Postgres 판단·버전·감사 transaction | 현재 권한/동시 충돌 방식 활용. 다음 분석의 실제 적용/거부/취소를 검증 |
| 장문 | 문서 공통 문맥+문단 단위+전역 검증을 우선 가설로 단일 호출과 비교 | 5만 자 전체 구간·문단 간 지시어·30개 초과 등장·자동 복구·지연/비용을 측정 |
| 사용자 통지 | 인증된 응답 스트림으로 진행·완료·판단 버전 변경 | 부분 카드는 공개하지 않고 전체 검증 후 결과 제공. 주기적 상태 polling 예외를 추가하지 않음 |
| 화면 | Vue의 구간 분절/다중 주석·상호작용 카드, 필요하면 Floating UI | 기존 첫 위치/겹침 제거는 대체 필요. 위치 보정과 접근성 검증은 별개 |
| 검증 | pytest/Playwright + 독립 정답 + 실제 host 실행 증거 검사 | 재생 응답만으로 의미 품질 통과 불가. 코드/계약/DB/모델 지문 연결 |

응답 스트림은 [Fetch response body의 증분 처리](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch)와 [SSE의 이벤트 식별·재연결](https://html.spec.whatwg.org/multipage/server-sent-events.html)을 참고한다. `EventSource`의 동작을 POST·Bearer 인증 Fetch 구현의 자동 제공 기능으로 오인하지 않는다. 사용한 전송 방식에 맞게 인증·파싱·재연결·중복 방지를 구현하고 프록시/서버·권한 철회를 검증해야 한다. endpoint 계약은 목업 뒤 작성한다.

## 2. 도입을 보류하는 구성과 재검토 조건

| 구성 | 현재 판단 | 다시 검토할 실제 조건 |
|---|---|---|
| pgvector/다국어 embedding | 기본 도입을 보류 | 문자열·음역·공통 별명·소속 후보를 써도 특정 언어/표현의 정답 후보가 반복 누락되고, 같은 corpus의 hybrid 검색이 개선을 보일 때 |
| PGroonga | 기본 도입을 보류 | CJK 이름·문맥 검색에서 현재 방식의 실패와 인덱스 이점을 실측할 때 |
| BLINK/ReFinED/BELA/mGENRE 등 | 즉시 도입하지 않고 비교 대안으로 유지 | 실제 모델별 언어/라이선스/KB 변환·자원·갱신 부담을 구분하고, 후보 생성/판별의 이득이 필요한 경우 |
| Graphiti/별도 graph DB/GraphRAG | 현재 관계형 DB로 시작 | 여러 출처의 시간 관계·다단계 탐색이 관계형 처리의 복잡도/오류를 실측상 키우는 경우. 통계 사실·사람 판단 취소를 자동 해결한다고 가정하지 않음 |
| LangGraph 등 workflow 라이브러리 | 내부 작업 상태와 제한 재시도로 시작 | 확인된 복구·중단/재개 요구가 단순 작업 상태로 충족되지 않을 때. 공통 판단 저장소와 구분 |
| Label Studio/Prodigy | 정답 작성 도구를 지금 고정하지 않음 | 실제 corpus 라벨링·검토량이 직접 JSONL/검토 UI의 부담을 넘고 권한/감사를 유지할 수 있을 때 |
| Langfuse/Phoenix 등 별도 계측 | 현재 요청 ID·단계/토큰·안전 로그로 시작 | 실제 실험 협업/추적 요구와 운영 부담을 비교했을 때. 원문 전문 저장이 자동 켜지는 구성을 허용하지 않음 |

보류는 기능 제외가 아니다. 필요가 확인되면 같은 필수 시나리오·정답·자료로 비교한다. 전용 EL 전체가 영어 또는 NC 라이선스라고 단정하지 않으며, '비용이 효익을 초과했다'는 실측 없는 결론을 사용하지 않는다. W3C 인용/위치 모델은 위치 계약의 참고 표준이며 위 선택 도구와 묶어서 제거하지 않는다.

## 3. 같은 조건의 기술 비교

- A(LLM 중심)/B(후보 검색+문맥 판별)는 기본정보뿐 아니라 기록·경기·이력·공통 피드백·수정/취소·후보 밖 검색·다국어·장문·한국어·권한 전체를 유지한다.
- B의 문자열 검색/혼합 검색, 단일/분할 호출은 같은 corpus·snapshot·정답·모델·프롬프트 버전에서 비교한다. 평가 계획의 3회 반복·필수 통과 기준을 적용한다.
- 비교 단위: 후보 recall, 정확한 등장+대상, 올바른 조회 계획/DB 값, 불확실성, 한국어 표시, 판단 재사용 효과, 자동 복구·전체 공개, 호출/token/비용/대기시간.
- 비용 상한·작업 기한·분할 크기·동시성을 고정하기 전 실제 추정/측정을 준비한다. 아직 실행하지 않은 유료 모델 비교 결과를 쓰지 않는다. 실패를 이유로 5만 자·언어·이력 요구를 줄이지 않는다.

## 4. 소유 파일과 선행 의존성

현재는 문서 설계만 변경한다. 제품 실행 계약을 동결할 때는 다음 영역을 실제 필요한 경로로 좁힌다.

- FE 목업/본문·카드·후보·범위 확인/진행·실패/충돌: `frontend/src/views/NewsAnalysisView.vue`, `frontend/src/components/news-analysis/`, 이후 `frontend/endpoint-requests/`의 해당 계약.
- 분석·원문 분절·후보/조회 계획·한국어 표시·내부 작업: 기존 `app/services/news_analysis*.py`와 필요한 별도 서비스. endpoint는 FE 계약 이후 `app/api/v1/news_analysis.py`에서 연결.
- 공통 판단·감사·버전: 후속 모델/서비스와 `supabase/migrations/*_news_context_feedback.sql`. extension이 채택되면 별도 migration과 ORM 정합성. 감독 번역 테이블을 중복 생성하지 않음.
- 데이터 선행 작업: 기존 daily-sync의 transfer/injury 수집·보관 의미·coverage를 별도 계약으로 관리. 뉴스 API에 외부 수집을 넣거나 다른 워커 수동 API를 선제 구현하지 않음.
- 검증 준비: 고정 입력/정답/snapshot, 판정 규칙·실제 실행기·증거 검사기와 테스트의 소유 경로를 실제 작성 후 동결.

미해결 준비 항목은 `Q-DATA`, `Q-TESTSET`, `Q-VERIFY`다. 이 설계는 해결 방법을 구체화했으며 실제 데이터·검증 파일·명령·왕복 증거를 이미 확보했다고 보고하지 않는다.
