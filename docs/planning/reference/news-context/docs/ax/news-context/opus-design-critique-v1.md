# 뉴스 문맥 연결 재기획 v3: Opus 설계 비평

결론부터: 요구사항은 원문을 대체로 충실하게 보존하고 있습니다. 다만 개발에 들어가기 전에 정해야 할 것이 네 가지 남아 있습니다.
- 공통 판단을 언제 재사용하는지에 대한 규칙
- 기록·경기 문맥으로 어떤 조회를 지원하는지의 목록
- 원문 위치를 지정하는 방식
- 정답셋을 고정할 DB 기준점

추천 B안의 방향은 유지해도 됩니다. 다만 pgvector·전용 EL 같은 무거운 구성요소는 빼고, 지금 DB 규모에 맞게 단순하게 줄이기를 권합니다.

**표기 규칙:** 【관찰】은 제가 파일·코드·DB 관찰 JSON에서 직접 확인한 사실, 【제안】은 설계 제안, 【추정·미검증】은 확인하지 않은 추론입니다. 테스트, 모델 호출, DB 조회는 하나도 실행하지 않았습니다. 이 비평은 제품 검증 PASS도, 머지·배포 승인도 아닙니다.

## 1. 지적 사항 (P0 → P2)

### P0-1. 공통 판단을 언제 재사용하는지 정의되지 않아 R09·R10을 테스트할 수 없음
- **근거:**
  - R09-S01은 "문맥이 같은 새 글", R09-S02는 "유효 문맥이 모호하면 다시 제시"를 요구합니다.
  - replan-v3.md:57은 "저장 구조는 화면·endpoint 계약 뒤 설계"라고 미뤄 두었습니다.
  - technology-options-v1.md:99는 판단 종류만 나열합니다.
  - 그런데 '같은 문맥'을 판정하는 규칙은 어디에도 없습니다.
- **사용자 실패 예:**
  - A가 축구 문맥에서 "손"을 특정 선수로 확인합니다. 그런데 B의 글에서 "손이 부족하다"(인력 비유)에도 그 판단이 붙습니다.
  - 반대로 확정 별명인데도 매번 다시 물어봐서 "다음에 더 나은 결과"가 체감되지 않습니다.
  - 어느 쪽이 맞는지 판정할 기준이 없어서 R09-S04의 전후 비교도 할 수 없습니다.
- **수정안:** 판단을 다섯 종류로 나누고, 종류마다 **재사용 범위**와 **적용 방식**을 계약에 명시합니다.

| 종류 | 재사용 범위 | 다음 분석에서 적용하는 방식 |
|---|---|---|
| 별명 → 대상 | 표면형 정규화값 + (선택) 팀/시즌/대회/언어 범위 | 후보에 강제로 넣고 판별 근거로 제공. 범위 키가 모두 맞고 상충하는 후보가 없을 때만 자동 확정 |
| 명시적 거부 | 표면형 + 거부한 후보 + 범위 키 | 같은 범위에서 그 후보를 제외하거나 감점. 다른 범위에는 영향 없음 |
| 경기 확정 | 명시 날짜 또는 대진 + 대회 | 같은 명시 조건에서만 근거로 사용. "어제" 같은 상대 시점은 전역 재사용 금지 |
| 지표 용어 ("공포" 등) | 전역 | 조회 계획의 용어 사전에 반영 |
| 문서 내 지시어 ("그", "걔") | 그 글에서만 | 근거·감사용으로 저장하고 다른 글에는 적용하지 않음 |

  - 같은 종류·같은 범위에서 활성 판단은 하나만 허용합니다(유일 제약). 다른 사용자의 상충 판단은 새 행으로 만들지 않고 기존 판단을 버전 수정하도록 합니다.
  - 이렇게 하면 "순차적으로 들어온 상충 판단"도 처리됩니다. 지금 R10-S02는 동시 수정만 다룹니다.
- **확인 테스트:**
  - 종류마다 (재사용해야 하는 글, 재사용하면 안 되는 반례 글) 쌍을 만들어 고정합니다.
  - 판단 저장소 스냅샷 v0 / v1(A의 판단) / v2(A의 취소) 세 상태에서 같은 모델·DB·입력으로 실행합니다.
  - 각 쌍마다 `applied_decision_ids`와 연결 결과가 기대값과 정확히 일치해야 합니다.

### P0-2. 정답셋이 고정된 DB를 전제하지 않아 정답이 하루 4번 흔들림
- **근거:**
  - R14-S01은 "기대 DB 자료"를 고정하라고 요구합니다.
  - 【관찰】 실제 DB는 daily-sync로 6시간마다 갱신되고, 2026 시즌 경기 1,291건 중 640건만 종료 상태입니다.
- **사용자 실패 예:**
  - "최근 5경기 득점"의 정답값은 다음 경기가 끝나는 순간 바뀝니다.
  - 그러면 평가 실패가 생겨도 제품 결함인지 정답이 낡은 것인지 구분할 수 없습니다.
  - 정답을 고치는 순간 "사후 정답 변경"이 되고, 고치지 않으면 의미 없는 FAIL이 쌓입니다.
- **수정안:** 【제안】
  - 평가 전용 Postgres를 둡니다. 관련 테이블 덤프나 Supabase branch 같은 형태이고, `db_snapshot_id`와 기준 시각을 함께 기록합니다.
  - 정답에는 계산된 값만 넣지 않고 조회 명세(대상 ID·지표·기간·as_of·대회)를 함께 넣습니다.
  - 이 DB 하나로 **격리 판단 저장 DB**(R09·R10)와 **정답 기준 DB**를 함께 해결할 수 있습니다.
- **확인 테스트:**
  - 정답 파일 hash와 DB 스냅샷 id를 실행 기록에 남깁니다.
  - 같은 정답·스냅샷으로 두 번 실행했을 때 조회 결과가 바이트 단위로 같아야 합니다.

### P0-3. "기록·관련 경기·이력" 문맥으로 어떤 조회를 지원하는지 목록이 없음
- **근거:**
  - R05는 열린 집합입니다.
  - technology-options-v1.md:87은 "새 지표가 빠지면 어휘 보완, 조용히 제외 금지"라고 합니다. 원칙은 맞지만 이대로는 끝나지 않는 범위가 됩니다.
- **사용자 실패 예:**
  - 정답 작성자는 "xG"나 "점유율"을 관련 기록으로 표시합니다.
  - 구현은 득점·도움만 지원합니다.
  - 그 결과 FAIL인지 범위 밖인지 아무도 판정할 수 없습니다.
- **수정안:**
  - 실제 DB 필드에서 출발한 **v1 조회 의도 목록**을 계약에 넣습니다.
    - 선수 경기별 지표 (`fixture_detail.players`)
    - 시즌 통계
    - 경기 결과와 대진
    - 상대전적
    - 순위
    - 팀 최근 흐름
    - 감독 관측 이력
    - 이적·부상 (적재 후)
  - 목록에 없는 문맥 표현은 숨기지 않습니다. "DB에 해당 기록 유형 없음"이라는 **명시 상태**로 표시하고, 정답셋에서도 그 상태를 기대값으로 라벨링합니다.
  - 이것은 요구 축소가 아니라 판정이 가능하게 만드는 작업입니다.
- **확인 테스트:**
  - 정답의 모든 문맥 구절에 `intent ∈ 목록 ∪ {unsupported}` 라벨을 붙입니다.
  - unsupported를 조용히 누락하면 그 자체로 FAIL입니다.

### P0-4. 원문 위치 계약: 지금 구조로는 등장 위치별 해석(R04-S02)이 불가능
- 【관찰】 현재 코드의 구조:
  - `app/services/news_analysis.py`의 `link_mentions`는 `(entity_type, normalize(mention))`로 중복 제거합니다. 같은 이름의 두 번째 등장은 버려집니다.
  - `annotations.ts`의 `articlePieces`는 `text.indexOf(evidence)`로 **첫 번째로 일치하는 근거 구절**만 강조합니다.
  - 겹치는 구간은 아예 버립니다.
  - 모델 출력 스키마에는 `maxItems: 30`(`news_analysis_vertex.py:16`)이 걸려 있습니다.
- **사용자 실패 예:**
  - 5만 자 글에서 "케인"이 40번 나오는데 첫 번째만 강조됩니다.
  - "케인 골"이라는 같은 문장이 반복되면 엉뚱한 위치에 카드가 붙습니다.
  - 이름 구간과 그 이름이 들어 있는 "최근 5경기 득점" 문장 구간이 겹치면 하나가 사라져서 R07-S01이 성립하지 않습니다.
- **수정안:** 【제안】
  - 서버가 원문을 문단·문장 단위로 나누고 `segment_id`와 **code point 오프셋**을 붙입니다.
  - 모델은 오프셋을 직접 내지 않습니다. 대신 `(segment_id, 원문 그대로의 표면형, 그 segment 안에서 몇 번째 등장인지)`만 냅니다.
  - 실제 오프셋은 서버가 계산합니다.
  - 응답에는 code point 오프셋을 정본으로 담습니다. 프론트는 단일 함수로 UTF-16으로 변환합니다.
  - 이름 구간과 문맥 구간은 **중첩 레이어**(이름은 문장 안의 하위 구간)로 표현합니다. 겹침을 버리는 규칙은 폐기합니다.
- **확인 테스트:**
  - 고정 자료를 만듭니다: 동일 문장 반복, 이모지·보조평면 문자, 결합 문자, RTL, CRLF.
  - 이 자료에서 서버 오프셋으로 자른 문자열이 원문 부분 문자열과 전부 일치해야 합니다.
  - 브라우저에서 강조된 DOM 텍스트도 같은 문자열과 일치해야 합니다(Playwright).

### P0-5. 이적·부상은 "수집 경로 미정"이 아니라 CLAUDE.md 명세와 구현이 어긋난 상태
- 【관찰】
  - CLAUDE.md §4는 daily-sync가 transfers·injuries를 적재한다고 명시합니다.
  - 그런데 `app/workers/daily_sync`에는 transfer·injury 적재 코드가 없습니다(grep 결과 없음). 두 테이블이 0행인 원인은 이것으로 보입니다.
- **설계 충돌:**
  - 데이터 정책은 "최신 2시즌 보관"인데, 이적 이력은 본질적으로 수년에 걸친 경력입니다.
  - 2시즌으로 자르면 "이력"의 의미가 크게 약해집니다.
- **수정안:**
  - 별도 워커 작업 계약을 만들고, 이 기능의 선행 의존성으로 겁니다. 뉴스 기능의 owned_paths에 섞지 않습니다.
  - 그 계약 안에서 API-Football `/transfers`·`/injuries` 호출량을 semaphore 6 범위에서 계산합니다. 팀 1,250개 기준입니다.
  - 이적 이력의 보관 범위는 사용자 결정 사항입니다(아래 4절 질문).
- **확인 테스트:**
  - 적재 후 정답셋의 이적·부상 문장에 실제 행이 연결되어야 합니다.
  - "루머·부정문"(R06-S02)은 확정 이력으로 표시되지 않아야 합니다.

### P1-1. 5만 자를 동기 단일 호출로 처리하는 구조는 그대로 둘 수 없음
- 【관찰】 현재 설정:
  - `maxOutputTokens: 4096`, httpx timeout 45초, 문서 단위 관련성 판정 하나(`relevance != football`이면 언급 전체를 버림), 동시 슬롯 2개
- 【추정·미검증】
  - 등장 위치별로 출력하면 5만 자 글은 수백 개 항목이 됩니다. 그러면 출력이 수만 토큰 규모가 될 수 있습니다.
  - 단일 호출로는 수 분 지연이 날 수 있고, MAX_TOKENS가 나면 문서 전체가 실패합니다.
- **수정안:** 【제안】
  - 기본 가설을 **2단계 분할**로 둡니다.
    - 1단계(저비용): 문서 수준 문맥을 추출합니다. 관련성 구간, 문서 기준일 후보, 등장 팀, 지시어 후보를 정리합니다.
    - 2단계: 문단 묶음 단위로 추출하고 1단계 결과를 공통 문맥으로 함께 줍니다.
  - 단일 호출은 비교 대상으로 둡니다.
  - 관련성도 문서 단위가 아니라 **구간 단위**로 판정해야 R03-S02(혼합 글)를 지킬 수 있습니다.
  - 처리는 우리 서버의 **비동기 작업 + 작업 상태 조회**로 바꿉니다.
    - 이 상태 조회는 API-Football polling이 아니므로 CLAUDE.md §6 위반이 아닙니다. 계약에 그 구분을 명시해야 나중에 오판정이 없습니다.
    - 원문은 단일 인스턴스의 프로세스 메모리에만 두고 TTL로 파기합니다. 서버 재시작 시 작업 실패를 명시적으로 알립니다. 영속 보관하지 않습니다.
  - 분할 처리에서 일부 구간만 실패하면 어떻게 보여줄지는 사용자 결정 사항입니다(4절).
- **확인 테스트:**
  - 5만 자 고정 자료 3종(한국어·영어·혼합)에 앞·중간·끝 정답과 30개를 넘는 언급을 배치합니다.
  - 구간별로 누락표를 만들고, 종료사유·토큰·시간을 함께 기록합니다.
  - 문단 경계를 넘는 지시어("그는…")의 정답도 포함합니다.

### P1-2. 필수 자동연결 사례와 금지 반례는 있지만 판정 규칙이 숫자로 정해지지 않음
- **위험:**
  - 전부 보류하거나, 평균 점수로 뭉개거나, 모델 비결정성으로 재실행 운에 기대는 상황이 생길 수 있습니다.
  - temperature 0이어도 Gemini 출력이 완전히 결정적이라는 보장은 없습니다.
- **수정안:** 첫 모델 실행 **전에** 다음을 고정합니다.
  - 필수 자동연결 집합: 누락 0 같은 하한
  - 금지 연결 집합: 오연결 0
  - 보류 허용 집합
  - 반복 실행 횟수 n과 통과 규칙: 예를 들어 n=3 전부 통과 등
- **정답 관리:**
  - 정답은 hash로 버전 관리합니다. 정답을 바꾸면 전체를 재실행합니다.
  - 정답 작성자는 예측 모델과 독립이어야 합니다. 최소한 다른 모델 계열이 쓰고 사용자가 표본 검수하는 정도는 필요합니다. 지금 이 주체가 정해져 있지 않습니다.
- **5만 자 문서의 정답:**
  - 수백 개 언급을 전부 사람이 라벨링하기는 비현실적입니다.
  - 짧은 실제 글은 전수 정답을 만듭니다.
  - 5만 자 글은 정해진 위치에 심은 정답 + 무작위 표본 감사로 나눕니다.

- **근거:**

- **수정안:**
  - 선택 입력 `reference_date`를 둡니다.
  - 본문에서 날짜를 감지하면 화면에 표시하고 사용자가 수정할 수 있게 합니다.
  - 상대 시점 표현이 있는데 기준일이 없으면 해당 구간을 "기준일 확인 필요" 상태로 둡니다.

### P1-5. "2022 시즌을 섞지 말 것"이라는 조건 자체가 잘못됐을 수 있음

### P1-6. 공통 판단이 즉시 전역에 퍼지는 위험에 대한 최소 안전장치가 없음

- **권한 검사:** JWT는 stateless라서 역할을 철회해도 토큰이 만료될 때까지 유효합니다. R13-S02를 지키려면 쓰기 API에서 DB의 역할과 활성 상태를 다시 조회해야 합니다.

### P1-7. 한국어 표시를 LLM 생성에 맡기면 수치를 창작할 위험이 있음

- **확인 테스트:** LLM 근거 문장에 나온 숫자·날짜가 해당 카드의 DB 값 집합에 포함되는지 자동 검사합니다.

### P1-8. 화면이 열린 동안 판단이 바뀐 경우(R10-S04)의 감지 시점이 없음
- **수정안:**

## 2. 기술 선택: B안 유지, 단 단순화

**현재 DB 규모 【관찰】:** 선수 12,315명, 팀 1,250개, 감독 756명, 경기 약 3.2천 건. 이 규모에서는 이름 후보 검색에 벡터 검색이 필요하다는 근거가 약합니다.

교차 문자 체계(가타카나·아랍어 → 라틴) 고유명은 trigram으로도 잡히지 않고, 범용 임베딩으로도 잘 잡히지 않는 영역입니다. 대신 다음 조합을 권합니다. 【제안】

1. **음역 다리:** 모델이 언급마다 원문 표면형에 더해 라틴 표기와 한국어 표기 추정값을 냅니다. 서버는 이것을 별명 테이블, `pg_trgm`+`unaccent`, 번역명과 대조합니다.
2. **팀 범위 후보 주입:** 1단계에서 찾은 팀의 스쿼드(팀당 수십 명)를 서버가 검증한 ID와 함께 2단계 판별에 넣습니다. 스포츠 도메인에서 가장 싸고 효과가 큰 후보 생성 방법입니다.
3. **초성 검색:** `name_ko`에서 초성 열을 미리 계산해 둡니다. trigram이나 벡터로는 해결되지 않습니다.
4. **판별 분기:** 쉬운 언급(유일 후보이고 판단 근거 일치)은 서버가 바로 확정합니다. 어려운 언급만 후보 프로필과 함께 LLM에 다시 판별시킵니다. MHEL-LLaMo의 쉬운/어려운 분기를 축구에 맞게 적용한 형태입니다.
5. **조회 계획:** 모델은 typed 조회 계획만 내고, SQLAlchemy 조회는 서버가 합니다. 기존 메모의 선택을 유지합니다.

**대안들의 비용:**
- **pgvector + 임베딩:** 확장 설치, 임베딩 갱신 워커(번역·적재 시마다), 차원 제약(3072차원 기본값 대 HNSW 2000차원 한도), 호출 비용이 듭니다. 측정한 후보 누락이 확인되기 전까지 보류하고 재검토 조건을 명시합니다.
- **PGroonga:** CJK 본문 검색용입니다. 짧은 이름 대조에는 이득이 불명확하니 보류합니다.
- **C안(전용 EL: BLINK, BELA, GENRE 등):** archived 저장소, 영어 중심, NC 라이선스, KB 변환 작업, 단일 Koyeb 인스턴스에 GPU·메모리 추가 부담이 있습니다. 비용이 효익을 명확히 초과하니 기각을 권합니다.
- **Graph(Graphiti, GraphRAG)와 LangGraph:** 관계는 이미 관계형 테이블에 있고, 사람 확인 대기는 비동기 작업 상태 하나로 충분합니다. 기각을 권합니다.
- **A안 대 B안:** 실질적인 비교는 "한 번 추출 → 서버 확정" 대 "추출 → 후보 검색 → 어려운 언급만 재판별"입니다. 후자의 추가 비용은 어려운 언급 비율에 비례합니다. 실측 대상입니다.

## 3. 결정 질문과 기술 준비의 구분

**사용자 결정이 필요한 질문:**
1. 판단 종류별 재사용 범위(P0-1 표)를 승인할지. 특히 문서 내 지시어는 저장하되 다른 글에는 재사용하지 않는 것.
2. 이적 이력의 보관 범위를 "최신 2시즌" 예외로 둘지.
3. 최신 2시즌을 전역 기준으로 볼지 리그별 기준으로 볼지(월드컵 등).
4. 분할 처리에서 일부 구간만 실패했을 때 완료 구간을 보여줄지(전체 미완료 배너 + 실패 구간 재시도), 아니면 전체 실패로 처리할지.
5. 역할이 철회된 편집자의 기존 판단을 유지할지 일괄 무효화할지.
6. 비교 실험(A/B × 단일/분할 × n회 반복)에 쓸 유료 모델 호출 예산 상한.
7. 독립 정답 작성 주체: 사용자 검수 비율.

**담당자가 조회·실험으로 해결할 기술 준비:**
- 평가 전용 DB 스냅샷과 격리 판단 DB 구성
- `fixture_detail.players` JSON의 경기별 지표 실제 충족률 측정. 행이 있다는 것과 지표가 완전하다는 것은 다릅니다.
- 이적·부상 워커 계약과 호출량 산정
- 5만 자 실측: 언어별 토큰 수, 종료사유, 지연, 비용
- 음역 다리 + 팀 범위 후보 방식의 후보 recall 측정. 측정에서 누락이 확인될 때만 벡터 검색 도입 검토.
- Q-VERIFY 해결: 실제 실행 결과를 검증 근거로 남기는 경로입니다.
  - 운영자가 네트워크가 허용된 실행기에서 실제 평가를 돌립니다.
  - 결과물에 코드 지문, 모델 버전, 정답 hash, DB 스냅샷 id를 기록합니다.
  - 제품 검증 명령은 이 결과물의 지문이 현재 코드와 일치하는지와 판정 규칙을 확인합니다.
  - 실제 모델 응답을 녹화해 두면 후처리를 오프라인에서 결정적으로 재검사할 수 있습니다. 단, 이것은 의미 품질의 증거가 아니라 회귀 검사용입니다.

## 4. 강점, 가장 큰 불확실성, 개발 진입 조건

**강점 【관찰】:**
- 원문 인용과 요구사항 ID가 연결되어 있습니다.
- 이력, 다국어, 공통 판단 요구를 축소하지 않았습니다.
- 다음 경계를 명시적으로 구분합니다: 실제 모델 대 대역 응답, 0 대 NULL, 감독 관측일 대 공식 취임일, 거부 대 보류.
- 과거 PASS를 이번 완료 근거로 승계하지 않습니다.
- 기존 503(MAX_TOKENS) 장애의 재현 한계를 정직하게 기록했습니다.
- 현재 서버의 근거 대조 방식(모델 출력이 원문에 실제로 있는지 확인)은 유지할 가치가 있습니다.

**가장 큰 불확실성:**
1. 공통 판단 재사용이 실제로 "더 나은 결과"를 내면서 반례에서는 오연결하지 않는지 (P0-1)
2. 5만 자에서 등장 위치별 완전성과 지연·비용 (P1-1)
3. 이적·부상 적재가 끝나기 전까지 "이력" 요구를 실제로 검증할 수 없다는 점 (P0-5)

**개발 진입 전 충족 조건 (제안):**
- P0-1 ~ P0-5가 계약에 반영되고 독립 재검토를 거칠 것. 47개 시나리오 전체가 대상이며, 기존 44개에 대한 검토로 대체할 수 없습니다.
- 정답 v1 동결: hash, DB 스냅샷 id, 판정 규칙, 반복 횟수 n을 첫 모델 실행 전에 고정합니다.
- 이적·부상 워커 계약을 선행 의존성으로 연결하고, 적재 결과를 관찰합니다.
- Q-VERIFY 증거 연결 경로가 실제로 1회 왕복할 것. 이것은 제품 PASS가 아니라 경로가 동작하는지의 확인입니다.
- 위 4절의 결정 질문 1~7에 대한 사용자 결정.

Q-VERIFY, Q-TESTSET, Q-DATA는 여전히 미해결입니다. 제품 개발·검증 준비가 미완료라는 평가는 기존 기획 검토와 같습니다.
