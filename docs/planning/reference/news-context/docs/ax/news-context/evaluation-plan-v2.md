# 개발 전 정답·검증·증거 계획 v2

상태: 설계. 실제 corpus·정답·DB 스냅샷·실행 명령은 준비 전이며 제품 테스트를 실행한 기록이 아니다. 문서의 존재나 아래 숫자를 PASS로 사용하지 않는다. R01~R14와 추가된 시나리오 전체가 대상이다.

## 1. 정답이 의존하는 자료의 고정

평가 원천 자료는 별도 Postgres/격리 schema의 읽기 전용 snapshot으로 고정한다. snapshot에는 entity/번역/대회·시즌/경기·상세/선수 통계/순위/이적/부상/소속·감독 관측을 필요한 참조 관계와 함께 넣는다. 실제 DB에서 온 자료와 합성 DB fixture를 표시한다. 데이터를 추측해 채우지 않는다.

`db_snapshot_id, extracted_at, source_inventory_hash, tables/rows hash, competition/season coverage, reference_time/timezone`을 기록한다. 독립 정답은 대상 ID·원문 영역·조회 의도/조건·기대 경기/행 ID·값/NULL·허용 보류·금지 출력을 갖는다. 계산값과 독립 조회 명세를 함께 보존한다. 결정적 조회의 비교는 정렬·날짜·NULL·수치 표기를 정규화한 결과로 한다.

피드백 쓰기 DB/schema는 원천 snapshot과 격리한다. v0(저장 전)/v1(A 저장)/v2(수정·취소)로 초기화하며 계정 A/B의 실제 인증을 사용한다. 쓰기·취소·이력은 실제 DB에서 확인한다. 평가자가 원하는 상태를 제품 모델 응답에 주입해 실제 피드백 효과라고 보고하지 않는다.

정답은 제품 추론 결과를 보기 전에 작성한다. 작성자와 독립 검토자가 출처·DB 조회·한국어 의미·원문 영역을 확인한다. 다른 모델이 썼다는 사실만으로 독립 검토를 대체하지 않는다. 사용자의 직접 라벨링을 기본 의존성으로 추가하지 않는다. 정답 오류가 발견되면 변경 근거·새 hash·무효화된 실행을 기록하고 관련 전체 비교를 다시 실행한다.

## 3. 5만 자와 사용자 조작 없는 복구

- 한/영/혼합 50,000자 고정 자료에 앞·중간·끝 정답, 30개 초과 등장, 동일 이름 반복, 문단을 넘는 지시어를 넣는다. 분할 경계와 긴 단일 문단/문장도 포함한다.
- 짧은 실제 글은 모든 기대 연결을 검토한다. 장문은 모든 예정 처리 구간의 coverage를 기계적으로 검사하고 심은 정답을 전수 대조하며, 나머지 언급은 실행 전에 고정한 표본으로 독립 감사한다. 표본 감사만으로 장문 전체 의미 정확도를 보증했다고 표현하지 않는다.
- 일시 장애→자동 회복, 출력 중단→제한된 재분할→회복, 전역 병합 후 모순, 복구 소진, 서버 유실을 각각 실행한다. 오류 주입 테스트와 실제 정상 장문 모델 실행을 구분한다.
- 브라우저 테스트에는 분석 제출 후 사용자의 추가 클릭/응답 없이 복구와 전체 결과 공개가 일어나는지 포함한다. 실패 구간을 클릭해야 진행되면 FAIL이다.
- 모든 구간 종료·span/DB/버전 검사 전 최종 완료 이벤트/카드가 노출되면 FAIL이다. 후보 확인 필요 같은 의미적 불확실성은 처리 실패와 구분한다.
- 복구 소진 시 전체 실패·원문/출처 유지·요청 ID를 확인한다. 정상 단위 재호출, 중복 과금 유발 작업 중복 생성, 취소 후 호출/저장이 발생하지 않는지도 확인한다.
- 기록: 입력 코드포인트/언어별 실제 token, 구간 수·시도·재분할 수, finish reason, 대기시간, 총 호출/token/비용, 원문 구간별 정답 대조. 소수 실행만으로 안정적인 p95를 측정했다고 주장하지 않는다.

## 4. 의미 품질의 판정 규칙

실제 모델 실행 전에 각 정답 항목을 `must_link / must_not_link / may_ask`로 분류한다. 필수값·시점·대회·집계·한국어 출력과 허용되는 후보/보류를 명시한다.

- 동일 코드·모델 버전·프롬프트·snapshot·정답에서 **3회 반복**한다. 각 회차에 필수 자동 연결 누락 0, 금지 오연결 0, 필수 수치/ID/구간 오류 0이어야 한다. 허용 보류를 필수 자동 연결 사례에 확대하지 않는다.
- 모든 필수 시나리오가 통과해야 한다. 평균 정확도·유사도·과거 PASS로 하나의 필수 실패를 덮지 않는다. 명확한 사례를 전부 후보로 돌리는 결과도 FAIL이다.
- 후보 검색 recall과 최종 판별·조회·표시를 분리한다. 올바른 후보가 없었던 실패와 후보는 있었지만 오판한 실패를 구분한다.
- 공통 판단은 v0/v1/v2 각각 3회, 모델/원천 자료/입력은 고정하고 판단 상태만 변경한다. 의도한 효과와 반례 비적용을 모두 만족해야 한다. '저장 행이 생김'으로 개선을 입증하지 않는다.
- 한국어 사실 필드는 DB 기대값과 정확히 대조한다. 생성 근거의 숫자/날짜 탐지는 보조 검사이며 의미 검토를 대신하지 않는다. 원문·보조 고유명과 한국어 설명을 구분한다.

이 기준은 고정 수용셋의 통과 기준이지 임의의 모든 글에 대한 무오류 보증이 아니다. 평가 결과를 보고 불리한 사례·언어·지표·반복 회차를 제외하지 않는다. 반복 횟수나 기준 변경은 근거와 새 실행 버전으로 기록하며 통과를 위해 약화하지 않는다.

## 5. 실제 모델/DB/브라우저의 검증 근거 연결

로컬 응답 재생으로 실제 모델의 의미 품질 검증을 대체하지 않는다. 다음은 **구현·왕복 확인이 필요한 검증 경로 설계**다.

1. 운영자가 네트워크 가능한 host에서 승인된 실제 모델·읽기 전용 원천 DB·격리 피드백 DB·브라우저를 실행한다. 해당 프로세스 명령/시각/종료코드와 실제 관찰을 남긴다.
2. 증거 묶음에는 `run_id, code_tree_hash, contract_hash, prompt_hash, model/version/config, corpus/gold_hash, db_snapshot_id, feedback_versions, repetition, scenario_ids, command/exit_code, observations, artifact_hashes, started/finished_at`를 포함한다. 스코프 소유 파일뿐 아니라 실행에 영향을 주는 코드/설정 지문을 묶는다. 비밀·토큰·운영 원문 전문은 제외한다.
3. 공식 검증 명령은 실행 전에 기대한 run/corpus/정답/snapshot/code/contract와 증거를 대조한다. 전체 시나리오·3회·두 사용자·판단 전후·필수 UI 관찰이 빠졌거나 실제 실행이 아니면 FAIL이다. 빈 파일·PASS 문자열·마지막 요약만 확인하지 않는다.
4. 외부 실행기는 실제 명령의 종료코드와 증거 지문을 보존하고 독립 구현 검토자는 해당 관찰과 원문 요구를 대조한다. 실제 응답 재생은 후처리 회귀 검사로 별도 표기한다.
5. 개발 전 폐기 fixture로 이 경로가 1회 연결되는지 확인한다. 이것은 경로 확인이며 제품 PASS가 아니다. 제품 구현 후 새 코드 지문으로 실제 전체 흐름을 다시 실행한다.

현재 이 host 실행기/증거 검사기와 원자적인 실행 전후 코드·계약 지문 확인은 아직 구현·확인되지 않았다. 동일 OS 계정의 증거 파일만으로 실행 진위를 암호학적으로 보증한다고 주장하지 않는다. 실행 기록·원본 관찰·동결 지문을 함께 검토한다. 해결 전 Q-VERIFY를 닫거나 VERIFIED를 선언하지 않는다.
