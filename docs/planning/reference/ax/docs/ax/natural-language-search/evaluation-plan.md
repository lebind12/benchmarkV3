# 자연어 검색 AX 평가·성능 분석 선행 계획

작성일: 2026-10-25. 사용자 요청에 따라 기능 개발에 앞서 평가 기준과 측정 순서를 정리한다. 문서의 숫자는 별도 확정 표시가 없으면 실험 제안이다. 작업 상태 정본은 Plans.md (원문 참조 경로: `../../../Plans.md`; 이 기획 묶음에 포함되지 않음)이며 이 문서 작성으로 평가 세트·runner·성능 측정을 완료 처리하지 않는다.

## 1. 현재 상태와 이번 범위

- DB 조사 (원문 참조 경로: `data-audit.md`; 이 기획 묶음에 포함되지 않음): 독립된 두 READ ONLY snapshot에서 33개 관측 완료. 검색 정확도/부하 성능의 기준선은 아니다.
- 계획 작성 시점의 기존 오프라인 테스트 5개: 사전 원천/의존 참조와 audit 도구의 일부 동작 검증이다. 이름 조회·LLM·QueryPlan·검색 SQL·FE 전체 흐름은 미검증이다.
- [사전 JSON](semantic-catalog.json.md)은 비활성 초안이며 [조회 도구 계약](retrieval-tool-contracts.md)은 구현 전 명세 초안이다.
- 이번 산출물은 평가 설계다. 다음에 정답/fixture와 최소 측정 runner를 준비하고, 기능별 구현을 추가할 때 동일 평가를 실행한다. 구현 없이 모델/도구 성능을 미리 증명할 수 있다고 가정하지 않는다.
- 새 공개 endpoint를 선제 구현하지 않는다. FE-first 계약 절차와 일반 페이지의 DB-only·6시간 정책을 유지한다. 배포는 범위 밖이다.

## 2. 평가 세트와 정답 준비

초기 약 100문항을 제안한다. 개수는 충분성의 증거가 아니며 실제 실패 유형과 지원 범위에 따라 보강한다.

| 질문군 | 초기 제안 수 | 주요 정답/판정 |
|---|---:|---|
| 이름·별칭·표기 변형 | 25 | 내부 ID/종류, 원천 이름, 같은 ID 중복 제거, 한글/영문/공백·Unicode 변형 |
| 충돌·모호함·후속 확인 | 20 | 후보 집합, 잘림, 확인할 조건, 원문 조건 보존 |
| 지표·시즌·필터 | 20 | 정의 key, 실제 대회/시즌, 비교 연산·값, 지원/미지원 |
| 합계·비율·동률 | 15 | 복수 팀 집계, NULL/0분, 최소 출전 조건, 값·순서·동률 정책 |
| 미수집·부분·범위 밖 | 10 | 0건/자료 없음/불명/미지원 구분, 근거·시각·한계 |
| 권한·입력 공격·제한 | 10 | 미인증/위조 ref/허용 밖 접근 차단, 예산·timeout 처리 |

위 분배는 출발점이다. SQL 공격·권한 경계의 조합 테스트는 10문항으로 제한하지 않고 별도 늘린다. 미확정 지표를 테스트 문항에 넣었다고 지원 지표로 확정하지 않는다. 기대 동작이 미정이면 임의 정답 대신 `blocked_policy`로 기록하고 공식 정확도 분모에서 제외한 수를 공개한다.

### 정답 항목

각 문항은 다음을 갖는다.

- `case_id`, 유형/태그, 원문, 확인된 이전 조건, 기준 시각/시간대.
- 데이터 snapshot/fixture 버전, catalog/normalization 버전, 지원 정책 버전.
- 기대 단계/상태: lookup 후보/재질문/실행 가능/자료 없음/미지원/제한/실패. 내부 Bundle 상태와 외부 API 상태는 계약에서 별도로 대응시킨다.
- 기대 entity 종류·ID/허용 후보 집합, 사전 key/필수 조건, 확인 질문이 요구해야 할 정보. 질문 문구 자체의 완전 일치는 요구하지 않는다.
- 통계 문항의 검토된 매개변수 기준 SQL, 기대 ID·값·정렬·단위·집계/NULL/coverage 규칙. 미지원/공격 문항은 SQL 대신 차단 근거와 실행 금지를 기록한다.
- 정답 출처와 검토 이력, 허용 오차가 필요한 소수 지표는 명시된 오차. 내부/외부 ID를 혼용하지 않는다.

SQL 문자열이 달라도 결과 의미가 같으면 통과할 수 있다. 반대로 SQL 실행 성공만으로 정답으로 보지 않는다. 생성기가 만든 SQL을 그대로 정답으로 채택하지 않으며, 기준 SQL은 원천 행과 대조해 검토한다. NULL과 0, 순위 동률·안정 정렬의 미정 정책은 먼저 정리한다.

### 고정 데이터와 평가 누출 방지

- 작은 결정론적 fixture로 NULL/0·다중 소속·동명이인·경계 시각 등 정답을 통제한다. 실제 저장 데이터 기반 snapshot으로 현실적인 이름/분포도 별도 평가한다.
- 현재 audit evidence는 전체 entity/통계 snapshot이 아니므로 그대로 완전한 정답 DB로 사용할 수 없다. 필요한 축구 데이터만 별도 추출하고 snapshot ID·행 수·checksum·스키마 버전을 기록한다. 사용자/인증·토큰 데이터는 포함하지 않는다.
- 운영 DB는 6시간 갱신될 수 있으므로 live 결과를 고정 정답과 무조건 비교하지 않는다. 실행 DB와 정답 snapshot이 다르면 재기준화 또는 무효 실행으로 표시한다.
- 개발 예시와 최종 holdout을 분리한다. 같은 질문의 단순 표현 변형이나 동일 집계 template이 양쪽에 섞이지 않도록 그룹 단위로 분리한다. 생성 문맥에는 holdout 질문·정답 SQL·정답 결과를 넣지 않는다.
- 실패한 holdout으로 프롬프트를 수정하면 해당 문항은 이후 개발 회귀군으로 이동하고 새 holdout을 보강한다. 기대값을 구현 출력에 맞춰 자동 갱신하지 않는다.

## 3. 단계별 검증 순서

| 단계 | 준비/실행 | 통과 근거와 다음 단계 |
|---|---|---|
| E0 기준 준비 | 질문/정답·고정 fixture·상태/지원 정책·실행 기록 형식 | 사람이 검토한 최소 대표 문항으로 runner 자체를 확인 |
| E1 LLM 없는 사전/이름 조회 | 로더·정규화·exact/fuzzy·후보 병합·의존 확장·관계/overflow의 최소 구현 | 정답 후보 회수, 잘못된 자동 확정, 참조/버전 검증을 오프라인 재현 |
| E2 Retriever 단독 PoC | 같은 fixture/도구에 지정 Vertex 모델 연결 | 도구/인수/선택 ref·확인 판단, 반복 일관성·호출/토큰/비용 측정 |
| E3 Planner 단독 PoC | 검토된 Bundle 주입 → typed 계획 → SQL 조립/검증 | 조회 실패와 계획 실패를 분리, 기준 SQL과 ID/값/조건 비교 |
| E4 DB/서버 성능 | 모델 응답을 고정한 서버·DB 부하, 실제 읽기 경로/권한·timeout | 연결 대기/DB 실행/취소·큐·오류의 성능 기준선 |
| E5 전체 흐름 | 실제 Retriever→도구→Planner→DB→FE, 재질문/취소/실패 포함 | 전체 정확도·지연·비용·보안·화면 상태 확인 |

E2는 전체 서비스 구현 전의 제한된 PoC다. 실제 계정/리전에서 지정 모델의 접근과 tool calling/구조화 응답을 확인하고 미지원이면 원인과 선택 필요를 기록한다. 모델을 임의 대체하지 않는다. 모델이 두 역할을 맡는다고 요청당 항상 두 번 호출되는 것은 아니며 도구 결과 재입력·재시도를 모두 센다.

## 4. 정확도·안전성 지표

| 지표 | 계산/판정 원칙 |
|---|---|
| 후보 recall@K | 정답이 있는 문항 중 정답 ID가 반환 K개에 포함된 비율. 검색 종류·타입별 분리. 다중 정답은 집합 recall도 보고 |
| 잘못된 자동 확정 | 자동 resolved 처리 중 잘못 확정한 건수/비율, 전체 문항 대비 비율을 함께 기록 |
| 자동 확정 비율 | 자동 확정 가능한 문항 중 자동 처리한 비율. 전부 재질문해 오확정률만 낮추는 결과를 방지 |
| 모호함/재질문 적절성 | 반드시 물어야 할 사례의 확인 성공률과 불필요한 재질문 비율을 별도로 기록 |
| 도구/참조 정확도 | 허용 도구/인수, 원문 mention 구간, 발행 ref/key, 조건·버전 보존 검증 |
| 계획 의미 정확도 | 대상·대회/시즌·필터·집계·정렬·최소 분모·제한의 기대 의미 일치 |
| 실행 결과 정확도 | ID/값·순서·단위·NULL/coverage/상태를 비교. 파싱/컴파일/실행 성공률은 별도 |
| 정책/안전성 실패 | 미인증 모델/조회 시작, 위조 ID/ref 수용, 허용 밖 테이블·변경·위험 함수 실행 등 |

전체 평균뿐 아니라 유형·exact/fuzzy·모호함·부분 자료별 성공/전체 수와 실패 목록을 남긴다. 모델의 자연어 설명을 평가하는 보조 심사만으로 ID·통계 정답을 판정하지 않는다. 같은 문항 반복은 변동성 측정이며 독립 문항 수를 늘린 것으로 집계하지 않는다.

필수 회귀 사례는 실측 (원문 참조 경로: `data-audit.md`; 이 기획 묶음에 포함되지 않음)을 따른다: 스미스 관측 29후보의 잘림, 원문/한글/짧은 이름의 동일 ID 병합, EPL 2026 복수 팀 기록, NULL/0분, 월드컵 실제 직전 저장 시즌 2022, 빈 fixture_detail JSON, 부상/이적 0행, 관계 unknown. 이 숫자는 조사 snapshot 기준이며 live 데이터에 고정 상수로 구현하지 않는다.

## 5. 성능·비용 측정

### 구간과 실행 기록

각 실행에 run/case/repetition ID, 커밋·모델 정확한 ID/리전·SDK/PG/사전 버전, 데이터 snapshot, 설정/timeout/동시성, 시작·종료·성공/오류/재시도·취소 여부를 남긴다. 비밀값·접속 문자열은 보관하지 않는다.

| 구간 | 기록할 값 |
|---|---|
| 인증/대기 | 인증 소요, 요청 큐/세마포어/DB pool 대기 |
| 사전/이름 조회 | 도구별 소요, 후보/반환 수, match 종류, 잘림/관계 상태 |
| Retriever/Planner 각각 | 모델 호출별 지연, 호출·재시도 수, 입력/출력·공급자가 보고한 추가 token, 상태 |
| DB | 계획 검사와 실제 실행 시간 구분, 반환 행/bytes, 스캔·조인/정렬, buffer·spill |
| 전체 | 사용자 요청부터 응답까지 시간, FE pending/오류 표시, timeout/실패/취소 비율 |
| 비용 | 요청별 전체 시도 토큰·도구/모델 호출, 확인된 단가/기준일 기반 추정 비용과 가용한 청구 집계 |

각 구간 및 전체의 p50/p95와 표본 수를 함께 보고한다. 실패/timeout 요청을 빼고 성공 지연만 발표하지 않는다. 성공·실패 지연과 timeout 비율을 분리한다. 구간 p95를 더해 전체 p95를 만들지 않는다. 병행 구간은 겹칠 수 있으므로 실제 wall-clock을 측정한다. 소수 smoke 표본의 p95는 탐색값으로만 표시한다. 비용 metadata가 없으면 0원 대신 미확인으로 기록한다.

### DB 분석과 부하 순서

1. 검토된 매개변수 SQL에 `EXPLAIN (FORMAT JSON)`으로 예상 scan/join/rows/cost를 기록한다. cost는 밀리초가 아니며 예상 행 수만으로 실제 시간을 확정하지 않는다.
2. 운영과 유사한 스키마/인덱스·대표 데이터 크기의 격리 DB에서 검토된 SELECT를 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`으로 분석한다. ANALYZE는 실제 실행하며 계측 오버헤드가 있으므로 별도의 일반 실행 시간도 측정한다. [PostgreSQL 17 공식 문서](https://www.postgresql.org/docs/17/using-explain.html)
3. exact/fuzzy·동명이인·조건 결합·다중 팀 합계 등 대표 쿼리를 같은 환경/데이터에서 비교한다. 작은 테이블의 sequential scan을 무조건 실패로 보지 않는다.
4. 초기 연결/모델 준비 여부와 반복 실행 상태를 구분한다. 반복 실행을 cold cache라고 부르지 않으며 운영 DB의 캐시를 강제로 비우지 않는다.
5. LLM 응답을 고정한 서버/DB 부하부터 시작하고 실제 모델을 포함한 작은 전체 실험으로 확장한다. 제안 동시 요청은 1→2→5→10이며 각 단계의 큐/거절·pool 한도를 함께 기록한다. 전체 SQL 동시 실행 한도와 외부 요청 동시성을 구분한다.
6. 새 요청 유입률과 실행 시간을 고정한 부하도 추가해 느린 요청 때문에 부하 생성량 자체가 줄어드는 착시를 확인한다. LLM 실험은 호출/토큰/비용 예산을 정해 시작하고 실제 동시성은 환경 한도 내에서 조정한다.
7. 연결 고갈·오류 증가·timeout·예산 초과의 중단 조건을 실행 전에 정한다. 취소/timeout 이후 서버 작업·DB 쿼리·모델 과금이 실제 종료됐는지 각 계층에서 확인한다.

운영 공유 DB에는 부하 실험을 수행하지 않는다. 현재 audit 계정은 검색 실행 계정으로 재사용하지 않는다. 테스트는 격리 DB/schema에서 수행하고, public 축구 데이터 snapshot을 만들 때만 별도 READ ONLY 추출을 한다. 실험 인덱스/pg_trgm/role 생성도 격리 환경에서 먼저 검증한다. 워커·API-Football·뉴스/번역 자동 작업은 평가 runner에서 실행하지 않는다.

## 6. 통과 조건과 보류 항목

실행 전 아래 차단 조건을 테스트로 표현한다. 통과는 해당 평가 범위의 관측 결과이며 안전성 전체를 수학적으로 증명하는 것은 아니다.

- 미인증 요청에서 LLM/축구 검색 DB 호출이 시작되거나 허용 밖 데이터/변경 SQL이 실행되면 공개 차단.
- 위조 ID/ref/key, 후보 잘림/충돌을 무시한 잘못된 자동 확정, unknown을 사실상 없음으로 바꾼 응답은 해당 경로 출시 차단 및 회귀 사례 추가.
- 순환/미등록/비활성 의존 정의가 실행 계획으로 넘어가거나 timeout/행·byte/동시성 예산 검증이 빠지면 공개 차단.
- 사용자 입력·조건 보존, 데이터 한계 표시, FE 로그인/재질문/실패 흐름은 통합 인수에서 확인.

정확도 목표 %, p95, 요청당 비용, 처리량, timeout·pool/동시성 값은 첫 기준선 후 고정한다. 현재 문서의 DB 3초·전체 15초·사용자 1개/전체 SQL 2개·100행/256KiB·최대 2회 등은 후보이며 본 계획으로 확정하지 않는다. 기준 변경 시 이유/정답 버전/비교 결과를 기록하고 검토 없이 실패를 숨기는 방향으로 바꾸지 않는다.
