# 자연어 검색 AX 사례 조사

조사일: 2026-10-25. 공식 제품 문서·개발팀 기술 글·저자 논문을 사용했다. 아래 제품 설명은 공개 자료의 근거이고, 프로젝트 적용 항목은 설계 제안이다. 외부 서비스의 정확도·비용·응답 시간을 우리 서비스의 보장값으로 사용하지 않는다.

## 1. StatMuse — 스포츠 자연어 검색

출처: [Asking Questions](https://developer.statmuse.com/docs/asking-questions/), [API 개요](https://statmuse-api-prod.developer.statmuse.com/docs/). 게시일 미표기, 조사일에 열람.

### 확인한 내용

- 스포츠 도메인을 지정해 자연어 질문을 전달한다. 축구 코드 `fc`도 문서에 포함되어 있다.
- 응답은 통계·선수·팀·알 수 없음 등의 유형으로 구분된다.
- 통계 응답은 설명문과 별개로 구조화된 `query`·`data.results`를 제공한다.
- 행의 문맥에는 선수·팀·시즌 등의 식별 정보가 들어간다. 통계는 원시 값과 표시 문자열을 구분하며, 기록되지 않은 수치는 `null`로 표현한다.

### 적용 제안과 한계

우리 결과 계약도 설명문·실제 적용 조건·수치·엔티티 링크를 분리한다. 미수집을 0으로 표현하지 않는다. 제품 형태의 가장 가까운 참고 사례지만, 이 문서만으로 내부 LLM·SQL 생성 구조나 한국어 지원을 확인할 수는 없다. 공급자 교체·데이터 구매를 결정한 것은 아니다.

## 2. Snowflake Cortex Analyst — 의미 모델과 검증 쿼리

출처: [Behind the Scenes](https://www.snowflake.com/en/blog/engineering/snowflake-cortex-analyst-behind-the-scenes/) (2024-08-14), [Verified Query Repository](https://docs.snowflake.com/en/user-guide/views-semantic/verified-query-repository) (현행 문서).

### 확인한 내용

- 원본 스키마와 업무 용어 사이의 차이를 줄이기 위해 설명·동의어·지표·조건 등을 담은 의미 모델을 사용한다.
- 질문을 분류하고 필요한 문맥을 보강한 뒤 SQL 생성·검사 흐름으로 이어간다. 2024년 글에서는 모호하거나 답할 수 없는 질문을 분류해 처리하는 구조를 설명한다.
- 사람이 검증한 질문·SQL을 저장하고, 새 질문과 관련 있는 예시를 문맥으로 활용한다.
- 질문 표현과 실제 DB 값이 다른 문제를 별도 검색으로 해결한다.

### 적용 제안과 한계

득점·도움·평점·최근 경기·시즌 소속·per90의 정의를 축구 의미 사전으로 관리한다. 통용 별칭을 실제 엔티티 ID로 해석하고, 검증된 SQL을 예시 자산으로 둔다. Snowflake 도입이나 외부 제품의 정확도 수치를 채택하는 제안은 아니다. 의미 사전 자체가 권한·비용 검증을 대신하지 않는다.

## 3. AWS·Cisco — 영역 선택과 이름/ID 해석

출처: [Enterprise-grade natural language to SQL generation using LLMs](https://aws.amazon.com/blogs/machine-learning/enterprise-grade-natural-language-to-sql-generation-using-llms-balancing-accuracy-latency-and-scale/) (2025-04-24).

### 확인한 내용

- 질문에 맞는 데이터 영역을 먼저 선택해 모델에 전달하는 스키마 범위를 줄인다.
- 질문의 이름을 실제 DB ID에 연결하는 단계를 SQL 생성 앞에 둔다. 모호하거나 찾지 못한 이름에 피드백할 수 있다.
- 설명·조인 힌트·업무 규칙·예시를 영역별 문맥으로 구성한다.
- 복잡한 조인·중첩 구조를 view나 임시 구조로 추상화하는 설계를 설명한다.

### 적용 제안과 한계

선수 시즌 통계·팀 시즌 통계·경기 목록을 논리 영역으로 나누고, `맨유` 등 별칭은 DB 조회로 해석한다. 확인된 JSONB 경로를 검색용 view로 투영하는 방향을 검토한다. 사례의 임시 테이블 생성·INSERT·클라우드 구성은 그대로 도입하지 않는다. 우리 검색 실행 계정은 제한된 읽기 경로를 유지한다.

## 4. Uber QueryGPT — 단계별 문맥 선택과 평가

출처: [QueryGPT – Natural Language to SQL Using Generative AI](https://www.uber.com/gb/en/blog/query-gpt/) (2024-09-19).

### 확인한 내용

- 질문 의도·테이블 선택·관련 컬럼 축소를 분리한다.
- 스키마와 SQL 예시 검색을 사용하고, 관련 없는 컬럼을 줄여 입력 크기·비용·지연을 개선했다고 설명한다.
- 실제 사용 질문에서 의도·필요 스키마·기준 SQL을 사람이 검증한 평가 세트를 구성한다.
- 전체 흐름과 개별 단계의 평가를 나누고, 정확도와 지연을 추적한다. 비결정성으로 인한 실행 간 변동도 명시한다.

### 적용 제안과 한계

오류를 이름/시즌 해석·데이터 영역 선택·계획·SQL·결과 단계로 구분한다. 한국어 표현 변형을 포함한 기준 질문을 만든다. 방대한 사내 데이터셋을 위한 벡터 검색·다중 에이전트를 현재 규모의 필수 구성으로 판단하지 않는다. SQL 작성 보조 UX와 일반 사용자의 결과 조회 UX도 구분한다.

## 5. Databricks Genie — 검증 자산과 평가 세트 분리

출처: [Genie Agents concepts](https://docs.databricks.com/aws/en/genie-agents/concepts) (2026-10-12 갱신), [Test and monitor](https://docs.databricks.com/aws/en/genie-agents/monitor) (2026-09-17 갱신), [사용자 흐름](https://docs.databricks.com/aws/en/genie-agents/talk-to-genie).

### 확인한 내용

- 데이터 정의·동의어·관계·예시 SQL·설명 지침을 사용한다.
- 검증한 매개변수 예시 쿼리와 SQL 함수를 trusted asset으로 관리한다.
- 벤치마크는 평가 전용이며 생성 문맥을 개선하는 예시와 구분한다.
- 응답을 만들기 어렵다면 후속 질문으로 확인할 수 있다. 결과 검토와 사용자 피드백 흐름을 제공한다.

### 적용 제안과 한계

프롬프트 참고 예시와 독립 평가 세트를 분리한다. 자주 쓰는 산식과 조인은 검증된 서버 로직으로 둔다. 예시를 재사용해도 지원 질문을 고정 템플릿으로 제한하지 않는다. 내부 분석 제품의 SQL 노출·권한 모델은 우리 일반 사용자 화면에 그대로 적용하지 않는다.

## 6. LinkedIn — 실제 운영에서 드러난 정확도의 한계

출처: [Text-to-SQL for Enterprise Data Analytics](https://arxiv.org/abs/2507.14372), [논문 본문](https://arxiv.org/html/2507.14372v1) (2025-07-18 제출).

### 확인한 내용

- 메타데이터·과거 쿼리·문서·코드를 지식 그래프로 연결하고, 검색·순위화·쿼리 생성·수정 흐름을 사용했다.
- 전문가가 평가한 124개 질문 중 53%가 정확하거나 거의 정확한 등급을 받았다. 가장 흔한 문제는 잘못된 필터였다(24%).
- 구성 요소 분석에서 문법/스키마 오류 개선과 의미적 정답률 개선을 구분한다. 예시 쿼리·테이블 묶음·컬럼 설명이 중요한 개선 요인으로 보고되었다.

### 적용 제안과 한계

컴파일/실행 성공과 실제 정답을 별도 지표로 관리한다. 시즌·대회·홈/원정·출전 시간·NULL·다중 소속을 핵심 평가 축으로 둔다. 대규모·다영역 사내 분석의 수치를 우리 성능 예상값으로 사용하지 않는다. 특히 ‘거의 정확함’을 일반 사용자에게 무검증 제공해도 된다는 근거로 해석하지 않는다.

## 7. 프로젝트에 가져올 원칙 — 조사에 따른 제안

| 원칙 | 구체 산출물 | 근거 사례 |
|---|---|---|
| 데이터의 의미를 버전 관리 | 지표·집계 단위·시즌·NULL·관계 사전 | Snowflake, LinkedIn |
| 이름 해석을 독립 처리 | 번역명·별칭·후보 ID·모호함 확인 | AWS·Cisco, Snowflake |
| 필요한 문맥만 선택 | 검색용 view·영역별 스키마/예시 | AWS·Cisco, Uber |
| 검증 예시와 시험 문제 분리 | 예시 저장소 / 독립 평가 세트 | Databricks, Uber |
| 설명과 실제 데이터를 분리 | typed 조건·표·링크·coverage 응답 | StatMuse |
| 실행 성공과 정답을 구분 | 조건/집계/결과·지연·비용별 측정 | LinkedIn, Uber |

이 사례들은 [상위 plan.md](../../../plan.md)의 QueryPlan 경로와 양립하지만, 특정 QueryPlan 스키마나 라이브러리 선택을 직접 입증하는 자료는 아니다. 읽기 role·SQL/함수 allowlist·비용 게이트·실행 제한은 프로젝트 정책에 따라 별도로 구현·검증해야 한다.

## 8. 추가 조사 과제

- 한국어 축구 별칭·시즌·비교 질문의 실제 오류 유형과 사용자 지정 Vertex AI `gemini-4-argon` 평가. 공급자 비교 선정은 후속 사용자 결정으로 제외한다.
- 작은 고정 스키마에서 전체 의미 사전 제공과 선택적 검색을 비교해 RAG 필요성 판단.
- 검증 SQL 예시가 새로운 조건 조합을 돕는지, 예시 밖 질문을 과도하게 거절하는지 측정.
- 공개 서비스의 비용 제한·취소·동시성·읽기 계정 운용 검증.
- 정책/제품 문서는 구현 시 다시 확인한다. 2024~2025 기술 글은 당시 구조 설명이며 현재 제품 내부와 동일하다고 단정하지 않는다.
