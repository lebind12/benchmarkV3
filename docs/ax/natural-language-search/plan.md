# 자연어 검색 AX 상세 실행 계획

작성일: 2026-10-25.

목표: 일반 사용자가 자유로운 한국어 질문으로 저장된 축구 기록의 목록·순위·비교를 조회하고, 적용 조건과 데이터 한계를 확인할 수 있게 한다.

이 문서는 자연어 검색의 실행 설계 정본이다. 도메인 정책은 [AGENTS.md](../../../AGENTS.md), 전체 작업 상태는 [Plans.md](../../../Plans.md)가 정본이다. 상위 기획은 [루트 plan.md §6](../../../plan.md#6-자연어--sql-검색-ax), 조사 근거는 [research.md](research.md)를 따른다. 아래 표의 상태는 중복 완료 표시 대신 `Plans.md`의 대응 작업을 참조한다.

비교 기록은 [stack-comparison.md](stack-comparison.md), 현재 채택 구성은 [기술 선정 결정](../../decisions/2026-10-25-natural-language-search-stack.md)을 따른다. SQLAlchemy Core·SQLGlot·Google Gen AI SDK·JSON 사전/DB 별칭·pg_trgm을 채택했다. S-4~6은 후보 재선정이 아니라 지정 기술의 호환·안전성·품질 검증 단계다. 신규 의존성 설치/운영 적용은 미완료다.

## 1. 현재 위치와 범위

확정 결정: Vertex AI `gemini-4-argon`, 로그인 필수(활성 USER/STREAMER/ADMIN), 기존 API-Football 기반 Supabase DB 재사용, 용어/이름/별칭 연결 사전 우선. [결정 기록](../../decisions/2026-10-25-natural-language-search.md), [사전 설계 초안](dictionary-design.md)을 따른다.

- 완료한 산출물: `/search` 검색창 목업, 로딩/결과/상태 예시, 초기 API 초안, 기술 점검, 사례 조사.
- 다음 단계: 용어/엔티티 사전을 우선 구체화하고 기존 DB의 컬럼·이름/ID·집계·coverage를 읽기 전용으로 확인한다(AX-9). 새로운 축구 데이터 소스 선정·복제 작업이 아니다.
- 미구현: 검색 endpoint·이름 해석·QueryPlan·검색 전용 role/view·SQL 게이트·실제 검색 연동.
- 제외: 검색 요청에서 외부 통계 수집, 실시간 기록, 무제한 SQL/자율 실행, 검색 응답 캐시 확대, 배포.
- SQL 작성 도구가 아니라 결과 조회 서비스다. 일반 사용자에게 SQL이나 내부 오류를 노출하지 않는다.

## 2. 제안 처리 구조

사전/이름 조회의 실행 기준은 [entity-resolution.md](entity-resolution.md)다. 의미 사전 문서만으로 조회가 자동 수행된다고 가정하지 않는다. 지정 모델을 조회 담당 Retriever와 계획 담당 Planner 역할로 나누고, 그 사이 서버의 실제 사전/DB 조회·판정을 둔다.

```text
서버에서 로그인/활성 사용자 검증
→ 자유로운 질문 + 선택 조건 + 제한된 문맥
→ Retriever: 원문 표현 분석·조회 도구 선택
→ 서버 도구: catalog/정의·실제 이름 후보·관계/시즌·availability 조회
→ 서버 판정: 근거 있는 key/ID 선택 검증·모호함 확인·RetrievalBundle 구성
→ Planner: 선택된 상세 정의·실제 후보·확인 문맥으로 계획 생성
→ 확인 질문 / 미지원 판정 또는 typed QueryPlan
→ 의미·지원 범위·허용 연산 검증
→ 매개변수 SQL 조립 → AST/참조/함수/비용 검사
→ 전용 읽기 계정·pool로 제한 실행
→ 실제 조건·목록/순위/비교·링크·기준 시각·누락 상태 반환
```

이름 추출과 계획 생성의 LLM 호출 횟수는 성능 평가로 정한다. 단계가 나뉜다고 각 단계마다 LLM이나 독립 에이전트를 두는 것은 아니다. 부족한 coverage는 질문을 좁히거나 한계를 알리는 근거이며 지원 예시 문장만 허용하는 규칙이 아니다.

Retriever의 도구 결과 재입력까지 실제 LLM 호출 수에 포함한다. 역할이 둘이라고 요청당 항상 두 번 호출한다고 가정하지 않는다. 조회 라운드·도구 호출·문맥 크기와 전체 모델/DB 비용을 제한한다. 별도 모델 제품·프레임워크를 추가하는 제안은 아니다.

## 4. S-1/2 조사 산출물

사전 세부 규칙의 출발점은 [dictionary-rules.md](dictionary-rules.md)다. 확정 정책/기술과 세부 제안/후속 결정을 구분한다. 문서 작성만으로 실제 매핑·집계·coverage 검증을 완료한 것으로 보지 않는다.

[조회 실행 계획](entity-resolution.md)의 LOOKUP-1~7을 S-1/2의 원천/정의 조사와 S-4~7의 도구/모델/판정 구현으로 연결한다. 이 내부 도구 명세는 새 공개 endpoint 목록이 아니며 기존 FE-first 계약 절차를 유지한다.

운영 값을 추정해서 채우지 않는다. 결과가 생기면 다음 파일을 추가한다.

| 산출물 | 포함할 내용 |
|---|---|
| `data-audit.md` | 조사 대상/접속 식별(비밀 제외)·시각·쿼리·대회/시즌별 실제 coverage·누락·판단 근거 |
| `semantic-catalog.*` | 지표·산식·집계 단위·조건·관계·시즌·NULL·동률 정의. JSON으로 확정, 세부 schema는 S-2에서 결정 |
| `entity-resolution.md` | 현재 작성된 조회 실행 계획. 실제 데이터 확인 후 원천/검색키·도구 schema·후보 선택/오류·모델 검증 근거를 추가 |
| `examples/` | 검토된 질문·의미 조건·매개변수 SQL·근거. 생성 문맥에 사용 가능 |

공급자의 capability는 수집 가능성이고 실제 적재 완료 상태가 아니다. `updated_at`·fixture 존재·최근 로그 한 건만으로 전체 coverage를 complete로 판정하지 않는다.

## 5. API/QueryPlan에서 확정할 항목

- 검색 화면의 로그인 진입/복귀와 endpoint의 서버 인증을 요구에 추가한다. 비로그인은 401로 차단하고 LLM/검색 DB 조회를 시작하지 않는다. 기존 인증 경로를 재사용하며 활성 USER/STREAMER/ADMIN이 대상이다.
- 현재 출발점은 [FE API 초안](../../features/ax-search-mock.md)의 `POST /api/v1/search/query`다. 이 문서로 BE 계약을 선제 확정하지 않는다.
- 외부 ID와 내부 FK ID의 용도를 명확히 한다. 엔티티 후보는 실제 DB 조회 결과에 한정하고 모델이 ID를 창작하지 못하게 한다.
- 계획은 projection·filter·group·aggregate·sort·compare를 표현하며 허용 지표/관계 사전으로 검증한다. 임의 SQL/함수/식별자 문자열을 실행 허가로 취급하지 않는다.
- `results`, `clarification_required`, `no_matches`, `data_unavailable`, `unsupported`, `limited`, `failed`를 구분한다. partial coverage는 결과와 함께 표시할 수 있다.
- 적용 대회/시즌·조건·단위·집계/분모·정렬·coverage·시각·행/페이지 제한을 typed 필드로 반환한다.
- 모호한 조건은 선택 후보 또는 자유 수정으로 확인한다. 재질문 문맥 token의 범위·만료·변조 방지·입력 보존을 정의한다.
- 초기 통신은 단일 응답 HTTP로 검증한다. 로컬 로딩 문구를 실제 서버 진행 단계로 해석하지 않는다. SSE는 필요성 검토 후 별도 결정한다.
- 브라우저 취소와 서버/DB 취소의 보장 범위는 구분하고 테스트한다.

## 6. 평가 설계

### 질문군

- 조건: 출전 시간·득점·국적·포지션 등 실제 지원 지표 조합.
- 순위/집계: 도움 순위·다중 소속 합계·동률·결측.
- 비율: 최소 출전 시간과 90분당 기록·0분·NULL.
- 경기: 홈/원정·완료 상태·대회/시즌·날짜 경계.
- 비교: 같은 범위의 팀/선수 비교·집계 단위 차이.
- 재질문: `잘한 선수`, `맨체스터`, 누락된 대회/시즌, 후속 조건 수정.
- 한계: 0건·미수집·부분 수집·보관 범위 밖·실시간/미지원 지표.
- 공격/부하: 민감정보·변경 지시·위험 함수/CTE/다중 문장·고비용 조인·과도한 입력·반복 요청.

### 측정과 분리

- 정답은 SQL 문자열 일치가 아니라 조건·반환 ID·값·순서·집계·누락 상태를 기준으로 한다.
- SQL 파싱/컴파일/실행 성공, 의미적 정답, 재질문·거절의 적절성을 따로 측정한다.
- 이름/범위 해석·문맥 선택·계획·SQL·결과 표시 단계를 나누어 실패를 기록한다.
- 지연 p50/p95·LLM/DB 호출 수·토큰·요청 비용·timeout·전체 동시성을 함께 측정한다.
- 예시와 평가 세트를 분리하고 한국어 표현 변형을 포함한다. 예시 밖의 합법적 조합을 거절하지 않는지 확인한다.
- 변경 SQL·허용 밖 데이터 접근은 차단되어야 한다. 품질/지연/비용의 정량 출시 기준은 측정 전 임의 확정하지 않는다.

## 8. 작업 규칙
