# 자연어 검색 용어·엔티티 연결 사전 설계 초안

표현 정규화·실제 ID 연결·지표 집계·시즌/소속·NULL/coverage·재질문·변경/버전·평가의 상세 규칙은 [dictionary-rules.md](dictionary-rules.md)를 따른다. 이 문서는 구성 개요이며 세부 규칙/미정 사항은 상세 문서에서 관리한다.

실제 사전/이름 조회를 어떻게 수행하는지는 [entity-resolution.md](entity-resolution.md)를 따른다. 조회 담당 모델·서버 도구·검색 순서·후보 선택·다음 모델 전달 문맥을 명시한다.

작성일: 2026-10-25. 사용자가 사전의 중요성을 강조한 결정은 [결정 기록](../../decisions/2026-10-25-natural-language-search.md)을 따른다. 저장 방식은 후속 [기술 선정](../../decisions/2026-10-25-natural-language-search-stack.md)으로 JSON 정의 파일 + DB 별칭 테이블로 확정했다. 아래 필드/테이블 상세는 설계 초안이며 실제 DB 적재·검증된 별칭 시드가 아니다.

## 1. 사전의 역할

질문의 표현을 DB에서 조회할 대상·지표·범위로 연결한다. 사전이 실제 기록을 보관하거나 없는 통계를 만들어내지는 않는다. 기존 API-Football 기반 DB와 번역 테이블을 기준으로 삼는다.

```text
사용자 표현
→ 정규화한 표현과 후보
→ 엔티티 ID / 지표 key / 범위 조건
→ 모호함 확인 또는 검증된 QueryPlan
→ 기존 DB 조회
```

## 2. 세 종류의 사전

| 종류 | 연결할 내용 | 예시와 확인 과제 |
|---|---|---|
| 지표 | 한국어/영어/약어 → 지표 key·실제 컬럼/계산식·단위·집계 규칙 | 득점/골 → goals, 도움 → assists. 90분당 득점의 분모·최소 출전·NULL 처리 정의 |
| 엔티티 | 원문명·번역명·짧은 이름·별칭 → 선수/팀/대회/감독의 실제 ID | `맨유` 같은 표현을 실제 DB 팀 후보로 조회. 동명이인·여러 후보면 확인 |
| 범위/관계 | 자연어 표현 → 대회·시즌·상태·시간·소속/홈원정 조건 | 이번 시즌, 지난 시즌, 최근 5경기, 홈 경기, 당시 소속팀 |

예시는 데이터 검증 과제를 설명한다. 실제 외부 ID·집계식·별칭 채택은 DB 조사와 검토 후 확정한다.

## 3. 기존 데이터 재사용

- `player/team/league/coach`의 원문명·외부 ID·slug와 대응 번역 테이블의 `name_ko/short_name_ko`를 기본 후보명으로 사용한다.
- 검색 별칭은 번역 표시명과 분리한다. 별칭 추가가 서비스의 한국어 표시명을 바꾸지 않도록 한다.
- 모든 선수명을 프롬프트에 나열하지 않는다. DB에서 이름 후보를 조회하고 필요한 후보/ID와 지표 정의를 모델에 제공한다.
- 현재 팀만으로 과거 시즌 소속을 판정하지 않는다. 질문의 시즌과 통계/경기 관계를 이용한다.
- 별칭 후보는 축구 데이터에 실재하는 엔티티로만 연결한다. 모델이 이름이나 ID를 추측해 확정하지 못하게 한다.
- 번역 fallback과 사람 수정 보호 정책을 유지한다. 초기 사전 작업은 번역 테이블 대량 수정 작업이 아니다.

## 4. 표현 정규화와 후보 선택

1. 대소문자·공백·유니코드 등을 정규화한다. 원문은 유지한다.
2. 원문/번역명·짧은 이름·검토된 별칭의 일치를 우선한다.
3. 정확 일치 다음의 유사 후보 탐색에는 PostgreSQL `pg_trgm`을 사용한다. 운영 확장·인덱스·한국어 품질 검증 후 연결하며, 부분 일치·유사 표기는 후보 탐색으로만 사용한다. 유사하다는 이유로 한 명을 자동 확정하지 않는다.
4. 대회·시즌·관련 팀으로 후보를 좁힌다. 유효한 선수를 잘못 제외하지 않도록 당시 소속 관계를 사용한다.
5. 후보가 여럿이면 구분할 이름·팀·대회 등의 정보를 제공하고 확인한다. 후보가 없으면 지원 범위/별칭 누락/미수집 가능성을 구분한다.

`이적 선수`, `잘한 선수`, `최근 경기`처럼 이름 검색만으로 해결되지 않는 표현은 지표/범위의 의미 규칙으로 처리한다.

## 5. 관리할 메타데이터 제안

| 사전 | 필드 후보 |
|---|---|
| 지표 | key, label, 표현 목록, entity/grain, 허용 연산, unit, 검증된 컬럼/산식 참조, NULL/분모/동률 규칙, coverage 조건, version |
| 엔티티 별칭 | entity_type, 실제 entity_id, 원문 alias, 정규화 alias, 언어, 출처/검토 근거, 생성/갱신 시각, 적용 범위 |
| 범위/관계 | key, 표현 목록, 해석 규칙, 필수 문맥, 모호함 확인 조건, 검증 사례, version |

지표·범위·관계는 JSON 파일로 버전 관리하고 Pydantic으로 읽기 검증한다. 엔티티 별칭은 기존 entity FK를 유지하는 DB 별칭 테이블로 관리한다. 세부 테이블 분리/컬럼은 실제 데이터 조사와 명세에서 확정한다. 동일 별칭이 여러 엔티티에 쓰일 수 있으므로 문자열 전체 unique만으로 모델링하지 않는다. 저장 값이 SQL이면 바로 실행하지 않고 검토된 서버 로직에 연결한다.

## 6. 우선 작업과 완료 기준

1. 기존 entity/번역/통계의 필드·시즌·누락을 읽기 전용으로 확인한다.
2. 실제 질문군을 기반으로 지표 정의와 범위 규칙을 먼저 작성한다. 미수집 지표는 명시한다.
3. 기존 원문·번역명·짧은 이름을 후보명으로 활용하고, 필요한 통용 별칭을 근거와 함께 추가한다.
4. 이름·별칭·동명이인·이적/시즌 소속·표현 변형·오타의 해석을 검증한다.
5. 지표별 기준 SQL/정답을 만들고, 생성 예시와 별개의 평가 세트로 확인한다.

완료 기준은 문구 수가 아니라 실제 ID 매핑·집계 의미·모호함 확인·오답/누락 판별이 재현되는 것이다. 사전이 없다는 이유로 예시 문장만 지원하는 구조를 만들지 않는다.

## 7. SQL 파서와의 관계

사전은 ‘무엇을 뜻하는가’를 연결한다. SQL 파서는 ‘실행할 SQL이 어떤 구조인가’를 분석한다. 예를 들어 사전은 ‘90분당 득점’의 의미를 정하고, SQL 검사 계층은 허용하지 않은 테이블·함수·변경 명령이 있는지 검사한다. 파서 자체가 권한이나 정확한 집계 의미를 보장하지 않는다.
