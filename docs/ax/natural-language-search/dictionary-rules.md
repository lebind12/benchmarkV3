# 자연어 검색 사전 상세 규칙

작성일: 2026-10-25. 문서 버전: `0.1-draft`.

사용자가 요청한 사전/이름 조회의 구체 실행 계획은 [entity-resolution.md](entity-resolution.md)에 별도로 작성했다. 이 문서는 지표 의미와 후보 판정의 참조 규칙이며, 조회 담당 모델·도구·호출 순서·선택/전달 절차를 대신하지 않는다.

## 1. 적용 범위와 확정 수준

이 문서는 [사전 설계 개요](dictionary-design.md)를 구현 가능한 규칙으로 구체화하는 초안이다. 사용자 확정 정책과 이 문서의 세부 설계 제안을 구분한다.

| 구분 | 내용 |
|---|---|
| 사용자 확정 | 기존 API-Football 기반 DB, 최신 2시즌/DB 저장본 정책, 로그인 필수, Vertex `gemini-4-argon`, 사전 우선 |
| 기술 채택 | JSON 지표/범위/관계 정의 + Pydantic, DB 엔티티/번역 + 별칭 테이블, 정확 일치 우선 + pg_trgm |
| 이 문서의 규칙 초안 | 정규화·후보 확정·집계·모호함·버전·평가·운영 절차 |
| 후속 결정/검증 | 실제 지원 지표와 coverage, 세부 DB/Pydantic schema, 수정 권한, 모호한 표현의 기본값, 순위 동률/행 수 정책 |

본문의 ‘한다/금지한다’는 규칙 초안 내에서 일관되게 구현하기 위한 표현이다. 모든 세부 규칙이 사용자 승인 정책이 되었다는 뜻은 아니다. 실제 데이터 조사·정식 계약·구현·사전 적재를 완료한 기록도 아니다.

목표는 표현을 실제 엔티티·지표·조건에 연결하는 것이다. 문장 템플릿 일치만 허용하거나, DB에 없는 통계/ID를 생성하는 방식으로 구현하지 않는다.

## 2. 사전 구성과 책임

| 사전 | 저장 | 포함 | 포함하지 않음 |
|---|---|---|---|
| 지표 | JSON | key·표현·단위·집계 단위·분모·허용 연산·NULL·서버 계산 참조·coverage 요구 | 매 요청의 실제 통계값, 실행 가능한 임의 SQL/코드 |
| 엔티티 이름 | 기존 DB | 선수/팀/대회/감독의 ID·원문명·번역명·짧은 이름·slug | LLM이 추정한 엔티티·소속·표시명 |
| 엔티티 별칭 | DB | 표현→실제 엔티티 연결, 근거·문맥 범위·변경 정보 | 번역 표시명 덮어쓰기, 검토 없는 자동 확정 |
| 범위/관계 | JSON | 시즌·날짜·대회·홈/원정·당시 소속·완료 상태·필수 문맥 | 임의 기간 전체 검색, 미확인 이력 추정 |

계산 구현은 서버의 등록된 SQLAlchemy 표현식에 둔다. JSON에는 등록된 참조 key만 저장한다. 파일/별칭에 적힌 지시문을 프롬프트 명령이나 실행 코드로 취급하지 않는다.

## 3. 공통 키와 검증

### 3.1 식별자

- 지표/범위/관계 key는 이름 변경과 분리된 영문 snake_case다. 의미가 달라지면 새 key를 만든다.
- 엔티티의 서버 내부 기준은 `(entity_type, entity_id)`다. 실제 대상 테이블의 FK를 검증한다.
- API-Football의 외부 ID는 `external_id`로 구분한다. 내부 PK와 숫자가 같아도 서로 대체하지 않는다.
- 감독 등 외부 ID가 NULL일 수 있는 모델은 실제 내부 FK로 연결한다. 외부 ID를 추정해 채우지 않는다.
- slug는 링크용으로 현재 엔티티에서 조회한다. 이름이나 별칭으로 slug를 조립하지 않는다.
- 표기 수정이 엔티티 ID 변경이나 두 엔티티의 병합으로 이어지지 않게 한다. DB 중복 엔티티 정리는 별도 작업이다.

### 3.2 정의의 사용 조건

- Pydantic 구조 검증과 서버 registry 참조 검증을 모두 통과해야 한다.
- 모델/컬럼 존재 확인만으로 사용 가능하게 하지 않는다. 실제 적재·의미·집계·coverage·기준 SQL 검증이 필요하다.
- 지표가 정의되어도 대회×시즌×영역에 따라 사용할 수 없을 수 있다. 정의 버전과 데이터 가용 상태를 분리한다.
- 미등록 지표·허용 밖 관계·지원하지 않는 계산은 임의의 비슷한 지표로 대체하지 않는다.
- 상한·타입·허용 연산·필수 문맥을 검사한다. LLM의 신뢰도 점수나 자연어 설명은 검증 통과 근거가 아니다.

## 4. 표현 정규화

### 4.1 기본 검색 키

검색 전용 키에 다음 순서를 적용하는 것을 제안한다.

1. 원문 표현을 별도 보존한다. 표시명/원문을 정규화 결과로 덮어쓰지 않는다.
2. Unicode NFKC 정규화 → casefold → 앞뒤 공백 제거 → 연속 공백을 하나로 축소한다.
3. 기본 키에서는 내부 공백·하이픈·아포스트로피·발음 구별 부호를 일괄 제거하지 않는다.
4. 공백 제거/부호 변형/악센트 제거는 필요할 때 별도 보조 키 또는 검토된 별칭으로 다룬다. 그 일치만으로 자동 확정하지 않는다.
5. 제어문자·입력 길이 등은 별도 입력 검증으로 처리한다. 축구 용어처럼 보인다는 이유로 실행 문자열을 허용하지 않는다.

NFKC는 호환 문자를 합칠 수 있으므로 검색 키 용도로만 사용하고 정규화 충돌을 검사한다. 근거: [Unicode 정규화 표준](https://www.unicode.org/reports/tr15/). 실제 Python Unicode 데이터 버전과 `normalization_version`을 함께 기록한다.

### 4.2 충돌과 표현 구간

- 같은 정규화 키가 여러 엔티티/지표에 연결될 수 있다. 문자열 전역 unique를 강제해 하나를 버리지 않는다.
- 엔티티 표현과 지표 표현을 구분하고 원문 구간을 보존한다. 이름의 일부를 무조건 독립된 단어로 잘라 다른 지표에 매핑하지 않는다.
- 구/긴 이름의 일치를 먼저 후보화하되 중첩된 유효 해석을 무조건 삭제하지 않는다.
- 오타/다른 음역은 유사 후보 탐색으로 다룬다. 사용자가 선택한 표기를 새로운 영구 별칭으로 자동 등록하지 않는다.

## 5. 엔티티 이름·별칭 규칙

### 5.1 기본 이름의 출처

- 원문명, firstname/lastname가 있는 경우의 필드, 한국어 이름, 선택적 짧은 이름을 기존 DB에서 읽는다.
- 성만 있는 표현·짧은 이름·약칭은 충돌 가능성이 있다. 완전 일치라도 후보가 하나인지 확인한다.
- 원문/번역명은 기존 수집/번역 갱신 경로를 따른다. 검색용 사전이 표시명이나 사람 수정 보호를 덮어쓰지 않는다.
- 이름이 바뀌었다고 예전 이름을 영구 별칭으로 자동 보존하지 않는다. 단순 오역을 재노출할 수 있으므로 별칭 채택 근거를 남긴다.

### 5.2 수동 별칭의 연결과 근거

- 별칭은 실제 엔티티 FK에 직접 연결한다. 별칭→별칭 체인이나 모델이 제안한 미확인 ID는 허용하지 않는다.
- 기록할 정보: 원문 표현·정규화 키·entity type/ID·언어·적용 문맥·출처/이유·수정자·시각·version·활성 여부.
- `source`는 DB 원문/번역 참조, 사용자가 제공한 표현, 기사/공식/통용 사용 근거 등으로 구분한다. 근거가 없는 모델 제안은 활성화하지 않는다.
- 기사 한 곳의 표기를 유일한 정답으로 보지 않는다. 여러 표기를 같은 ID로 연결할 수 있고, 여러 ID에 쓰이는 별칭도 보존한다.
- 문맥 제한이 있는 별칭은 제한 밖에서 전역 일치로 사용하지 않는다. 명시적 이름의 시점과 별칭 적용 기간은 구분한다.
- 다른 대상 연결이 필요한 변경은 이전 연결을 무기록으로 덮어쓰지 않는다. 비활성화/새 연결과 변경 이유를 남긴다.

### 5.3 후보 생성과 확정

1. 기존 이름/검토된 별칭의 기본 정규화 정확 일치 후보를 모은다.
2. 정확 일치가 없거나 사용자가 수정을 원하면 pg_trgm/부분 일치로 보조 후보를 찾는다.
3. 한글·짧은 이름은 별도 평가한다. 낮은 유사도 후보를 채우기 위해 무관한 대상을 강제로 포함하지 않는다.
4. 명시된 entity type·대회·시즌·팀과 확인 가능한 당시 관계로 후보를 좁힌다.
5. 검증된 정확 일치 후보가 하나이고 명시 조건과 충돌하지 않을 때만 자동 연결한다.
6. 여러 후보, 유사 일치만 있는 후보, 명시 조건과 충돌하는 후보는 확인 질문으로 돌린다.
7. 표시명 출처의 우선순위나 pg_trgm 점수만으로 충돌 후보 중 하나를 정답으로 고르지 않는다.

현재 소속으로 과거 시즌 선수를 제외하거나, 소속 자료가 없다는 이유로 관계가 없다고 단정하지 않는다. `후보 없음`을 `그런 선수/팀은 존재하지 않음`으로 답하지 않는다.

### 5.4 확인 질문

- 원문 표기·표시명·팀/대회/시즌 등 구분 가능한 공개 정보와 실제 후보 ID를 제공한다.
- 사용자는 후보 선택뿐 아니라 이름/질문을 직접 고칠 수 있다. ‘다른 대상’ 경로를 둔다.
- 선택은 해당 사용자/질문 문맥에만 적용한다. 이후 다른 질문이나 다른 사용자의 별칭 매핑을 바꾸지 않는다.
- 대회/시즌과 모순되는 선택은 해석을 다시 확인한다. 묻지 않고 다른 대회로 변경하지 않는다.

## 6. 지표 정의 규칙

### 6.1 지표별 필수 정의

| 필드 | 규칙 |
|---|---|
| `key`, `label`, `terms` | 안정된 식별자·표시명·동의어/약어. 표현 충돌 시 필요한 문맥도 정의 |
| `entity_type`, `source_grain`, `result_grains` | 원천 한 행의 의미와 허용 결과 단위 구분 |
| `source_ref`, `expression_ref` | 검토한 컬럼/서버 표현식 registry key. 임의 SQL 아님 |
| `unit`, `value_type`, `display` | 골/회/분/% 등 단위, 숫자 타입, 표시 반올림 |
| `operators` | 비교·정렬·집계·비율 등 허용 연산. 알 수 없는 연산 차단 |
| `aggregation` | 합계/가중/비집계 등 검증된 방식, 중복 제거 기준 |
| `null_policy`, `denominator` | 누락·0·분모·최소 자격 조건, 필요한 확인 질문 |
| `required_context`, `coverage_requirements` | 대회·시즌·대상·데이터 영역 요구 |
| `version`, `enabled`, `evidence`, `tests` | 변경/사용 상태·기준 SQL/검증 근거 |

| 부상/소속 | 현재 플래그·소속·부상/이적 관련 테이블 | 현재 상태로 과거 상태를 추정하지 않음. 이력 coverage 확인 |

### 6.3 집계 단위와 중복

- 선수 시즌 원천 행은 `(player, team, league, season)`이다. 기본 합계는 같은 대회/시즌의 검증된 팀별 기록을 합치는 경우에만 허용한다.
- 팀 조건이 있으면 해당 팀 기록만, 전체 선수 시즌 합계면 당시 팀 기록을 합산하고 결과의 소속 표현을 별도로 정한다.
- 상세 fixture·이적·라인업·별칭은 일대다 관계일 수 있다. 조인으로 같은 통계 행이 여러 번 늘어나지 않도록 사전 집계/관계/EXISTS 등 검증된 조립을 사용한다.
- `DISTINCT`를 무조건 붙여 중복 문제를 감추지 않는다. 의도한 기본키와 집계 단위를 검증한다.
- 시즌 누적 snapshot과 경기별 기록을 중복 합산하지 않는다. 최신 snapshot의 선택 근거와 출처를 정의한다.
- 평점/비율처럼 비가산 지표에 SUM을 허용하지 않는다. 서로 다른 공급자/정의의 값을 같은 지표로 혼합하지 않는다.
- 대회가 여러 개면 명시적으로 구분/합산한다. 시즌 번호가 같다는 이유로 같은 기간이나 같은 대회로 취급하지 않는다.

### 6.4 NULL·0·부분 집계

- 수집된 실제 0과 미수집 NULL은 다르다. 검색/집계 전에 일괄 `COALESCE(..., 0)` 하지 않는다.
- 모든 입력이 NULL이면 결과는 누락이다. 일부만 알려진 경우 전체 합계/평균이 아니라 불완전한 값으로 다룬다.
- 신뢰 가능한 부분 결과를 보여줄 때 실제 알려진 범위·제외 수·누락을 함께 표시한다. 전체를 대표할 수 없는 비교/비율은 계산을 보류한다.
- 예상 대상 수를 모르면 complete 비율을 만들지 않는다. 기대/적재/유효값 수를 구분하고 모르는 값은 unknown으로 둔다.
- `0건`은 수집된 조회 가능 범위 안에서 조건에 맞는 대상이 없다는 뜻이다. 미수집/전체 NULL을 0건으로 바꾸지 않는다.
- 도움 수가 NULL인 선수는 ‘도움 0회’ 조건에 포함하지 않는다. `> 0` 조건에서 제외되어도 누락 상태는 보존한다.

PostgreSQL의 SUM/AVG는 NULL을 제외하므로 별도 coverage 처리가 필요하다. 근거: [집계 함수 공식 문서](https://www.postgresql.org/docs/current/functions-aggregate.html). 이 SQL 동작을 완전성 판단 규칙으로 대체하지 않는다.

### 6.5 파생 지표·비율·평균

- 계산식은 사전에서 승인한 서버 expression에만 연결한다. LLM이 새 공식을 만들지 못하게 한다.
- `90분당 득점`의 제안 정의는 `득점 × 90 / 실제 출전 분`이다. 분모 0/NULL이면 계산하지 않는다. 최소 출전 자격은 별도 조건이다.
- 최소 출전 시간을 사용자가 지정하면 그대로 검증한다. 서비스 기본값이 합의되지 않은 상태에서 900분 등을 임의 삽입하지 않는다. 순위가 크게 달라지면 최소 자격을 확인한다.
- 합산 per90은 유효한 동일 범위의 합계 득점/합계 분으로 계산한다. 팀별 per90의 단순 평균을 사용하지 않는다.
- 백분율은 분자/분모가 같은 대상·기간·대회인지 검사한다. 분모/기록의 불완전성이 결과를 왜곡하면 보류한다.
- `평균`은 경기당·출전당·분당 등의 분모를 확인한다. 공급자 평점 평균은 별도 정의가 없으면 재집계하지 않는다.
- 계산/정렬은 원래 정밀도로 하고 반올림은 표시 단계에 적용한다. 표시값이 같다고 통계적으로 동률이라고 단정하지 않는다.
- 시즌 간 증가율에서 직전 값이 0이면 무한대 등으로 표시하지 않는다. 차이와 증가율을 구분해 확인/안내한다.

## 7. 범위·시즌·관계 해석

### 7.1 조건 우선순위

1. 이번 요청에서 사용자가 명시한 조건.
2. 사용자가 확인한 현재 대화 조건 중 이번 요청과 모순되지 않는 것.
3. 별도로 확정·공개한 서비스 기본값.
4. 결과가 달라질 수 있는데 위 근거가 없으면 재질문.

명시 조건과 문맥이 충돌하면 새 조건을 우선하고 이전 조건을 해제/수정했음을 표시한다. 서로 모순되는 새 조건은 확인한다. 모델의 친숙도·인기 팀·로그인 사용자라는 사실만으로 기본 대회를 추정하지 않는다.

### 7.2 시즌·날짜

- `이번 시즌`은 확인된 대회의 current 시즌, `지난 시즌`은 그 대회의 실제 직전 시즌이다. 컵/국가대항 대회에 `연도-1`을 일괄 적용하지 않는다.
- `2026년`과 `2026/27 시즌`은 다른 범위다. 달력 연도 필터와 시즌 필터를 구분한다.
- 대회 생략 시 해석이 여러 개면 확인한다. `EPL`처럼 대회가 확정되어도 current 시즌 정보가 없으면 추측하지 않는다.
- 요청 시작 시 기준 시각과 사용자에게 표시할 시간대를 고정한다. 날짜 표현의 기본 시간대는 서비스 KST 정책을 따른다.
- 같은 요청의 조건 해석 중 날짜가 바뀌어도 기준 시각을 다시 계산하지 않는다. 날짜 범위는 경계 포함/제외를 명시한다.
- 최신 2시즌 밖 요청은 범위 제한을 알린다. 가까운 시즌으로 조용히 대체하지 않는다. 시즌 교체 후 만료된 후속 문맥도 재검증한다.

### 7.3 경기·소속

- `최근 5경기`의 대회 범위가 모호하면 확인한다. 확정 범위에서 기준 시각 이전의 완료 경기를 시간순으로 선택한다.
- 5경기 미만이거나 경기 coverage가 부족하면 실제 확인 가능한 수와 한계를 표시한다. ‘수집된 최근 5경기’를 실제 전체 최근 5경기로 단정하지 않는다.
- 완료 상태는 DB 상태 코드와 공급자 의미를 검증한 allowlist로 정한다. 취소/연기/중단/부전승 등의 처리를 임의로 완료 경기와 합치지 않는다.
- 경기 득점에서 승부차기·연장 포함 여부는 지표 정의에 둔다. 이름이 비슷한 점수 컬럼을 혼용하지 않는다.
- `홈 경기`는 fixture의 home team 관계다. 중립 구장 등 별도 개념은 실제 필드/coverage가 없으면 만들어내지 않는다.
- `팀 소속 선수`는 현재/해당 시즌/경기 당시 소속을 구분한다. 현재 팀 하나로 과거를 판정하지 않는다.
- 감독의 first/last seen이나 이적 row만으로 완전한 재임/계약 기간을 추정하지 않는다. 이력 coverage가 부족하면 알린다.

### 7.4 비교

- 비교 대상·지표·시즌·대회·범위·분모를 맞춘다. 한 팀은 전체 시즌, 다른 팀은 최근 경기로 조용히 비교하지 않는다.
- 시즌 간 비교는 실제 양쪽 데이터와 같은 지표 버전을 요구한다. 다른 팀 소속 이력의 범위를 명시한다.
- 대회 간 비교를 명시하면 대회별 조건/시즌/경기 수/한계를 구분한다. 임의의 난이도 보정 점수를 만들지 않는다.

## 8. 정렬·순위·결과 수 — 제안 규칙

- 정렬 지표·방향과 동률 기준을 구조화된 응답에 남긴다. 별도 요청이 없으면 순위 질문은 해당 지표의 큰 값 우선으로 해석한다. 실점 적은 순처럼 방향이 명시되면 이를 따른다.
- NULL은 순위 경쟁에서 제외하고 제외 범위를 표시한다. 0으로 치환해 최하위에 넣지 않는다.
- 동일한 원시 지표 값은 공동 순위로 취급하는 것을 제안한다. 표시 순위는 `1, 1, 3` 방식, 행 위치와 공동 순위는 별개다. 최종 동률 방식은 후속 결정 표에서 확정한다.
- 재조회/페이지 처리를 위해 동률 안에서는 실제 entity ID 등 안정된 보조 정렬을 사용한다. 보조 정렬은 경기력 우열을 뜻하지 않는다.
- `상위 10명`(행 수)과 `10위까지`(공동 순위 포함)를 구분한다. 공동 순위가 행 제한을 넘으면 잘림/다음 페이지를 표시한다. 제한을 무시해 무제한 반환하지 않는다.
- 비교/순위의 정확도를 위해 대회·그룹·집계 단위가 다른 결과를 한 순위에 섞지 않는다.
- 최신화 중 페이지 결과의 중복/누락 방지와 페이지 token의 데이터 기준은 API/DB 설계에서 정한다. 안정된 정렬만으로 서로 다른 시점의 snapshot이 같아진다고 보지 않는다.

## 9. 재질문과 답변 불가 구분

| 상황 | 응답 상태/행동 | 금지할 행동 |
|---|---|---|
| 한 이름에 여러 후보 | `clarification_required`, 후보+직접 수정 | 인기/현재 소속으로 추측 확정 |
| ‘잘한 선수’ 등 지표 모호 | `clarification_required`, 지원 지표 선택 | 임의 종합 점수 생성 |
| 대회/시즌/분모가 결과를 바꿈 | `clarification_required`, 빠진 조건만 확인 | 이미 확인한 조건 반복 질문 |
| 이름 후보 없음 | 현재 가능한 후보 수정/지원 범위 안내 | 엔티티 비존재 단정, 새 ID 생성 |
| 지표/연산/기간을 지원하지 않음 | `unsupported`, 가능 범위 설명 | 비슷한 지표/기간으로 몰래 대체 |
| 지표는 지원하지만 데이터 없음 | `data_unavailable` | 0 또는 0건으로 답변 |
| 부분 수집에서도 유효한 제한 결과 가능 | `results` + partial/unknown coverage와 한계 | 전체 리그/선수를 대표한다고 표현 |
| 확인된 조회 가능 범위에 일치 없음 | `no_matches` | 누락값을 근거로 불일치 판정 |
| 시스템/모델 장애·예산/시간 제한 | `failed` 또는 `limited` | 통계·이유를 창작하거나 사전 오류로 단정 |

이름 후보 없음의 구체 reason code와 상태는 FE 계약 단계에서 확정한다. 현재 상태 enum에 임의 새 항목을 추가하지 않는다. 여러 질문이 필요하면 결과를 가장 많이 바꾸는 조건부터 묻고 나머지 입력은 보존한다.

## 10. JSON과 별칭 데이터 형식 예시

아래는 문서용 계약 초안이다. 운영 JSON 파일·Pydantic schema·실제 데이터 시드가 아니다. `enabled: false`는 실제 데이터와 SQL 검증 전 사용하지 않는다는 의미다.

```json
{
  "schema_version": "0.1-draft",
  "catalog_version": "draft-20261025-1",
  "normalization_version": "nfkc-casefold-space-v1",
  "metrics": [
    {
      "key": "player_goals",
      "label": "득점",
      "terms": ["득점", "골", "goals"],
      "entity_type": "player",
      "source_grain": ["player", "team", "league", "season"],
      "result_grains": [["player", "league", "season"]],
      "source_ref": "player_season_stat.goals",
      "expression_ref": "player_goals_sum_v1",
      "unit": "골",
      "value_type": "integer",
      "operators": ["eq", "gte", "lte", "sort", "sum"],
      "null_policy": "preserve_and_report_coverage",
      "required_context": ["league", "season"],
      "coverage_requirements": ["player_season_stats"],
      "enabled": false,
      "version": 1,
      "evidence": ["orm_column_confirmed", "db_audit_pending"],
      "tests": ["multi_team_sum", "null_is_not_zero", "no_join_multiplication"]
    }
  ]
}
```

`expression_ref`가 서버에 없거나 기대하는 grain과 다르면 로딩/실행을 거부한다. 위 예시는 모든 필수 필드의 최종 타입을 고정한 schema가 아니며 나머지 표시·집계·상태 상세는 계약 시 확정한다.

별칭의 최소 논리 필드는 `entity_type`, 내부 FK, `alias`, `normalized_alias`, `locale`, 문맥 범위, 출처/이유, 활성 여부, version, 생성/수정 정보다. 이 구조를 한 개의 다형 FK 문자열로 구현해 참조 무결성을 포기하지 않는다. entity별 테이블/FK 구성은 BE 명세에서 결정한다.

## 11. 사전 생성·수정·게시 절차

### 11.1 지표/범위 JSON

1. 현재 실제 필드·원천 단위·coverage를 조사한다.
2. 정의와 서버 expression을 함께 작성하고 기준 SQL/정답을 검토한다.
3. JSON/Pydantic·registry 참조·충돌·연산/관계·NULL/중복 회귀 검증을 수행한다.
4. 검증된 버전만 활성 release로 게시한다. 개발 초안·미지원 지표를 LLM의 사용 가능 목록에 섞지 않는다.
5. 변경은 코드 리뷰/명시적 결정 기록과 함께 관리한다. 사람 검토 역할의 구체 운영 절차는 후속 결정한다.

### 11.2 이름/별칭

1. 기존 원문·번역명을 후보명으로 활용한다. 미번역이면 영문 fallback을 유지한다.
2. 추가 별칭은 실제 엔티티·근거·충돌·문맥을 확인한다. 자동 추출은 제안 데이터까지만 허용한다.
3. 등록/수정/비활성화는 변경 전후·이유·행 version을 남긴다. 동시 수정은 expected version 불일치로 덮어쓰기를 막는다.
4. 특정 사용자의 후보 선택/검색 실패만으로 전역 별칭을 자동 추가하지 않는다.
5. 수집·자동번역·import가 수동 별칭을 무단 변경하지 않게 한다. 외부 엔티티 제거 시 참조/보관 처리는 실제 FK 정책으로 정한다.

### 11.3 권한 제안과 범위

- 확정: 실제 검색 사용은 활성 USER/STREAMER/ADMIN 로그인 필요. 기존 번역 수정은 STREAMER/ADMIN 정책을 따른다.
- 제안: 별칭 수정은 STREAMER/ADMIN, 일반 USER는 검색/후보 선택만 허용한다. JSON 지표/산식 변경은 코드 리뷰 경로로 제한한다.
- 미정: 누가 사전 변경을 담당하는지, 자동 추천 검토·제보 수집·관리 UI 제공 여부. 이 문서만으로 관리 endpoint/UI를 추가하지 않는다.
- 별칭의 활성/비활성 및 내부 변경 절차는 번역 화면의 별도 ‘검수 완료’ 상태를 신설하는 결정이 아니다.

## 12. 버전·요청 일관성·재현

- schema/정의 내용·정규화 정책·서버 expression·별칭 변경을 식별할 수 있게 버전 관리한다.
- 요청 시작에 사용할 지표/범위 catalog 버전을 고정한다. 처리 중 파일 갱신을 부분 적용하지 않는다.
- 별칭/번역 후보는 조회 시점의 ID·값·행 version을 보존한다. LLM 대기 동안 snapshot 유지를 이유로 DB 연결/트랜잭션을 붙잡지 않는다.
- 후속 확인/실행 때 ID·활성 대회/2시즌·선택 조건을 서버에서 다시 검증한다. 별칭이 다른 대상으로 변경됐다면 변경을 감지하고 재질문한다.
- 대화 조건 token은 사용자·질문 흐름에 연결하고 만료/변조를 검증한다. 사용자가 새 검색을 시작하면 이전 해석을 초기화한다.
- 진단 기록에는 model ID·prompt/QueryPlan schema·catalog/expression/normalization 버전·선택 엔티티·실제 조건·data_as_of·coverage를 남기는 구조를 설계한다.
- 버전 정보만으로 바뀐 운영 데이터 전체를 복원할 수 있다고 주장하지 않는다. 결과 시점 재현은 별도 snapshot/최소 결과 보관 정책에서 정한다.
- 질문 원문/후보명/SQL을 무제한 보관하거나 일반 사용자에게 내부 SQL·schema를 노출하지 않는다. 로그 범위/보관 기간은 API 운영 설계에서 정한다.
- 사전 변경 rollback은 이전 release로 가능하게 설계하되, 바뀐 DB schema와 호환되지 않는 과거 정의는 활성화하지 않는다.

## 13. 검증 예시와 완료 기준

아래 입력은 평가 설계용이다. 테스트에서 실제 또는 격리 fixture의 대회/시즌/엔티티를 채워 정답을 고정한다. 예시에 등장한다는 이유로 운영 지원이 확정되지는 않는다.

| 검증군 | 입력/상황 | 기대 |
|---|---|---|
| 기본 매핑 | 동일 선수의 원문·한글 표기 | 같은 실제 내부 ID |
| 정규화 | 대소문자·전각·결합 문자·연속 공백 변형 | 정책에 맞는 후보와 원문 보존 |
| 이름 충돌 | 같은 성/짧은 이름의 선수 2명 | 후보 확인, 임의 선택 금지 |
| 별칭 충돌 | 한 표현이 팀/선수 또는 두 팀에 연결 | 문맥으로 구분하거나 재질문 |
| 유사 일치 | 오타로 후보 하나만 검색 | 자동 확정 대신 후보 확인 |
| 누락 | 이름 후보가 전혀 없음 | 존재하지 않는다고 단정하지 않음 |
| 이적 | 한 시즌 두 팀 통계, 현재 팀은 별도 | 팀 조건/시즌 합계 정확, 현재 팀으로 과거 제거 금지 |
| 조인 중복 | 선수에게 별칭/이적 row가 여러 개 | 합계가 배수로 증가하지 않음 |
| NULL/0 | 도움 NULL과 0 선수 혼재 | 0회 필터/순위에서 구분 |
| 부분 합계 | 팀별 통계 한 행의 값 누락 | 완전한 시즌 합계로 표시 금지 |
| per90 | 분모 0/NULL·두 팀·최소 출전 미지정 | 계산 차단/정확 합산/필요 조건 확인 |
| 평점 | 다중 팀 평점이나 일부 누락 | 임의 합계/가중치 생성 금지 |
| 시즌 | 이번/직전·달력 연도·시즌 경계·범위 밖 | 실제 대회 시즌 검증/구분/제한 안내 |
| 최근 경기 | 경기 일부 미수집·완료 여부 불명 | 전체 최근 5경기라고 단정하지 않음 |
| 동률 | 원시 값 동률/반올림만 같음 | 원시값 기준 순위와 안정적 행 정렬 |
| 비교 | 한쪽 기간·분모·coverage 불일치 | 공통 범위 확인 또는 한계 표시/보류 |
| 표현 확장 | 예시 밖 유효 지표/조건 조합 | 사전/조립 지원 범위면 처리 |
| 사전 변경 | 후보 확인 후 별칭/정의 변경 | 오래된 매핑/허용 범위 재검증 |
| 지시문 | 별칭/질문에 SQL·내부 지시 포함 | 데이터 취급, 허용 registry 밖 실행 차단 |

예시 SQL과 독립 평가 세트를 분리한다. 사전 변경 때 이름/조건·기준 SQL 결과 ID/값/순서·재질문·누락 상태 회귀를 다시 실행한다. 문법 통과율·엔티티 연결 정답률·조건/집계 정답률은 따로 측정한다.
