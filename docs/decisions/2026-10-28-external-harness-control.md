# 요구사항 구체화와 외부 실행 제어 도입

상태: 사용자 직접 수정 지시에 따라 로컬 활성 파일에 반영. 실제 개발에서의 효과 평가는 사용 후 피드백으로 진행한다.

## 문제와 비교

사용자는 개발 중 요구사항 누락·임의 범위 축소, 추상적 요청을 구체화하지 않고 구현하는 현상, 그리고 그 원인이 하네스여도 보완되지 않는 문제를 제기했다.

| 항목 | 기존 운영자 중심 하네스 | 조사한 외부 제어 방식 | 이번 반영 |
|---|---|---|---|
| 요구사항 | 운영자가 계획·브리프 작성 | 원문과 실행 계약 보존 | 원문 인용 → 요구사항 → 수용 시나리오 → 검증 명령 연결, 중요한 미정 사항 차단 |
| 작업 시작 | 대화 지침 준수에 의존 | 코드가 진입 조건 확인 | 구조 검사와 별도 읽기 전용 명세 검토 후 개발 실행 |
| 단계/완료 | 에이전트가 실행하고 상태 도구에 보고 | 엔진이 실행·결과 수집·전환 | 실제 Codex 프로세스와 검증 명령을 실행하고 코드/로그 지문에 연결 |
| 운영 에이전트 | 현재 대화가 기획·조율·승인 | 별도 모델 또는 외부 프로그램 | 현재 대화는 사용자와 기획, 일반 프로그램은 필수 전환/완료 권한 |
| 범위 축소 | 지침과 검토 | 원본 명세와 변경 권한 분리 | 후속 사용자 메시지와 정확한 계약 digest를 연결, 기존 PASS 무효화 |
| 이상현상 | 별도 개선 절차 | 관찰·실패 기록·수정 반복 | 실행 이력과 사용자 feedback 보존, 코드/환경/하네스 원인 구분 |

별도 관리자 모델을 하나 더 추가하는 것과 실행 권한을 프로그램으로 옮기는 것은 다르다. 독립 검토 세션은 누락 판단에 활용하지만 테스트 실패를 PASS로 바꾸거나 완료 상태를 직접 변경할 수 없다. 외부 엔진 역시 불충분한 명세·테스트의 의미까지 보장하지는 않는다.

## 근거와 한계

- [Reddit 개발자 경험담](https://www.reddit.com/r/ClaudeAI/comments/1saxm4z/i_tried_letting_ai_orchestrate_ai_heres_why_i/): AI 오케스트레이터에서 결정론적 작업 흐름으로 전환한 사례. 40%→0% 수치는 콘텐츠 파이프라인의 본인 보고이며 소프트웨어 품질에 대한 통제 실험이 아니다. 댓글의 LangGraph 개발 파이프라인도 경험담이다.
- [Anthropic의 장기 실행 앱 하네스 설계](https://www.anthropic.com/research/harness-design-long-running-apps): 기획·생성·평가 역할 분리, 요구사항과 실제 동작의 확인을 참고했다. 특정 구성·모델·비용 조건의 결과를 이 프로젝트 성과로 일반화하지 않는다.
- [LangChain 하네스 엔지니어링](https://www.langchain.com/blog/improving-deep-agents-with-harness-engineering): 완료 전 확인, 컨텍스트와 실행 환경 조정의 중요성. 여러 변경을 함께 적용한 결과이며 리마인더 자체가 외부 완료 권한을 뜻하지는 않는다.
- [Magentic-One 논문](https://arxiv.org/html/2411.04468v1): 목표·진행 원장을 사용하는 관리 구조를 참고한다. 관리 모델의 유용성과 결정론적 완료 강제력은 별개다.
- [Microsoft Durable 에이전트 패턴](https://learn.microsoft.com/en-us/azure/durable-task/sdks/durable-agents-patterns), [LangGraph 설계 안내](https://docs.langchain.com/oss/javascript/langgraph/thinking-in-langgraph): 코드가 정한 흐름 안에서 모델의 구현 판단을 활용한다.

단일 로컬 프로젝트에서는 Python 표준 라이브러리 상태 머신, SQLite, 설치된 Codex CLI로 시작한다. 별도 서버·분산 실행이 필요해질 때 LangGraph/Temporal 등을 재검토한다. 설치된 CLI의 help와 구조화된 출력 형식을 기준으로 연결했으며, 이번 반영 과정에서 실제 모델 실행은 하지 않았다.

## 사용자 후속 결정

사용자는 기존 하네스가 자기 수정의 개발·검증을 통제하는 절차에 이의를 제기한 뒤 다음과 같이 지시했다.

> 아뇨 그냥 하네스를 무시하고 기획한 하네스를 완전반영하는 것을 목표로 진행해주세요. 테스트는 제가 직접 개발을 진행해보면서 수정을 요청하거나 체감해보는게 제일 효과적인거 같아서

따라서 **이번 직접 요청한 전환**에는 기존 FULL 배정·하네스 후보 평가·추가 digest 승인 절차를 적용하지 않는다. 기존 파일을 보존한 격리 작업 공간에서 구현한 뒤 활성 파일에 반영한다. 문법·import·도움말 연결만 확인하고, 행동 실험·독립 테스트·실제 모델 호출·효과 수치 측정은 하지 않는다. 사용자가 실제 개발을 진행하며 개선을 요청하는 방식으로 평가한다.

이 지시는 앞으로 자동 생성되는 모든 하네스 후보의 무제한 수정 승인이나 배포 허가가 아니다. 미래의 사용자 직접 수정 요청도 해당 최신 지시를 따른다. 일반 자동 개선 후보에는 기존 사람 승인 경계가 남는다.

## 적용 범위와 현실적인 경계

- 새 정본: `docs/spec/agentic-workflow.md`, `scripts/harness-run.sh`, `scripts/harness_runtime/`.
- 요구사항/검토 스키마, 역할 지침, 작성 템플릿, 실행 안내를 함께 전환한다. 기존 상태와 과거 검증 보고서는 이력으로 보존한다.
- 제어 런타임과 상태는 개발 workspace 밖에 보존하고, 개발·검토·검증은 별도 제한 프로세스에서 실행한다. 같은 OS 사용자로 샌드박스 밖에서 직접 파일을 고치는 공격까지 인증·차단하는 서비스는 아니다.
- 엔진 진입점을 이용한 작업의 공식 완료만 제어한다. native 대화의 final 응답을 가로채는 전역 훅을 설치한 것이 아니다.
- 자동 merge/push/배포가 없다. 다른 세션의 checkout·인덱스·기존 변경을 보호한다.

실행 방법: [외부 제어 안내](../harness/external-control.md).
