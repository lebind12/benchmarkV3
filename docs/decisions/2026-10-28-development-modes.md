# 2026-10-28 개발 진행 방식 구분

## 사용자 요청과 결정

사용자는 간단한 수정과 기획·기능 계획부터 개발까지의 전체 파이프라인을 구별하고, 개발 전에 진행 방식을 물어 작은 작업에 전체 절차를 사용하지 않도록 요청했다. 새 독립 개발 요청은 QUICK / FULL 중 사용자 선택을 받은 뒤 구현한다. 기존 요청에서 방식이 명시됐거나 같은 작업을 이어가는 경우 다시 묻지 않는다.

- **QUICK:** 범위가 명확한 기존 기능의 국소 수정. 목표·범위·완료 기준을 짧게 확인하고 구현·적절한 검증·짧은 결과 보고로 진행한다. 운영자가 직접 처리하거나 필요한 개발자만 배정한다. 동작 변경·회귀 우려는 독립 테스트 담당자가 검증한다. 낮은 영향의 문구·문서·스타일 수정은 운영자 확인으로 완료할 수 있다.
- **FULL:** 서비스 기획, 기술 조사, 기획 검증, 기능별 작업 계획, 개발, 독립 동작 검증, 운영자 검토·머지 흐름이다. 유효한 기존 계획·조사 근거는 재사용한다.

QUICK은 기획 역할 전체, 서비스 계획, 기능 명세, 정형 보고서, work-flow 상태, 커밋 또는 포트폴리오 생성을 요구하지 않는다. 중요한 결과는 서비스 단위 이정표에서 다시 활용한다. 새 기능·요구사항·DB 구조·권한 정책·외부 연동 등으로 범위가 커지면 확장 구현 전에 FULL 전환 또는 원래 범위 유지에 대한 선택을 받는다. FULL의 검증 실패를 QUICK으로 바꾸어 우회하지 않는다.

## 기존 하네스와의 관계

`work-flow`는 FULL의 커밋·독립 테스트·운영자 머지 판단을 검증하는 도구로 유지한다. QUICK 상태를 끼워 넣어 기존 조건을 약화하지 않는다. 선택적 완료 어댑터도 FULL에만 연결한다. QUICK 완료는 MERGED 기록이 아니다. 진행 방식 질문·선택 확인은 운영자의 대화 절차이며 CLI가 자동으로 묻거나 인간 응답을 인증하는 기능은 아니다.

운영 정본은 [작업 흐름](../spec/agentic-workflow.md)이다. 2026-10-28 [초기 운영자 하네스 결정](2026-10-28-operator-led-harness.md)의 모든 신규 작업에 work-flow를 적용하는 부분은 이 후속 결정으로 대체한다. 모델·추론·속도 정책은 유지한다.

도메인, FE→BE 순서, worktree, 배포 제한은 두 방식에 동일하게 적용한다. 자동 발견한 하네스 후보에는 별도 재현·비교·실제 사용자 승인이 계속 필요하다. 이번 변경은 사용자가 직접 요청한 운영 규칙 편집이며, 향후 후보에 대한 일괄 승인은 아니다.
