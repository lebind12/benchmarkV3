# 2026-10-28 사용자 승인형 하네스 개선

## 사용자 결정

참조 대화 「하네스 설계 개선 사례」의 설계를 사용자가 본 대화에 직접 제공했다. 단일 benchmark 프로젝트에서 개발 중 하네스 문제를 관찰·진단하고, 별도 에이전트가 개선 후보를 생성하며, 기준본/후보본 비교 및 회귀 검증 후 **사용자 명시적 승인**을 받아 적용한다. 거절하면 기존 버전을 유지하고 승인된 개선과 재현 사례는 이력으로 축적한다.

운영 환경은 현재 Codex Desktop 대화와 하위 에이전트다. 기존 운영자는 서비스 기획·조율·코드 머지를 담당한다. 운영자 에이전트의 서비스 머지 승인과 실제 사용자의 하네스 채택 승인은 별개의 결정이다. 이번 구현 요청은 개선 시스템 구축 허가이며 이후 생성되는 개별 후보의 일괄 승인으로 해석하지 않는다.

## 저장소에 맞춘 적용

- 기존 `.codex/agents`, `.codex/config.toml`, 루트 `AGENTS.md`, work-flow CLI는 유지한다. `.harness/`는 이 실제 경로와 후보 편집 범위를 정의하며 활성 지침을 이중 복제하지 않는다.
- `.harness-engineering/`에 관찰·진단·동결 평가·후보·사용자 결정·적용/복구 이력을 분리한다.
- inspector는 개발자와 분리하고, optimizer와 evaluator도 분리한다. 역할은 GPT-6.1 Sol medium을 기본으로 하며 단순 요약·정리는 기존 Terra/Luna 정책을 따른다.
- 직접 수집한 Codex 관찰과 서비스 작업 기록을 사용한다. 내부 추론이나 모든 도구 이벤트의 자동 수집을 구현한 것으로 주장하지 않는다.
- 후보는 격리 worktree에서 만들고 기준본은 그대로 둔다. 활성 파일과 평가 기준·승인 장치는 후보 편집 대상에서 제외한다. MVP는 허용된 기존 정규 파일의 내용 수정만 지원한다.
- 문법·문자열 검사만으로 에이전트 행동이 개선됐다고 판단하지 않는다. 실제 행동 비교 근거, 동일 조건과 필수 회귀 사례를 요구한다. 증거가 부족하면 승인 요청으로 진행하지 않는다.
- 사용자 승인에는 정확한 후보와 평가 결과의 digest를 연결한다. 운영자가 실제 사용자 메시지를 확인한다. CLI JSON은 이 근거를 연결하는 기록이며 신원 인증 수단이 아니다.
- 실제 적용은 허용 파일만 대상으로 하고 변경된 기준본을 덮어쓰지 않는다. 복구는 별도 사용자 승인과 현재 파일 일치 확인 후 진행한다.

## 범위 구분

AHE의 관찰·구성요소 편집·예측/평가 연결을 참고한다. ACE/GEPA는 보조 연구 근거다. 논문의 무인 최적화, 모델 학습, 공식 벤치마크 성과를 재현했다고 주장하지 않는다. 상세는 [연구 검토](../harness/self-improvement-research.md)와 [실행 명세](../spec/harness-self-improvement.md)를 따른다.

서비스 코드·환경 결함은 기존 개발 흐름에서 다룬다. 이 변경으로 원격 push, 배포, 운영 DB 변경, 외부 게시 권한이 생기지 않는다. 새 하네스 적용 후 서비스 작업을 재개할 때 기존 목표·코드·검증 결과의 유효성을 다시 확인한다.
