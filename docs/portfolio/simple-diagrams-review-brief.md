## 사용자 추가 요청: README 자체의 품질과 프로젝트 진입점

사용자가 “readme 파일에 대한 검토도 필요한데, 메인 readme 파일에 대해서는 프로젝트의 readme인지를 검토하도록 해야합니다”라고 명시했다. 그림 평가와 함께 다음 문서 평가를 추가한다. 이미 끝낸 그림 평가는 반복하지 않는다.

- `/Users/woolee/benchmark/README.md`: 최우선 평가 대상. **프로젝트 README로 적합한가**를 별도 판정한다. 단순 문서 목차 또는 내부 작업 보고서에 그치지 않는지 확인한다.
- `docs/portfolio/README.md` 및 각 기능·배포 README: 처음 읽는 사람이 기능의 목적·구현·근거를 이해하는지, root와 상세 문서의 역할이 나뉘는지 확인한다. 이번 새 그림이 없는 기능도 문서 텍스트는 포함한다. 기존 프리뷰 그림 재심사는 하지 않는다.

메인 README 평가 질문:

1. 첫 문단에서 무엇을 누구에게 제공하고 어떤 문제를 해결하는 프로젝트인지 알 수 있는가?
2. 사용자 관점의 주요 기능과 이용 흐름, 서비스 접근 위치가 초반에 드러나는가?
3. 기술 스택·전체 구조를 짧게 파악하고 상세 문서로 이동할 수 있는가?
4. 소스를 확인하거나 실행하려는 독자에게 구현 브랜치·선행 환경·검증된 실행 안내의 진입점이 있는가? 현재 main에 앱 소스가 없는 사실을 숨기지 않고 설명하는가? 실행 안내가 부족하더라도 확인하지 않은 설치·실행 명령을 만들어 제안하지 않는다.
5. 내부 SHA·작업 이력·주의 문구가 프로젝트 설명보다 앞서거나 과도한 분량을 차지하는가? 과거 기록을 보존하되 어디로 옮기면 좋을지 제안한다.
6. 미구현 뉴스 관리·자연어 검색을 구현된 기능으로 보이지 않게 유지하는가? 측정하지 않은 성능·보안·운영 성공을 주장하지 않는가?

출력 보고서에 `메인 README: 프로젝트 소개 적합성`, `기능별 README`, `도식`을 구분한다. 각 문제는 해당 위치·독자가 오해하거나 찾지 못하는 내용·최소 개선안을 제시한다. root 구조는 권장 목차 정도로 제안하고 직접 수정하지 않는다. 새 제품 코드 조사·테스트·보안 감사로 확대하지 않는다. 보고서 편집 소유는 기존 한 파일 그대로다.
