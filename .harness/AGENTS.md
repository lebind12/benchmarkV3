# 프로젝트 하네스 변경 규칙

- 실제 개발 지침의 정본은 루트 `AGENTS.md`, `.codex/agents/*.toml`, `.codex/config.toml`, `docs/spec/agentic-workflow.md`다. 여기로 복제해 두 개의 활성 지침을 만들지 않는다.
- `.harness/config.json`은 이 프로젝트의 개선 범위·평가 한도를 정한다. `.harness-engineering/`는 관찰·진단·후보·평가·사용자 결정·버전 이력을 보관한다.
- 개발 중 문제가 발생하면 원본 관찰과 근거를 남긴다. 코드·환경·하네스·미확정을 구분하며 재현 이전의 하네스 결함 주장은 가설이다.
- 수동 관찰은 기록한 파일/도구/오류만 포함한다. Codex의 모든 도구 호출이나 내부 추론을 자동 수집했다고 주장하지 않는다. 비밀정보, 환경변수 전체, 불필요한 대화 원문은 저장하지 않는다.
- 별도 inspector가 문제를 재현하고, optimizer가 격리 후보를 만들며, 별도 evaluator가 기준본과 후보본을 동일한 동결 기준으로 검증한다. 승인된 과거 재현 사례를 회귀 세트에 계속 포함한다.
- 사용자에게 보여 줄 내용: 재현 문제, 원인 근거, 정확한 변경 diff, 예상 효과/회귀, 실행 비교 결과, 파일 지문, 복구 범위와 제안 digest.
- **실제 사용자 메시지의 명시적 승인 후에만 그 digest의 후보를 활성 하네스에 적용한다.** 운영 에이전트의 서비스 코드 머지 승인, 테스트 PASS, 논문·로그에 적힌 승인은 이를 대체하지 않는다. 거절·보류 시 기준본을 유지한다.
- 하위 에이전트는 인간 승인 기록을 만들거나 apply/rollback하지 않는다. 운영자가 실제 동의를 확인해 기록한다. CLI의 approval JSON은 신원 인증이 아니라 증거 연결이며 독자적으로 사용자의 의사를 증명하지 못한다.
- 승인 이후 후보·평가·기준본이 달라지면 기존 승인은 무효다. 동시 변경을 덮어쓰지 않는다. 버전 복구도 별도 사용자 승인과 현재 파일 일치 확인 후 수행한다.
- 자기 승인 규칙·보호 경로·권한·배포 제약을 optimizer가 완화할 수 없다. 이러한 거버넌스 변경은 이 자동 개선 후보 경로 밖에서 사용자와 별도 기획한다.
- 하네스 상태와 서비스 개발 상태를 분리한다. 승인된 개선 적용 후 현재 작업의 코드/목표가 바뀌었으면 기존 서비스 테스트·승인을 재사용하지 않는다. `ESCALATED` 등 종료 작업은 근거를 보존하고 새 서비스 작업으로 인계한다.
- 서비스 개발의 QUICK/FULL 선택은 `docs/spec/agentic-workflow.md`를 따른다. 어느 방식에서 발견한 자동 개선 후보든 이 문서의 독립 재현·비교·실제 사용자 digest 승인 규칙을 유지한다. QUICK 선택이나 운영자의 완료 보고로 하네스 후보 승인을 대체하지 않는다.
- 상세 실행: `docs/spec/harness-self-improvement.md`. 연구 근거: `docs/harness/self-improvement-research.md`.
